## 拿不准的合并决定

- [用业务事件检验边界]、[以关键场景评价方案]、[按需要区分状态归属] 三节的插入位置选在 [依赖检测] 之后、[文件结构] 之前（贴近 C 原书顺序），而不是紧邻 [七大设计原则]；因为 K 现有章节顺序（任务→依赖检测→文件结构→第一性原则→七大设计原则→规模分级→设计维度清单→推演策略→信息充足度判断→对话示例→工作流程→初始化）里没有一个天然贴合三节内容的既有位置，选择「先立方法论，再进原则与维度清单」的顺序，衔接句在 [工作流程] 的 [推演阶段] 里显式串起三节与 [设计维度清单]/[推演策略] 的先后关系——如果应该贴着 [推演策略] 或 [设计维度清单] 放会更顺，请指出。
- [迭代与纠正]、[压力场景] 两节 T4 判「单边 C」，但 K 原本没有独立的迭代/压力场景章节（这类内容原来散在 [推演策略] 的棕地演进一句、[依赖检测] 的演进模式一句）；选择新增两个独立顶格章节而不是把内容拆散塞进既有句子，因为派单里明确列了 `[迭代与纠正]`、`[压力场景]` 两个节名——如果本仓更倾向把这些判据揉进 [推演策略]/[依赖检测] 而不单开新节，请指出。
- [压力场景]「既有仓库架构混乱」一条里引用的 `arch-check --record` / `arch-trend --gate` ratchet 机制，已用 `grep -n "baseline" .claude/harness/ext/graph.mjs` 核实本仓确有对应实现（含「forbiddenDependencies are declared boundaries, not debt: no baseline licenses them」的实测依据），判定为可以直接引用而非改写成「有该检查时」的降级说法；如果这个判断偏乐观（该机制还不够稳定到写进 Skill 正文），请指出。
- [签字前覆盖清单]「对应本仓章节」一列的映射（如「不变量与最小契约」→ [第一性原则] + [设计维度清单] 一致性约定/依赖规则）是本次重新撰写，不是 C 原表逐字翻译，因为 C 原表指向它自己的章节结构；格子名称（覆盖格第一列）与「要核的决定」一列保持与合成版一致。
- T4 把 `[回执]` 和 `[迭代与纠正]`、`[压力场景]` 分到同一行「单边 C」，但派单正文点名要搬的只有 `[迭代与纠正]`、`[压力场景]`，未提 `[回执]`；本次判断为有意排除——C 的 `[回执]` 是它被主 Agent 派发、执行完回传 Status/Changed/Verified 的子 Agent 汇报格式，本仓 arch-designer 是直接与用户对话的 Skill（不经派单/回执机制），[工作流程] 第六步已有对用户的「引导下一步」收尾，没有另开一份机器回执格式的必要——如果判断有误（该节该搬），请指出。
