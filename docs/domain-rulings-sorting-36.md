# 36 条全量分拣（2026-09-11）

素材：digifiber `Product-Spec-CHANGELOG.md` 的 11 个 `### 口径` / `### 硬约束` 段，共 36 条 bullet，v1.35（2026-07-16）到 v2.45.1（2026-08-31）。

分拣判据只有一句：**本次开发做完之后，这条还成不成立、还需不需要被下一个人读到？**

- **口径**：描述这个领域里事情是怎么算的，做完仍然为真 → 进库
- **范围限制**：约束本次改动边界（不新建表、不新增依赖、本批不改），做完即失效 → 不进库
- **待拆**：一条 bullet 里两类混着
- **事实记录**：既不是判据也不是限制，是「当前数据处于什么状态」

## 结论

**分布**：纯口径 24 条（67%）、待拆 8 条（22%）、纯范围限制 2 条（6%）、事实记录 2 条（6%）。去掉一处重复，实际口径 23 条。

**更正我上一轮的估计**。我说「粗看约 1/3 是范围限制」，错了——纯范围限制只有 2 条，6%。把待拆条目里的范围部分折算进去，范围内容约占 17%，不到我说的一半。

**但真正的麻烦不是比例，是 22% 的混合条目**。「不改①–⑤ 的口径和默认页签；加载/失败/空态/无命中独立可见，窄屏横滚降级」——前半句做完就失效，后半句是永久的 UI 状态口径。整条丢会丢掉真东西，整条留会留下过期噪音，只能一条条拆。8 条要拆，这是分拣真正的工作量所在。

**「事实记录」这一类是分拣逼出来的第四类**，我原来只设了三类。它既不是判据也不是限制，是「当前数据处于什么状态」——session3 的 74,586 行全 NULL、缺陷 B 全库唯一实例。它有时效、会被修复，但在被修复之前，任何读口径的人都必须知道。回填试验里我给它起名叫「已知污染」，全量分拣确认这一类真实存在，且不止一条。

**混合的成因值得记一句**：这些条目写在 CHANGELOG 里，而 CHANGELOG 天然是「本次做了什么」的容器。人在写「本次的约束」时，顺手把「永久的判据」也写进同一段——因为当时两者确实都在约束这次开发。混合不是写的人不严谨，是容器逼出来的。这反过来证明口径需要独立载体。
