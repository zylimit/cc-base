# 前期能力提升计划（2026-09-10）

目标由用户定：**架构完美、界面时尚易用、执行效率高、容错性好、加功能方便**。约束是「后期最多重来，只是时间问题，Token 不缺，时间不能接受」——所以本计划只收**能缩短返工反馈环**或**能机器判定**的条目，落不到「改哪个文件、加什么、怎么验」的一律不写。

**结论：纸面覆盖不差，缺的不是「有没有写」。**

## 1. 已坐实的缺口

1. **界面这条链在本机跑不起来**——`design-maker` 把外部 CLI `odc` 列为必需依赖，`which odc` 无；`ui-audit` 真渲染需 `playwright-core`，`require` 失败。四个目标里「界面时尚易用」的产稿工具当前是断的。
2. **跨文档一致性无闸**——`predev-lint` 查的全是单份文档内部结构（必需段、占位符、功能条目不许挂 `[待定]`、SCREEN 必需状态与响应式、DESIGN 前言 token 与段序、ADR 四字段）。Spec 的功能与实体 ↔ 架构模块 ↔ DFX 定档对象 ↔ Brief 页面，四者对不对得上没人查（只有 Brief 引 Spec 编号一条弱提醒）。
3. **架构 / DFX / 设计三步全是「可选」**——主控写「M/L 档推荐」「可选」，没有一个判定输出说「本项目这三步该不该做、不做的风险是什么」。想「前期满分」，这三步的取舍不该靠心情。
4. **前期假设的验证被推到开发期**——`dev-planner` 的「验证的假设」是好机制，但它在开发计划阶段才安排；方向性假设错了，此时已经晚了。
5. **没有时间盒**——Spec 模板全文没有「这个产品值得花多久」的概念。用户的真实约束是时间，而文档里没有一个字承载它。
6. **没有「不可逆决策」维度**——四种标记（`[确认]`/`[推断]`/`[默认]`/`[待定]`）表达的是**确定性**，没有表达**代价**：哪些条目错了必须推倒重来。用户最怕的正是这一类。

## 2. 需求分析（第一批，可立即落地）

来源：GitHub spec-kit 模板与 `/clarify` `/analyze` 命令、Shape Up、User Story Mapping、Amazon Internal FAQ、OpenSpec；实证参考 NaPiRE（228 家公司、10 国、同行评审）——按**导致项目失败**的比例排，第一位是 moving targets（需求漂移），不是需求不全。

> 方法学纪律：流传的「56% 缺陷源自需求」「一半预算是返工」这类数字来自厂商博客与少量老二手源，不写进 skill。

### 2.1 核心功能每条自带「怎么单独验」
- **改**：`product-spec-builder/templates/product-spec-template.md` 的「功能需求」段，核心功能每条尾部加 `验：<一句话，这条单独做完怎么证明它成立>`。
- **改**：`references/spec-self-review.md` 的 [完整性] 加一条——「核心功能全做、辅助功能一条不做，成功判据还成立吗？不成立说明切片切错了」。
- **闸**：`scripts/predev-lint.mjs` 加检查——核心功能条目缺 `验：` 报 warning（不报 error，避免为小项目添堵）。
- **为什么**：这是唯一能把「方向错了」的发现成本压到一条功能的机制。其余条目都在提高 Spec 质量，只有它在缩短反馈环。

### 2.2 时间盒（appetite）与已知无底洞
- **改**：模板「范围与非目标」段前加三行——`时间盒：<这个产品值得花多久>` / `已知无底洞：<明知会掉进去的坑，各一行>` / 非目标沿用现有表。
- **改**：`SKILL.md` [覆盖扫描] 的停问信号里加一句：时间盒定了才算范围收敛。
- **闸**：`predev-lint` 查「范围与非目标」段是否含 `时间盒`，缺则 warning。
- **为什么**：先定花多久再倒推做多少，正对「时间不能接受」。今天 Spec 模板里一个字都没有承载时间。

### 2.3 「这事成立要相信什么」
- **改**：模板「决策依据」段增设子段 `要相信什么这事才成立`，一行一条方向性假设，每条标「怎么证伪、什么时候证」。
- **改**：`SKILL.md` [复述理解] 在复述后加一问：这几条假设里，哪一条错了会让整件事白做？
- **接**：这些条目直接成为 `dev-planner` 每个 Phase「验证的假设」的上游来源，并优先排进最早能演示它的 Phase。
- **为什么**：把方向性赌注从隐性变显性。我们的签字闸是复述式的，复述能挑出「理解错了」，挑不出「前提就不成立」。

### 2.4 需求 ↔ 开发计划双向覆盖闸
- **接现成约定**：`harness.mjs trace` 已用 `[REQ-<模块>-<三位数>]` 做需求↔测试覆盖；本条复用同一套 id，不另发明。
- **改**：`scripts/plan-lint.sh` 增两项检查——① Spec 里带 id 的核心功能，DEV-PLAN 中无任何 Task 引用它 → 报「需求没人做」；② DEV-PLAN 的 Task 引用了 Spec 中不存在的 id → 报「悬空引用」。两项都只在 Spec 使用了 REQ id 时启用（小项目不写 id 就不查，与 `trace` 的现有口径一致）。
- **为什么**：这是「计划漏实现了某条需求」和「实现了没人要的东西」两类返工的直接机器闸，且成本极低。

### 2.5 待定问题表的配额与排序
- **改**：`SKILL.md` [收敛条件] 加一句——待定问题表超过 3 条即停下做一次收敛审计：按 `范围 > 安全隐私 > 体验 > 技术` 排序，排在后面的能用默认就用默认，不许拿一表未决进开发。
- **为什么**：防「问了一堆无关紧要的，同时漏掉真正决定方向的那一个」。我们已有问题预算（6-8 / 8-12 / 15 问），但没有对**遗留未决条数**的约束。

### 2.6 外部依赖与集成单列一类
- **改**：`SKILL.md` [覆盖扫描] 的十类里，把「数据与权限」拆出一类 `外部依赖与集成`——对接谁、谁的接口、挂了怎么办、配额与计费、数据出入口。
- **为什么**：这一整类今天靠对话直觉覆盖，容易整类漏掉；而它是架构边界与 DFX 韧性档位的直接输入。

## 3. 架构设计（第二批）

来源：ATAM / ALMA 可修改性评估、DSM propagation cost、MADR v4 与 log4brains 的 ADR 字段、Building Evolutionary Architectures 的 fitness function 分类、dependency-cruiser、arc42。
**已确认我们不缺的**：ADR 的「执法方式」我们已有且被 `adr-check` 机器校验，比 MADR 的 `Confirmation` 更硬；C4 停画判据我们的 C1/C2 已覆盖。

### 3.1 变更场景 + 触碰面预算（最该先做）
- **改**：`arch-designer/SKILL.md` 的 [设计维度清单] 把「关键场景走查」从「尽量落定」提到「必须落定」，并增一项 **变更场景走查**——列 3 个「半年内最可能来的新需求」，在模块图上各走一遍，数出**要改几个模块 / 总共几个模块**，写成 `触碰面 = 改动模块数 / 总模块数`，给出本项目可接受的上限。
- **改**：`templates/architecture-design-template.md` 增表：`变更场景 | 涉及模块 | 触碰面 | 是否超预算 | 超了怎么改边界`。
- **为什么**：这是把「加功能方便」从形容词变成数字的唯一低成本办法，零工具、无代码阶段可用。防的是「模块表评审时都说好，接第一个新需求才发现要动五个模块」。
- **诚实的局限**（写进 skill，别让人误用）：架构层面的估算系统性低估真实改动量（实证约 80%），所以这个数**只能用于方案 A / B 横比与自身趋势**，不能当绝对承诺。

### 3.2 传递波及率（接现成的 catalog，几乎零成本）
- **做**：`module-catalog.json` 的 `dependsOn` 本身就是一张依赖矩阵，对它求传递闭包即可得「改任一模块平均波及百分之几」。落点是 `arch-check` 的附加输出行，不新建子命令。
- **用法**：只做同项目内的趋势比较（进 `arch-trend` 棘轮，只许降不许升），不跨项目比、不设绝对阈值——该指标对模块数敏感。
- **为什么**：防「模块划分看着分层清楚、实则全连通」。这是 3.1 的机器化版本，在有 catalog 的项目上自动跑。

### 3.3 ADR 补两个字段：`revisit-if:` 与 `reversal:`
- **改**：`arch-designer/SKILL.md` [设计维度清单] 的 ADR 字段清单与模板同步加两项：
  - `revisit-if:` —— **什么条件出现时这条决策不再成立**（写条件，不写日期；例：「日活超过 5 万」「需要多租户」「团队超过 3 人」）。
  - `reversal:` —— **要撤回它得做什么、大概多久**。写不出撤回步骤的，就地判定为**单向门**，必须在 ADR 里显式标注并升级为用户拍板事项。
- **闸**：`adr-check` 已在校验执法方式，同批加校验这两个字段非空（沿用它现有的 fail 口径）。
- **为什么**：`revisit-if` 管的是「拿早已失效的前提当铁律继续建」；`reversal` 就是用户说的「哪些错了必须重来」——把不可逆性做成一个字段，而不是一节没人读的文档。MADR v4 与 log4brains 都没有这两个字段，这是我们可以走在前面的地方。

### 3.4 环检测（现有 `arch-check` 管不到）
- **事实**：`arch-check` 管的是「未声明的依赖边」，不等于「无环」。声明齐全的环，它是绿的。
- **做**：加一条零依赖的环检测（对 catalog 的 `dependsOn` 跑一次 DFS 找回边），命中报 error。Node 侧有代码后可另接 dependency-cruiser 的 `no-circular` 规则做文件级。
- **为什么**：环形依赖长成之后拆不开，加功能只能绕着走——直接抵消「加功能方便」。

### 3.5 时间维度的适应度函数（我们一条都没有）
- **事实**：我们现有五条 fitness 规则全是「改动触发、静态、单点」，没有一条是**随时间衰减**的。
- **做**：在 DFX-Spec 的可维护性维加一行依赖漂移预算（用 libyear：所有依赖落后年数之和，给一个上限），到期由 `fitness` 或 CI 定期扫。
- **为什么**：防「你没改任何东西、外部世界变了」这类被动返工——过期依赖出安全问题的概率显著高于最新版。这一条在无代码阶段就能把预算数字定下来。

### 3.6 baseline 棘轮泛化
- **现状**：我们只对 undeclared 边做了棘轮（`arch-trend --gate`）。
- **做**：把「基线入库、只许缩、新违规必红」泛化成任意检查可用的通用能力（`--baseline` + `--ignore-known`）。纪律照抄：baseline 文件入库、只许变小、与 CI 同构环境生成。
- **为什么**：老债不拦、新债必红。防「老违规撑绿把新违规混进来」。

### 3.7 空章节必须带理由（arc42 的防填空作业）
- **现状**：我们已有「押后决定」段与包络三态，思路一致但只覆盖两处。
- **做**：泛化成模板级规矩——`Architecture-Design.md` 任一必需段留空时，必须写一行 `留空理由：<为什么这个项目不需要>`；`predev-lint` 查「必需段存在但正文为空且无留空理由」→ error。
- **为什么**：今天缺一段是 error（逼你写），写了一句废话是绿的。加这条之后，「不需要」是合法答案但要署名。

## 4. 前端设计（第四批，杠杆最大）

来源：v0 / Lovable 的原始系统提示词、OpenAI 官方 frontend guide、DTCG 2025.10、axe-core 规则表、Material color utilities 源码。

**先说我们已经有的，别重复投入**：`ui-quality-floor.md` 已覆盖命中区 ≥24px（移动端 ≥44px）、焦点环不被 sticky 遮挡、拖拽必须有点击与键盘替代——正是 WCAG 2.2 AA 最常被漏的那三条，我们一条不缺。`style-vocabulary.md` 的 [AI 生成界面的通病] 已经点名奶油底 + 衬线大标题 + 陶土橙那套、过度居中、紫色渐变、一律圆角、Inter 当个性、每段淡入上滑。

**所以真正的缺口只有一个形状**：我们的清单是**定性的、写给人读的**；缺的是把同一份清单变成**数字**和**一条能跑的扫描**。而且——

> **这一节能顺手补上本机的断链**。`design-maker` 依赖外部 `odc`（本机没有）、`ui-audit` 真渲染依赖 `playwright-core`（本机没有）。下面 4.2 的扫描是**纯静态源码扫描**，不需要浏览器引擎，本机立刻能跑。

### 4.1 把通病清单数字化（写进 DESIGN.md 模板，当生成前约束）
- **改**：`design-brief-builder/templates/design-md-template.md` 增一节「硬约束」，值直接可查：
  | 项 | 约束 |
  |---|---|
  | 主色 | 不用紫 / 靛作主色；不用「奶油底 + 衬线大标题 + 陶土橙」整套 |
  | 色彩数量 | 总色 ≤ 5，渐变色标 ≤ 3，不单一色相统治全屏 |
  | 字体 | 字族 ≤ 2；正文 ≥ 14px；letter-spacing 不为负；字号不随视口缩放 |
  | 行长与行高 | 正文 `max-width: 65ch`；`line-height` 1.4–1.6 |
  | 圆角 | ≤ 8px；不全场统一一个圆角；禁卡中卡、禁区块做浮卡 |
- **为什么**：这些正是「一眼 AI」的成因，且全部是数值——写在 token 文件里既约束生成、又能被机器验。

### 4.2 源码级「AI 味」静态扫描（本节最该先做）
- **做**：新增 `scripts/ui-slop-scan.mjs`（暂名），纯静态读源码与 CSS，输出 `file:line + 命中项 + 严重度`，退出码非零即红；支持 `unslop-ignore` 行内注释逃逸（有意为之的写明理由）。
- **判据就用 4.1 那张表** —— 一份清单两用：生成前是约束，生成后是闸。检测形态是 hex 值与 Tailwind 类名的正则（`purple-`/`violet-`/`rounded-2xl` 之类）、token 计数、`max-w` 与 `text-` 尺度。
- **接线**：`dev-builder` 四步走第一步 Code Review 时跑；有 UI 的 Phase 才跑，无 UI 跳过。
- **为什么**：今天我们只能在**渲染之后**用 `ui-audit` 发现难看，而 `ui-audit` 需要浏览器引擎、本机没有。静态扫描把这道闸提前到编码当场，且零依赖。
- **诚实的边界**：静态扫得出「用了禁色、圆角过大、行太长」，扫不出「整体气质对不对」。后者仍归 design-maker 的三方向样张与人眼。

### 4.3 色阶算出来，不手挑
- **改**：`design-brief-builder/SKILL.md` 的视觉方向环节，要求主色定下后**按算法生成色阶**（Material 3 的 tone 表：primary 40 / container 90 / onSurface 10，暗色反转为 80 / 30 / 90；或 OKLCH 固定亮度 11 档 + gamut mapping），并把生成结果直接验一次对比度。
- **为什么**：手挑色阶的典型症状是亮色勉强能看、暗色当场翻车。算出来的色阶自带对比度保证。

### 4.4 暗色地板（我们的地板只有 4.5:1，暗色场景不够）
- **改**：`references/ui-quality-floor.md` 增四条 MUST：底色从 `#121212` 起不用纯黑；层级靠白色叠加表达（4dp ≈ 9% 白）不靠更黑；主色在暗色下降饱和；最底层与白字对比 ≥ 15.8:1。
- **为什么**：纯黑底 + 高饱和主色是暗色模式眩光的标准配方；层级靠「更黑」表达则在最高层级面板上必然失效。

### 4.5 动效 token 表
- **改**：`design-md-template.md` 增动效 token——时长分档（50 / 100 / 150 / 200 / 250 / 300 / 400 / 500 / 700 / 1000ms 取用），**进场用减速曲线、离场用加速曲线，两者必须不同**。
- **现状差距**：我们只有「动效可关」「只动 transform / opacity」，没有「该多长、该用哪条曲线」。
- **为什么**：所有元素同一条 ease 是 AI 味的隐形来源之一；这条半可检（能数动效密度，曲线正确性查不了）。

### 4.6 生成前的四个先决决策（不可机器检，但必答）
- **改**：`design-brief-builder/SKILL.md` 的收敛条件加四问，缺一不许进 design-maker：① 参照锚是什么（具体产品，不是形容词）；② 主色从哪来（品牌 / 行业惯例 / 内容本身，不是「看着好看」）；③ 为什么选这个字族（一句理由）；④ 这一屏的首要动作是什么、布局怎么对应它。
- **为什么**：R3 的判断值得原样记住——**病因不是「用了紫色」，而是「没做选择」**（a tell is an unspecified default, not a banned color）。前面五条都是在堵默认，这一条是在逼选择。

### 4.7 可选基建（先不做，记着）
- `stylelint-declaration-strict-value` 让硬编码 hex 直接构建失败：**先只开 color**，spacing 早开会逼模型编造不存在的 token 名。
- `DESIGN.md` 迁到 DTCG 2025.10 标准格式（已 stable，7 基础 + 6 复合 `$type`），好处是 lint / 主题生成 / shadcn 都能自动消费。属于收益明确但不紧急。

## 5. 执行效率与容错（第三批）

来源：Lighthouse 官方 budget 文档、web.dev 性能预算、Google SRE Workbook、Azure Well-Architected RE:03、IETF 幂等键 draft-07。
**全部按档位适用**——S 档小工具只做 5.1 与 5.3，别拿支付系统的成本压原型（沿用 dfx 的档位经济学）。

我们现在的问题不是没写，是**写了词没写数**：dfx 第 2 维韧性写着「有界重试 + 退避、熔断、限流、超时预算」，第 6 维性能写着「预算分解」——四个词，没有一张表、一个数字。词是挡不住返工的。

### 5.1 延迟预算树 + 重试预算（合并成韧性维的一张必填表，优先做）
- **改**：`dfx-designer/templates/dfx-spec-template.md` 增一张表，列为 `层 | 预算(ms) | 超时(ms) | 重试次数 | 退避 | 失败时的 fallback`，末行 `端到端` 且**各层之和 ≤ 端到端目标**。
- **改**：`dfx-designer/SKILL.md` 第 2 维韧性的「对策」里，把「有界重试 + 退避」升格为三个必填数字——每请求最多 3 次、**每客户端 retry/total ≤ 10%**、**全链路只指定一层做重试**（其余层禁重试）。
- **为什么**：重试次数在 N 层链路上是 3^N 放大（5 层就是 243 次），「有界重试」四个字挡不住它；超时不做自上而下分解，每层都觉得自己不慢、端到端却是各层之和。这两类都是上线后才炸、且必须动架构才能修。
- **验**：`predev-lint` 查 DFX-Spec 若含该表，则各层预算之和 ≤ 端到端值，且重试层数 = 1；不满足报 error。这是纯算术，机器判得动。

### 5.2 三个算术护栏（无代码阶段就能算）
- **改**：`dfx-designer/SKILL.md` [过堂阶段] 第 6 维性能前加一步「先算三个数」：
  - 容量：`QPS = 日请求量 / 86400`，`峰值 QPS ≈ 均值 × 10`，`存储 = 单条字节 × 日写入 × 保留天数 × 副本数`。
  - 利用率天花板：目标利用率 ρ 下的排队放大 `≈ 1/(1−ρ)`——跑到 80% 利用率，尾延迟是空载的 5 倍。定容量时把这个系数算进去。
  - 扇出宽度：单次请求扇出 N 个依赖、每个慢的概率 p，则**至少一个慢**的概率是 `1−(1−p)^N`——N=50、p=1% 时是 39%。
- **为什么**：这三条是纯算术，在还没有一行代码时就能算出「这个设计撑不住」，而这类结论一旦晚到就是选型级返工。
- **验**：不做机器闸（输入是估算值，机器判不了真假）。改为 `spec-self-review` 加一问：非功能表里的性能数字，是拿这三条算过的还是拍的？

### 5.3 幂等键契约表（我们完全空白）
- **改**：`dfx-designer/SKILL.md` 第 1 维可靠性的「对策」里，「幂等」升格为一张表：`作用域（账号 + key）| 指纹字段 | 在途返回 409 | 指纹不匹配返回 422 | 保留期 24h | 完成标记与业务写同事务`。
- **触发条件**：Spec 里出现付款、下单、扣减、发送、外部调用重试任一项即必填；否则 N/A + 理由。
- **为什么**：断网重试不重复建单这类要求，我们的范例 Spec 里已经写了（「提交成功即落库，断网重试不重复建单」），但没有落到契约。事后全表补幂等是最贵的返工之一。

### 5.4 依赖故障模式表（M/L 档必填，S 档可 N/A）
- **改**：`dfx-designer/templates/dfx-spec-template.md` 增表，列为 `依赖 | 风险类型 | 可能性 | 影响与缓解 | 挂了整体还能用吗`，风险类型取值固定八种（超时 / 限流 / 错误响应 / 数据损坏 / 版本不兼容 / 认证失效 / 配额耗尽 / 完全不可达），并标**强依赖**（它挂产品就挂）还是**弱依赖**（可降级）。
- **为什么**：「每个外部依赖挂了会怎样」是最容易整类漏掉的一问，而它同时是架构隔离边界的输入。
- **验**：`predev-lint` 查表内每行「挂了整体还能用吗」列非空；强依赖数量 ≥ 2 时提醒「单点过多」。

### 5.5 前端性能预算文件（有 UI 的项目）
- **改**：`dfx-designer` 输出阶段增一步——有 Web UI 的项目产出 `perf-budget.json`（Lighthouse budget 格式），起始值用 web.dev 缺省：关键路径资源 ≤ 170KB、TTI < 5s，再按项目调。
- **接**：`dev-planner` 把它写进含 UI 的首个 Phase 的验收标准；有 CI 的项目由 Lighthouse CI 卡。
- **为什么**：预算是**决定**不是测量，所以能在无代码阶段就写成文件；等做完再量就只剩「要不要重构」这一个选项。

### 5.6 不做的
- **SLO + 错误预算政策**：仅当项目对外提供服务、且有真实用户量时才做（L 档）。单人内部工具写 SLO 是仪式，不是工程。
- **完整 FMEA / RPN 打分**：5.4 的五列表已经够，RPN 三维打分对单人项目是纯负担。

## 6. 两件必须你拍板的事

### 6.1 `design-maker` 的外部依赖要不要拆掉
现状：它把 `odc` 列为**必需**依赖，本机没有，所以这条链此刻产不出任何稿。而我们自己的 skill 里写着 odc 是「本地 daemon 驱动，**内部调用 Claude/Codex agent 生成 HTML**」——它包的就是 Claude，而我们本身就在 Claude Code 里。

两条路：
- **甲：装 odc + playwright**。保持现状不动，代价是每台机器都要装，Windows 工作机上多半又是一轮折腾。
- **乙：给 design-maker 加一条无 odc 的兜底路径**——主 Agent 按同样的 prompt 结构（design system 基底 + DESIGN.md token 覆盖 + 八态 + 真实数据 + 离线自包含）派 implementer 直接写单文件 HTML，odc 在就用 odc，不在就走兜底。
我的建议是乙，理由是它去掉一个硬依赖、任何机器都能出稿，且产物形态完全一样。但这是改家底 skill，按规矩你拍板。

### 6.2 架构 / DFX / 设计三步的「可选」要不要变成「判定」
现状：主控写「M/L 档推荐」「可选」，没有输出说清本项目该不该做。想要「前期满分」，这三步的取舍不该靠当时的心情。
建议：`product-spec-builder` 收尾时多输出三行判定——依据风险档位、模块数、有无 UI、是否涉钱涉个人数据，给出「架构：建议做 / 可跳过（理由）」「DFX：…」「设计：…」，跳过的写清跳过的风险。不强制执行，只是让跳过成为一个有署名的决定。

## 7. 排期

按「杠杆 ÷ 成本」排，不按章节顺序。每批做完跑 `predev-lint` + `run-all --level high` + 拿售后派单范例走一遍验证。

**第一批（立刻做，收益最直接）**
1. **4.1 + 4.2**：通病清单数字化 + 纯静态 AI 味扫描。一份清单两用，零外部依赖，同时补上本机断链——四个目标里「界面时尚易用」当前最缺的一环。
2. **3.3**：ADR 补 `revisit-if:` 与 `reversal:`。`adr-check` 已有校验框架，加两个字段边际成本极小；`reversal` 写不出即判单向门，正对你说的「哪些错了必须重来」。
3. **5.1**：延迟预算树 + 重试预算三个数字。一张表，`predev-lint` 用纯算术就能验（各层之和 ≤ 端到端、重试层数 = 1）。
4. **2.4**：需求 ↔ 计划双向覆盖闸。接现成的 `[REQ-模块-编号]` 约定，`plan-lint` 加两项检查。

**第二批（结构性补强）**
5. 2.1 核心功能「怎么单独验」+ 2.2 时间盒 + 2.3 要相信什么 —— 三条同批改 Spec 模板与 skill。
6. 3.1 变更场景触碰面预算 —— 把「加功能方便」变成数字。
7. 5.3 幂等键契约表 + 5.4 依赖故障模式表。
8. 4.3 色阶算法 + 4.4 暗色地板 + 4.5 动效 token。

**第三批（机器化，收益慢但持久）**
9. 3.2 传递波及率（接 catalog，进 `arch-trend` 棘轮）。
10. 3.4 环检测；3.6 baseline 棘轮泛化；3.5 依赖漂移预算。
11. 跨文档一致性闸：`predev-lint` 扩出 Spec 实体 ↔ arch 模块 ↔ DFX 定档对象 ↔ Brief 页面的四向核对。
12. 2.5 待定问题配额；2.6 外部依赖单列一类；3.7 空章节须带留空理由。

**明确不做**
- SLO 与错误预算政策（单人内部工具写它是仪式不是工程，L 档对外产品再说）。
- 完整 FMEA 的 RPN 三维打分（5.4 的五列表已经够）。
- 整套 EARS `shall` 语法（作者自己承认价值在 mindset 不在 syntax，只借 `IF…THEN` 不良行为模板一条）。
- 把 `stylelint` spacing 规则早开（会逼模型编造不存在的 token 名，先只开 color）。

## 8. 方法学纪律

调研里凡是只有二手来源的，本计划都标了或直接弃用：
- 「56% 缺陷源自需求」「一半预算是返工」这类流传数字来自厂商博客与少量老二手源，**不写进 skill**。可用的实证是 NaPiRE（228 家公司、10 国、同行评审）：按导致失败的比例排，第一位是需求漂移。
- 架构层面的改动量估算系统性低估约 80%，所以 3.1 的触碰面数字**只能横比与看趋势**，不能当绝对承诺——这条要写进 skill，防止后人误用。
- 传递波及率对模块数敏感，只做同项目内趋势。
- arc42 模板原文与部分 ADR 字段说法未取到一手，落地前复核。
