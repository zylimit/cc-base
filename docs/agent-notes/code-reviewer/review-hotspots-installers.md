- 高发模式：安装器新增「同一文件拷两处」的分支时，按**路径键**的机制不会跟着走——`harness/audit/instructions-allowlist.json` 的 `file` 键、`FRAMEWORK-MANIFEST.txt`、四份排除表各自认路径，第二份副本拿不到豁免/记录，下游装完被自家地板审计判红。新增拷贝目标路径时逐个对这四处。
- 薄弱模块（2026-09-19 发现，2026-09-22 TODO #74 修过一轮，见下条）：`setup.sh` / `setup.ps1` 的可选包分支（`--with-tests` / `--with-harness`）刻意绕过 manifest 分层，也绕过主循环的排除表过滤（`.bak` / `.DS_Store` 等不再被挡）；两侧 copy 语义还不同（sh 走 `copy_file` 留 `.bak`，ps1 走 `Copy-Item -Force` 不留），fresh 装对等、重装才分叉。
- 2026-09-22 复审现状：排除表用两侧手写的 `is_optional_excluded()` / `Test-OptionalExcluded()` 补上（只收叶子级 `.bak`/`.DS_Store`/`signals.jsonl`/手写追加的 `state/*`，不进 `@exclusions` 生成块）；ps1 侧改走 `Copy-WithBackup` 留 `.bak`，两侧对等；rules/ 顶层限定两侧一致。**新的两条残留**（探针见下条复现法③④）：①手写排除表与 `exclusions.json` 脱钩——`gen-exclusions.mjs --check` 管不到它，往 json 加新叶子级条目不会自动同步进这两个函数，探针已实测「往沙箱 json 塞 `*.future-lock` 重新生成后，主循环挡住、`is_optional_excluded` 不挡，文件真的漏进 `--with-harness` 装出的目标」；②可选包**永不拒绝覆盖**，跟主循环「不确定就不碰 live、落 `.framework-new`」的语义不同——dry-run 对「用户真改过的可选包文件」和「纯框架版本升级」都报同一个 `update`，核心文件对应场景报的是 `conflict`；连续两轮「改动→重装」会让第二轮的 `.bak` 覆盖掉第一轮的 `.bak`，只保一代。
- 2026-09-22 审 #81/#82 修复现状：手写排除表已删，`gen-exclusions.mjs` 从 `exclusions.json` 的 `optionalLeaf:true` 条目同时产出 `setup.sh is_optional_excluded()` / `setup.ps1 Test-OptionalExcluded()`（新增 `mainTree:false` 字段让 `state/*` 这类只供可选包用的条目不进主循环三张表），R6 探针（往沙箱 json 塞新叶子条目、重新生成、装出验证）两侧都过。覆盖语义改走 `plan_and_apply`/`Invoke-PlanAndApply`：与主树共用同一判定函数，`.bak` 消失、改用「不确定就落 `.framework-new`」。**新发现的 HIGH**：这个共用函数靠「target 当前 sha == 旧 FRAMEWORK-MANIFEST.txt 里记的 sha」判「安全升级可 update」，但 `harness/ext/*` 与 `tests/*` 是故意不入 manifest 的（gen-manifest.sh 的排除表），所以对这两棵子树 `old_sha` 永远是空字符串——`update` 分支对可选包文件是不可达代码，任何内容差异（哪怕是纯粹的上游版本升级、target 那份文件用户一个字节都没碰）一律判 conflict、落 `.framework-new`，不会像主树文件那样自动升级。实验：`--with-harness` 装一次 → 只在 SRC 侧改一个 ext 文件内容（target 不动）→ 重装 → 该文件仍报 conflict（对照组：同样手法改一个主树文件，会正确报 update 并原地升级）。影响：以后每次框架引擎升级，凡是 target 装过 `--with-harness`/`--with-tests` 的项目，每一个改动过的 ext/tests 文件都会变成需要手工合并的 `.framework-new`，即使那份文件从未被使用者改过——`①对等语义` 的「未改的文件被更新」这条对可选包文件永远不成立。sh:`setup.sh:290-313 plan_and_apply()`（`old_sha` 查询与 else 分支注释「可选包文件本就不入清单」已经自己点破这个后果，但没意识到这是缺陷）；ps1:`setup.ps1:254-272 Invoke-PlanAndApply()`。
- 复现手法（比读代码硬）：① 在 scratchpad 拼出「装完后的目标树」，把框架自带审计脚本连 `lib.mjs` + 白名单一起拷进去按相对路径跑（`scan-instructions.mjs --paths …`，无 `--staged` 时不需要 git）；② `bash setup.sh --dry-run [--with-harness] <scratchpad 目标>` 只写目标侧锁文件，可安全对比两种模式的 plan 条数；③ 判「手写排除表会不会漂移」：把整个 `setup.sh`/`setup.ps1`/`.claude`（`git ls-files -z --cached --others --exclude-standard | tar` 天然跳过 worktrees）拷进沙箱，往沙箱里的 `harness/exclusions.json` 塞一条新叶子级条目，在沙箱内跑 `node .claude/scripts/gen-exclusions.mjs`（无参，真重写，只动沙箱文件），比对新条目有没有进主循环生成块、有没有进手写函数，再装一次看文件漏没漏；④ 判「默认行为有没有被带坏」：旧版（`git show HEAD:setup.sh`）和新版各自拼一份源码沙箱，都跑默认安装（不带任何 `--with-*`），`diff -rq` 两个目标树的 `.claude`，空输出 = 字节级不变。
- 判缺陷影响面时的链路：审计脚本 rc 1 → `.claude/githooks/pre-commit` 的 `classify audit` 判 block → commit 阻断；githooks 随装进目标但 `core.hooksPath` 要用户自己 `install-githooks.sh on`，所以「会不会真拦」取决于下游是否开了 githooks，而 `.github/workflows/gate.yml` 的无参全量扫描一开就持续红。
