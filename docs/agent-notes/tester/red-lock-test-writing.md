红锁测试的断言写**修复后应该成立的行为**，不是「缺陷能复现」。复现式断言（现在 exit 0、修好变 exit 1）语义是拧巴的，修完还得反过来改一遍。

**Why:** 红锁的两个目的是「缺陷固化成永久回归防线」和「修复有客观靶子（红转绿）」。复现式断言两个都拿不到——它修完就得删。

**How to apply:**
- 整体现在必须 FAIL，那是成功状态；交付时把「哪几条红、红因是功能缺失」逐条核到。
- **偶然绿的断言要显式标注**（如「白名单 sha256 不符须失效」——机制还没实现时命中本来就报错，绿得毫无信息量）。标成「防回归位」，别让人误读成已实现。
- **别读实现源码来决定断言**，用行为探测：先在临时仓造一次条件，观察脚本的实际能力（如「行内压制标记还认不认」），把结论存成变量喂给后续断言。这样实现换了路子测试不会假红。
- 一条缺陷若有多种合规修法（降级 rc 3 / 真扫到 rc 1），断言写**否定形式**（「rc 不许是 0」），别钉死某一种。
- **否定形式必须点名主体，别写成「N 个命令里至少一个非 0」**：析取判据会被**用法错 rc 2** 冒充成「检查真抓到了」。踩过一次——E4b/E4c 跑一列命令里混了个引擎从不存在的 `ledger --verify-evidence`，旧 parser 静默吞未知 flag 时它 rc 0 无害，parser 一收严变 rc 2，两条断言从此拿用法错撑绿，真正该由 `ledger=1` 提供的证据被垃圾数据盖住。写成「`ledger` 自己 rc != 0」才验的是它本该验的东西。
- **验红打两版补丁，不是一版**：只废掉主判定者的（如只让 `ledger` 失明、`risk` 仍报）证明新判据比旧的严——旧析取判据在这版下照样绿；全废的（整条校验失明）证明缺陷本体仍被抓。只跑后者说不出「判据有没有被改弱」。
- 主 Agent 的目标行为裁定里若含技术上讲不通的部分，顶回去说理由再写，别闷头按错方案写一堆将来必删的断言。
- **「可见性断言」不替代「判定断言」**：实测过一次——`check-syntax` 的 SKIPPED 被改回 rc 0 时，原有的「SKIPPED 行必须打印出来」照样绿，只有另加的 rc/ok 断言才红。凡是「X 要在输出里看得见」的断言，旁边必须再配一条「X 导致的判定必须是什么」。
- **新断言交付前必须做一次反向验证**：临时把对应实现改回旧行为，确认新断言真的红且点名，再 `cp` 还原（勿 git checkout，见 [[audit-scripts-fragile-zones]]）。只跑正向全绿等于没有断言——顺带还能看出哪条老断言其实是摆设。
- **改「锁了旧行为」的断言不是删掉了事**：一条换一条起步，覆盖面只许涨不许缩；与红锁重叠的部分在行为测试里写成一条冒烟即可，深水区（哈希失配、条目过期）留给红锁，两边不重复造轮子。
- **被测代码在 Out of Scope 时这样验红**：让测试脚本收一个位置参数指向被测实现（`REPO` 目录或单个 `.mjs`，默认本仓），把被测对象 `cp` 到 /tmp、在副本上打补丁，然后 `bash 测试.sh /tmp/副本` 跑同一份断言。正向红锁在副本上打「修复补丁」验转绿；已修好的分支则反过来打「退回旧行为」的变异补丁验必红。零改动、无还原风险，比改本仓再回滚干净得多；顺手 `sha256sum -c` 复核仓里那份逐字节没动过再收工。顺带再打一版「天真修法」副本（如只加拦停、不接熔断），确认防砖类断言真的会红，别让它当橡皮图章。
- **命令的自述状态不能当判据，要取旁路派生的收敛态**：实测过一次——`stop` 的 win32 分支被改坏后，它自己把孤儿子进程收了，照样回 `{"ok":true,"status":"stopped"}` rc=0；只有另跑 `status`（从 state.json + pid 存活派生）才看得见真相是 `dead` + state 停在 `running`。断言写在自述上那一版，变异后全绿。凡「做完了吗」类断言，判据一律换成独立命令读到的落盘状态。
- **测试自身的卫生也要有断言，否则那个修等于没锁**：清理逻辑（杀进程、删临时文件）改错了整套照样绿。把它变成一条真断言——如按记录下来的各 childPid 当 pgid 查残留进程，精确到组所以不误伤并发跑的别的测试。实测把 `kill -9 -pgid` 改回单杀，这条立刻红并打印出泄漏进程；没有它，那个修永远没人守。
- **对照组的期望值必须写死字面量，不许从「同批别的探测」的结果里取**：实测过一次——路径归一化三态里，相对路径那条本该在变异下仍绿（用来证明红的是绝对路径那两态），但它拿了态一探测回填的变量当期望值，态一一红它跟着红，对照组当场失效。写死同一个字面量，两种写法同名照样锁得住。
- **单元测试守住了工具函数，不等于守住了调用点**：`repoRelative` 的三态单测早就在 selftest 里，但坏在 `path.resolve(root, dir)` 这个调用点上时它一动不动——变异改的是「谁喂给它」。凡是「helper + 调用点」成对的归一化逻辑，断言要落在 CLI 行为层（records 有没有真读到 + source/note 报的是不是同一个地方），单测只是补充。
- **防砖/熔断类断言按轨迹判，别按次数判**：stop-gate 三振熔断的实际形态是 `BBB.B`——5 次里拦 4 次。写成「blocks<=3」会把正确实现判红。正解是记轨迹串，断言「前 4 次里至少出现一次放行」。
- **契约里「哪个字段/形态算合规」不确定时，用行为探测选形态而不是赌**：主 Agent 给的修法有两条等效路（如哈希扩到三行窗口 / 要求豁免行仍在围栏内），断言就只写否定形式（「这次攻击后豁免不许还生效」），两条路都能转绿；控制组那半则先拿候选形态各试一次、把实际被接受的那种存进变量（`BOUNDFORM`）喂给后续断言，实现换了写法测试不会假红。
- **契约从「可选」收严成「强制」时，只补正向断言挡不住回退**：实测过一次——把 `context` 改回可选（无 context 也豁免）后，「绑对了→生效」那条照样绿，只有「没绑→不生效且打点名 note」那条才红；反过来把白名单整个废掉，两条一起红，而反向那条靠的是**note 必须出现**才没被 rc=1 蒙混。收严类改动一律正反各一条，反向那条断言里必须点名那条 note。
- **「A 表有的 B 表也得有」类断言必须限定在 B 的表体内比，整文件 `grep -F` = 永久免检**：实测过一次——⑥ 拿整文件比四份排除表，`settings.json` 在 setup.sh 别处有 13 行、`'FRAMEWORK-MANIFEST.txt'` 在 release.mjs 另有个同名常量，这些臂从表里删光照样全绿。正解是先把表体抽出来（case 块 / 数组字面量 / 规则数组各自的起止）再逐条 `grep -qxF` 整行匹配；顺带整行匹配才分得清 `.DS_Store` 和 `*/.DS_Store` 这种子串关系。
- **首中即返回的表还要比「序」和「处置」，不能只比集合**：`case` 和 `manifestIncludes` 都是首个命中即返回，垃圾臂挪到 keep 臂之后就漏出去而集合毫无变化；把每条抽成 `<臂>TAB<drop|keep>` 后整序列 `cmp`，序、缺、多、keep 翻面四类漂移一网打尽。结构不同没法比序的那份（如 ps1 全是无条件 drop）就改为断言「它凭什么与序无关」，一旦出现 keep 分支当场红提醒回来补。
- **抽取式断言的自检写死条数，别写 `-ge`**：`-ge 20` 而实际 34，抽取正则半坏只抽到 25 条时闸不响、后面逐条比对全在空转。写死 `EXPECTED_ARMS=34` 并在报错里附「另一份表相对它多出哪些」，红了一眼看出是表改了还是抽取坏了。
- **正反两向的红因都要留在输出里**：`chk` 的 GOT 字段把原始 rc / 完整 stdout / 轨迹串全打出来，主 Agent 不用重跑就能判「这条红是 hook 没实现」还是「夹具没搭起来」。脚手架自证（沙箱 git 仓、catalog 就位、故障引擎确实给出契约外码）单独列一段并保持全绿，红全部集中在行为段。
- **红锁除了「验它现在红」，还要验「它修得好」**：把一版候选修复打进实现跑一遍，确认整组转绿。只验红证明得了缺陷在，证明不了这组断言彼此相容——防砖条款（如「仓外路径不许被改写」「不存在的路径不许崩」）很容易和主断言冲突，implementer 接手才发现就晚了。实测：软链归一化那组 5 条，候选修复下 5 条全绿且 selftest 268 不动，才敢交。
- **红锁跨了派单 Goal 没点名的同源方向时，照写但在回执里点出来让主 Agent 裁定**——别闷头扩范围，也别因为「派单没说」就放着同一处缺陷的另一半不锁。软链那条：Goal 只点名「入参经软链」，实测「根经软链、入参真实」是同一处 realpath 基准不对称的镜像方向，只 realpath 入参补不上。
- **「每条表成员一条断言」挡不住表长出新成员——必须再加一条成员集合对拍**：⑤ 给 10 条 pathspec 各写了断言，但加第 11 条时全体沉默，新成员天生免检（那九条前缀裸奔很久就是这么来的）。对拍写法：从**被测那份** core.mjs 里抠数组字面量成员，与测试自己的用例表排序后 `cmp`，报错打印「core 独有 / 本文件独有」。实测加一条假 pathspec、加一条假前缀都当场红并点名。
- **对拍断言必须能分辨「表真的变了」和「我的抽取正则坏了」**：这两种红的处置完全相反。做法是抽取返回哨兵值 + 写死期望条数（不写 `-ge`），抽不到就报「抽取坏了，不是表变了」。实测把被测表整个改名（模拟正则失效），红的是抽取自检那条而不是成员比对那条。
- **「特例先行」的老段落会伪装成全覆盖**：`.runtime/` 那条 untracked 断言写在前面，注释一句「③ 走的是 STATE_EXCLUDE_PREFIXES」就让人以为七条前缀都被守着，实则只守了一条、另有三条 PATHS 一条没碰。写覆盖类注释要点明「覆盖的是表里的哪几条」，别用表名替代条目。
- **「不可读 ≠ 不存在」这类红锁，判据必须同时锁「码」和「话」**：`stop` 遇到坏 state.json 本来就 rc 1，只断言退出码那条天生是绿的；真正的缺陷在它说「no state for id」——文件明明在。写法是 rc + 「必须出现 corrupt」+「不许出现那句误导的话」三件套，缺一条就漏。同理 `gate` 的 reason 早就是 `every-check-skipped`、只有退出码是 0，所以 reason 和 code 要一起断言。
- **grep 类判据别让 fixture 的 id 里带上判据关键词**：给 supervisor 的坏 state 用例最初取名 `corruptstatus`，`grep -q corrupt` 会命中 id 自己，断言恒真。改成 `badstate/badstart/badstop` 才验的是输出里真有 corrupt。
- **「拒绝执行」类断言不能只看它回了什么，要看副作用有没有发生**：`start` 遇到坏 state.json 该拒绝，判据取 state.json 的 sha256 前后一致——它被覆盖就说明第二个 supervisor 真起来了并开始写。只看 rc 会被「回了错但照样起了」骗过。
- **候选修复不必覆盖全部契约，挑「防砖条款最多的那条」验就够**：9 条红锁里只给 S1（receipt 不可读，含「不删/不改/不重命名」三条防砖 + 一条对照）和 S4（rc 3 + 对照仍 0）打了候选修复，两条当场转绿且既有 268 条一条没破——足以证明这组断言彼此相容。单形态断言（某字段要出现）互相打架的风险低，可以不验。
- **selftest 的候选修复验证要整棵目录拷**：`.claude/harness` + `.claude/tests/fixtures` 一起拷到 `/tmp/x/.claude/` 下保持相对层级，`loadFx()` 的 `HARNESS_DIR/../tests/fixtures/harness` 就能找到夹具，然后在副本上打补丁跑 `node /tmp/x/.claude/harness/harness.mjs selftest`。仓里那份全程零改动，比 cp 备份 + trap 还原干净。
- **改「锁了旧契约」的断言，两向变异各跑一次**：契约从 rc 0 改成 rc 3 后重写断言，只跑正向全绿说明不了它有没有变成橡皮图章。变异 A（rc 退回旧值）与变异 B（rc 对但新字段 note 被拿掉）各跑一遍，两次都该红且失败信息各自点名自己的因（A 打 `exit 0`、B 打 `exit 3` 但输出无 note）——B 那次才证明新加的字段合取不是凑数。
- **把意图写进冗余合取里**：`[ "$RC" -eq 3 ] && [ "$RC" -ne 2 ]` 后一半逻辑上恒真，留着是因为契约的意图是「不阻断」而 2 才是阻断；将来谁把契约改成 2，红的是这条点名「阻断」的断言，而不是一句光秃秃的数字不符。
- **`cases/test-harness.sh` 的 `ROOT` 从 `BASH_SOURCE/../../..` 推导，所以变异验证走「整棵树拷到 /tmp」**：`tar -cf - --exclude=.git . | tar -xf - -C /tmp/mut`（本仓 5MB，秒级；对仓纯只读，不惊动并行 agent），在副本的 `lib/` 上打变异再跑 `/tmp/mut/.claude/tests/cases/test-harness.sh`。它不像 test-release-manifest.sh 那样收引擎路径入参，别去找那个参数。
- **同一族缺陷补第二轮时，期望值去「引用已经修好的那一半」，别自己发明**：先把已修好的形态（如「文件在但 JSON 解析失败」）逐个artefact 实测一遍当参照表，再把新形态（「文件在但打不开」）的断言写成「落在同一个答案上」。这样每条期望都是引文不是发明，reviewer 问「凭什么是 rc 3 不是 rc 2」时有据可答；顺带自动覆盖到 quarantine 留痕这种容易漏掉的伴生要求——参照表里有，就该有。
- **每条 lane 的控制组用 ENOENT（真不存在）并写死字面量**：这一族的全部危害就是「读不出来被当成不存在」，所以控制组必须钉住「真不存在时行为一个字节不变」，否则修复很容易矫枉过正、把正常的空仓也拦了。实测 10 条 lane 配控制组后打候选修复，277 条老断言一条没破，就是这组控制组挣来的。
- **探到「派单没点名的裸崩」要报不要断言**：`task start` 撞上目录形态的 task.json 时 `writeAtomic` 的 `renameSync` 直接抛未捕获 EISDIR，stdout 空、stderr 是 node 堆栈还带机器绝对路径（仓里明文禁止的回显形态）。这属于另一个缺陷、正确答案也没人定过，写进断言就是替主 Agent 定契约——回执里点名让他裁。
- **幂等断言用「整棵目录指纹」比只比一个文件抓得多，但发现要拆成命名清晰的独立断言**：拿目录指纹比 fix-platform 二次跑，红在 `settings.json.bak` 上——`.ps1` 侧写备份、`.sh` 侧不写，且二次跑把备份覆盖成归一后的内容（迁移前的原件就此没了）。指纹那条读起来像噪声，拆成「⑥ settings 逐字节不变」+「⑦ 首次的备份不许被二次跑覆盖」之后，红因一眼可判、也不会被当成夹具毛刺驳回。

- **「输出里要出现关键词」类断言，先在被测程序的现有输出里搜一遍那些词**：实测过一次——「接管陈旧锁要说一句」的备选词里放了 `残留`，被 setup.sh 自己那句「清理异平台残留 + chmod」冒充成绿；同理 `too long` 会被 mkdir 的 ENAMETOOLONG 顶包、裸 `64` 会被路径里那段 `s64` 顶包。选词后必须在「该功能没实现时的实际输出」里 grep 一遍确认零命中，再配一条点名主体（锁文件名 / pid）的合取。
- **回显整条路径会让「点名犯规的那一段」这一列变成橡皮图章**：路径边界类断言里，被拒消息通常把整个 target 打出来，于是 `grep -F "$seg"` 恒真。判别力只能靠 rc + **一个目录都没建**（validate 跑在 mkdir 前，半截目录树就是没跑）。段本身是 `.`、或规则针对的是数量（总段数超限）时，这一列干脆传哨兵值显式跳过——硬凑会误伤正确实现，实测候选修复就栽在这两条上。
- **候选修复要连「已有的老段落」一起跑，跨段约束只有这样才浮出来**：批 5 的锁 / 标记住在 `.claude/.runtime/`，而老段落 ⑤ 是按 `[ ! -e ]` 判**目录**的——装完只删两个文件、留个空目录，⑤ 当场红且报的是「运行态目录被装进产物」，看起来跟批 5 毫无关系。跑了候选才发现，于是把「装完 .runtime 整个不留」补成一条显式断言摆在功能所在的那段里。只跑自己新加的那几条断言看不见这类耦合。
- **给「新加的段落」单独开 pass/fail 计数，别硬塞进 fail-fast 的老脚本**：老脚本 `fail(){ exit 1; }` 撞见第一条就走人，四个互相独立的新功能只能看见第一个红。加一组自己的 `chk` 计数 + 末尾 `PASS=n FAIL=m` 汇总 + 非零退出，老段落一行不动；脚手架自证（首装成功、探针文件在、doctor 基线绿）仍走老的 fail()——它红了后面的断言没判别力，继续跑只会产出误导性的红。
- **红锁落在 fail-fast 脚本（`fail(){ ...; exit 1; }`）里时，同一次运行只看得见第一条红**：test-setup.sh 就是这形状，⑥ 的计数一红，末尾新段整段不执行。派单要求「只有新增段红并点名」时别硬凑——照常写，另跑一版「软失败」探针（`sed` 把 `fail()` 换成计数器 + 末尾打总数，跑完删）把后面几条红一次亮出来当证据。pass/fail 计数式的脚本（test-release-manifest.sh）没这问题。
- **给「N 份表互相对拍」的族加新条目，必须连写死的条数一起改，且要先分清哪份是自动抽的**：cc-base 六份排除表里，test-setup ⑥ 的基准臂表是从 gen-manifest.sh **自动抽**的，真正写死的只有 `EXPECTED_ARMS` 和 ps1 映射表；test-release-manifest ⑥ 的 `EXP_PREFIXES` 等则和自己的用例表配对。把期望条数 +1 而不给自己的用例表加行，会变成「修完仍红」的坏锁——两边必须同步加。
- **往「先提交进 HEAD 再改内容」的表驱动段（如 ⑤c 的 once-tracked 形态）加新用例，会把那个文件永久留在 HEAD 里，把后面段落顶红**：test-release-manifest ⑤c 提交 ALL_TRACKED 后，新加的 worktrees 用例就一直在磁盘和 HEAD 上，⑦ 的脚手架自检当场变红、红因还错记成「功能缺失」。后续段落的前置清理要 `rm -rf` **加**一次 `git add -A -- <路径> && commit`（清 HEAD，不只清工作树），并在注释里写明清的是哪一段留下的。
- **「逐条都合规」类断言在集合为空时会空转全绿，校验器提前返回必须填哨兵而不是缺省值**：给 MUTANTS.json 写的 lint，文件不存在时只发了 `EXISTS NO` 就 return，于是「每条 find 恰好一次」「每条字段齐全」因为一条都没有而全 PASS——红锁最想锁的那几条反倒成了免检。改成 bail 时把逐条类字段一律填 `<NOT-CHECKED>`，红了还一眼看得出是「没扫」不是「扫过没问题」。
- **正向的 rc 断言同样会被「用法错 rc 2」冒充，不只是析取判据**：新模式没实现时裸跑就是 usage rc 2，于是「not-applicable 应 rc 2」「脏树拒跑应 rc 2」两条红锁当场假绿。判据要和「stdout 真是那份 JSON」或「输出点名了主体」绑成一条断言，别让退出码单独作证。
- **验「修得好」不必真改被测文件**：按被测入口的路径推导规则把候选实现放成**同目录的另一个文件名**（`harness-golden-candidate.mjs`），测试收路径入参指过去跑同一份断言，跑完删掉。实测这一步当场抓出两个只验红看不见的问题——stdout 被老 banner 污染、以及上面那条空集假绿；且证明了 kill 用的突变真 kill、注释突变真 survive（后者错了会让 implementer 追一个不存在的目标）。
- **整批被测文件还不存在时（如 22 个 hook 一起换运行时），单边断言全是假绿**：「stdout 为空 / stderr 非空 / rc=1」在 node 报 module-not-found 时统统成立，实测 12 条这样被顶绿；每条必须配一个正向合取（rc 的具体值 / 关键字段真的在）。更阴的是 module-not-found 的报错里**带着被测文件名**，`grep <主体名>` 类判据照样被顶包——`static-check` 那条靠 `hasq static-check` 恒绿，换成点名行为的 `hasq unsafe` 才红。收紧后 PASS 从 12 掉到 0，那才是干净的红。
- **「文件不存在」型整批红锁，用仓外薄壳控制组证明红是真红**：`cp -R .claude /tmp/ctrl` 后给每个 `X.mjs` 造一个转发到同名 `X.sh` 的两行薄壳（`spawnSync("bash",[sh,...],{stdio:"inherit"})`），lib 按契约手写十几行，再跑同一份测试。232/239 绿就同时证明了两件事：夹具是好的、仓内那 239 条红全出自「文件缺席」。剩下的红逐条分档——控制组自身限制（薄壳找不到没拷进沙箱的 `.sh`）/ 派单明确要求的行为变更 / 真夹具 bug。对仓库零改动，比在仓里塞桩干净。
- **锁类红锁：后台持锁进程 + ready 文件握手，持锁时长卡在两个阈值中间**：`node -e '…' &` 后台真 `fs.openSync(lock,'wx')`、拿到就写 ready 文件，测试用 node 轮询等 ready（别用小数秒 `sleep`，Git Bash 不保证有）；持锁时长要 > 被测的 LOCK_WAIT（hook 必然等不到、走裸跑分支）且 < LOCK_STALE（这把锁全程「新鲜」、按契约不该被回收），否则红因会飘成「锁陈旧被回收」。另：裸跑分支下的丢更新，「只删自己拿到的锁」这类一行修复挡不住——那条断言只能锁「不删别人的锁」，别把挡不住的东西写进同一条判据里凑数。
- **一个夹具里放两个能各自独立触发同一判据的样本 = 析取，单臂突变顶不红**：`src/a.mjs` 与 `src/a.cjs` 同改一份工作树、断言只看 `decision:block`，正则里删掉 `mjs|` 那一臂，`.cjs` 照样把 block 顶出来、断言仍绿——`.mjs` 那臂等于没锁。规则表 / 扩展名表 / 白名单这类「多条目命中同一出口」的被测面，**一个条目一个沙箱**，写完必须逐臂突变自证（删臂 A → 只有 A 红、B 仍绿；再删臂 B 反过来一遍），还原后 `sha256sum` + `git diff --quiet` 双证被测文件没被留下痕迹。
- **被测是「薄壳 / 转发器」时，判据必须走旁路命令**：把 `off` 变异成「只 print 不转发」，薄壳自己的回显照旧说 standard，四条断言里只有那条另跑 `node harness.mjs tier status`（读到 `tier=fast source=session`）的才红。转发器问它自己等于让它给自己判卷——这跟「命令的自述状态不能当判据」是同一条病的薄壳形态。
- **「前后一致」类断言要配非空转闸**：`$after -eq $before` 在夹具坏掉（两边都读不到文件）时恒真。加一条 `$before -ne ''` 合取，夹具一坏它就红并打出 `recordedBefore=<empty>`，与真缺陷分得开——实测「沙箱少拷一棵 lib」那版变异就是靠这条才没假绿。
- **被测脚本「尚不存在」时，只判 rc 的用例会被 `Cannot find module` 撑绿**：node 找不到模块也是 rc 1，凡期望 rc=1（有 error）的用例必须再判一条正向证据（`--json` 里那个 code 出现），否则实现写好前后这条断言的结果一模一样，等于没锁。实测 25 条里有 18 条期望 rc=1，全靠 code 判据才红。同理，「缺依赖 → rc 3 缺席」这类用例天然免疫，因为 rc 值本身就区分得开。
- **写「文档格式闸」的红锁，接受用例要和拒绝用例一样多**：一个把所有文档判红的 lint 和一个什么都不判的 lint 一样没用，而只写坏样例时，实现方无脑 `rc 1` 就能全绿。合规夹具（全对、围栏内不扫、缺文件跳过、warning 不阻断）就是防这个的对照组；顺带把「随 skill 发布的示例文档必须过自己的闸」写成一条，能同时验出模板和规则谁对不上。
- **两个缺陷叠在同一份夹具上时，rc 会互相打掩护，判据必须点名 code**：P29（缺必需段该报 MISSING_SECTION）用的夹具同时踩了 P28 的 MADR 标签缺陷，现状 rc 已经是 1——只判 `rc=1` 那版会当场假绿，判「rc=1 **且** 含 MISSING_SECTION」才红。收尾要跑一次 findings 明细（`--json` 里逐条打 code），确认红因是你要锁的那条；再跑一次「只修另一个缺陷」的控制组，看这条是否仍红、且红得干净。
- **「报了，但报错了地方」这类缺陷，判据必须按行号写，判 rc / 判含不含 code 都测不出来**：诱饵段抢锚点那条，闸照样 rc=1、照样有 PENDING_ROW_INCOMPLETE——只是三条全指着诱饵表，真正缺格那行零输出。断言写成「该 code 的行号列表恰等于 [真行号]」才抓得住。配套加个 `fjq()` 从 `--json` 的 findings 取行号（`filter(code).map(line).sort()`），别在 JSON 文本上 grep。
- **同族双实现（predev-lint.mjs / harness spec.mjs 这种同病两闸）要各自实测，别信派单里的合并描述**：派单说「两个闸目前都 rc 0」，实测 spec-lint 已经 rc 1——它对尖括号是全文都扫（在 pending 判断之前），只有 TBD/TODO/待补 被段内 `continue` 吃掉。按 rc 写的 lane 会当场假绿，只有按「哪几行该报」写才红。
- **尖括号/成对符号类的扫描会跨单元格配对，夹具必须覆盖「一行里两个孤立括号」**：`| 首屏 <1s | 并发 >100 |` 的 `<` 和 `>` 分属两个格子，正则把中间整段（含 `|`）当成一个占位候选报出来。只拿 `<x>` 这种规规矩矩的单个占位做夹具，永远测不到这类误报；判「像不像占位」的规则也因此必须看候选内容（含 `|`、以数字/`=`/空白/`-` 开头就是比较式）。
- **同族两闸的修复进度可能不同步，一条口径要给两边各自实测**：这轮编号归一化，`spec.mjs` 已经吃得下 `## 1) 待定问题`、`predev-lint.mjs` 还不能——同一条口径写出来一条红一条绿是正常的，别当夹具写错去「修」它。绿的那条按防回归位标注清楚，红的那条才是红锁。
- **表格/分隔行识别失灵的红长成「什么都不报」，不是「报错地方」**：`|:-:|` 不被认成分隔行时，整张维度总表被判成没有表头，UNMEASURED 一条都不出，`rc=0 ok=true`——看汇总行像通过。所以表格类断言一律写成「某 code 的行号恰等于 [数据行]」，把「零输出」也纳进红里；只写「rc=1 且含 UNMEASURED」的话，这类失灵会安静地绿着。
- **去重实现会把 finding 的行号钉在首次出现那一行，判条数会漏判**：P44 里反引号示例行和裸写行各有一个同名坏记号，闸按记号名去重、只报一条——条数=1 完全符合「恰 1 条」，但那一条指着**示例行**。凡是「某类行不该被扫」的断言，判据必须落在行号上，条数只能当补充。
- **判「像不像占位」这类首字符规则，夹具要成对造紧贴版与带空格版**：实现读的是正则原始捕获还是 trim 之后的串，差一个空格就是一整类漏报——`<数据库选型>` 报、`< 数据库选型 >` 不报，两个都造才看得见。同理比较式也要造 `<1s` 和 `< 100` 两版，防修的时候把带空格的比较式一起判成占位。
- **跨闸对拍的判据只能落在两闸共有的维度上，先探 code 词表再定判据**：predev-lint 用 `PENDING_ROW_INCOMPLETE`、spec-lint 用 `PLACEHOLDER` 表达「待定表行缺格」同一件事，派单要求的「`行号:code` 集合相同」永远不可能成立——修好也不成立。实测两边输出后改判**行号集合**相同（再加一条「都把真段认作待定段」），才是既可达又抓得住锚点被抢的判据；用例说明里要写明为什么不比 code，否则下一个人会以为是漏写。
- **参数化对拍要把「哪几个参数不一致」打进 GOT**：七种编号写法只有全角 `）` 与 `．` 两种分歧，GOT 里点名这两种并附 `predev=[…] spec=[…] 应为[…]`，实现者一眼知道补哪两个字符；只写一句「不一致」等于让人重跑一遍才知道改什么。
- **模板自身就是现成的坏样例，别手造**：把 `skills/*/templates/*.md` 原样拷成正式文件名（`product-spec-template.md` → `Product-Spec.md`）跑一遍闸，模板里没填完的槽全是天然夹具，比手写更贴近真实误用（作者拷了模板直接交）。配套必须同时锁「五份范例仍 rc 0」——两边一起才证明闸认的是「填没填」而不是「像不像模板」；实测过 `{{…}}` 进闸后范例零误伤，就是靠这一对。
- **新增一类占位语法时，把扫描挂进既有的行循环能白捡免检机制**：predev 的 `line = stripCode(doc.lines[i])` 已经吃掉行内反引号、`doc.fenced[i]` 已经跳过围栏，`{{…}}` 只要加在这个循环里，反引号与围栏的豁免自动继承、一行不用写。但测试里仍要各锁一条——下一个实现者完全可能另起炉灶写个独立扫描器，那时免检就没了。
- **跨闸对拍的「另一闸报空」必须算不一致，别用 `[ -z "$X" ] ||` 放过**：我这次差点留个假绿洞——`SL=$(sfall ...)` 在 spec-lint 报空时得到空串，`[ -z "$SL" ] || [ "$SL" = "$PL" ]` 会直接跳过整条对拍。改成哨兵值（`SL=未跑`，跑过就覆盖）之后，空集与非空集比较照样红。判据里凡是「取不到就跳过」的分支，都要问一句：取到了空值算不算问题？
- **候选修复只覆盖一侧时，跨闸对拍那条仍红是对的，别当成断言不可达**：本批候选只打了 predev，P49b/P52/P53b 全转绿而 P53 仍红——红因是 spec.mjs 没跟着改，正是这条断言存在的意义。报告里要把「哪几条因候选覆盖不全而仍红」和「哪几条是断言本身有问题」分开说。
- **调外部检查器当判据时，必须同时断言「它确实扫到了东西」**：`harness fitness --paths` 只认相对仓根的路径，喂绝对路径会返回 `scannedFiles=0 findings=[]`——我第一版 U22 就这么绿了，看着像「没有空 catch」，其实一个文件都没扫。判据加上 `scannedFiles>=1` 之后立刻转红并点名两行。凡是「工具报了零问题」的断言，旁边都要有一条「工具真的看过目标」的断言，否则路径写错、参数改名、工具降级三种情况都会安静地绿。
- **锁「行为要反转」的契约，三个变异各验一条**：① 把追加句整句删掉（天真的「删了就算修」）——只该打死正向那条；② 把条件换成恒真（无条件追加）——只该打死两条否定断言；③ 让 hook 静默（emit 前 return）——全组该一起红，证明否定式断言不是被空输出顶绿。实测 subagent-acceptance-reminder 的 Domain findings 反转：A 红 1 条、B 红 2 条、C 红 4 条，三发各打中不同的那条才说明三条断言各管一件事、没互相搭便车。**追加句里带两件事（如「证据归类」+「定论归主 Agent」）时补第四发：只写半句**——这发才分得出判据是合取还是析取，析取在它下面照样绿。实测新措辞那轮：整删红 1、只写半句也红 1（`证据分类=有 只报不判=无`）、恒真红 2、静默红 4。
- **锁「哨兵值 = 没有」的判据，夹具必须造带括注的变体，裸 `None` 测不到真实回执形态**：子 Agent 写回执的自然写法是 `**Domain findings**: None（本轮全是框架自身测试基建）`，而实现若写成 `/^(none|n\/a|无)[.。]?$/` 这种**锚定到行尾**的否定判断，括注一加就整条翻面判成「真有发现」。裸 `None` 那条用例全程绿着，照不出来——我自己那份回执就当场被闸误判了一次。同族形态至少造四个：裸 `None` / `None（中文括注）` / `None (english paren)` / `无（括注）`。
- **措辞迁移期的负向断言，尺子必须是跨两版措辞都成立的词**：给「不许追加那句」写断言时只判**新**措辞的标记（`证据是哪一类` / `只报不判`），旧措辞的追加句照样漏出来而新标记天生不命中——四条用例当场全假绿（PASS=27 FAIL=1 看着像只差一条），GOT 里 `追加段` 结尾那个孤零零的「另」字是唯一线索。挑一个两版都含的词（本例 `领域发现`）当泄漏探针，新标记留着钉目标措辞，两样合取；泄漏句按 `${AC##*<该词>}` 打出来，红因直接可读。
- **被主 Agent 否掉的候选实现就是现成的变异体，拿它证明每条新增臂不是凑数**：判据定稿前往往摆过两三种写法，否掉的那些各自只在某一种输入上出错——把它们逐个打进候选跑全套，应当恰好打死为它而加的那一臂。实测这轮三发：定稿 T2 全绿 31/0；被否的 `\b` 版红 2（`无（括注）` + **裸「无」**，后者正是为「会退化」才补的臂）；被否的纯前缀版红 1（以「无」起头的**真**发现被吞）。一发打死不该死的、或某臂谁都打不死，就说明臂选错了——比事后讲理由可靠。
