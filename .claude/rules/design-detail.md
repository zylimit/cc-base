[定位与边界]
    - **设计详述 = 某个模块内部的算法与业务规则到底怎么算**：阈值、先后顺序、例外、取代关系，一字不落写下来，每条带代码位置和测试。文档分层里它在 Architecture-Design（模块怎么划）之下、代码之上；DEV-PLAN 管排期，不管规则。
    - 起因：规则只散在 progress.md 的流水账和代码里，几十条一晚上反复改，一旦脱离 AI 就没人说得清程序为什么这么判。设计详述要做到的是：规则全写下来，代码改了文档必须跟着改，机器查得出漏改。
    - **一个复杂模块一份，简单模块不强制**：放 `docs/design/<模块名>-设计.md`。存在即维护、不存在的不强造；判「复杂」看规则数与反复改的频度，不看代码行数——同一模块的规则一周内改过两次以上、或规则超过五条，就该开一份。Architecture-Design §2 模块表的「设计详述」栏写路径或「无」。
    - 与已有几样划清界限：`domain/` 口径库记**领域里事情是怎么算的**，跟领域走、换了代码库仍成立；设计详述记**本模块代码怎么落实这些口径**，带代码位置、常量和测试，跟仓库走。一条规则同时是口径时，口径进 domain/，设计详述的来源栏引口径编号（`R-CLU-002`），不两头抄判据。progress.md 的 Decisions 是项目决策，属于某模块算法规则的，正文进设计详述，progress 只留一行指针。Product-Spec 的规则与例外是产品要什么，设计详述是代码按什么算，Spec 改了规则含义要回填设计详述，反之设计详述冒出产品层取舍要回 Spec。

[文档结构]
    模板在 `.claude/skills/arch-designer/templates/design-detail-template.md`，结构固定、段名不改（design-trace.mjs 按段名读，three-file-sync-gate 读文首代码范围行）：
    - 文首 `> 代码范围：` 一行，反引号括起的路径或通配（`**` 跨目录、`*` 不跨目录），相对项目根，逗号分隔；反斜杠当 `/`、开头 `./` 与末尾 `/` 忽略，不含 `*` 的条目按目录或文件前缀算（`src/restore` 等于 `src/restore/**`）。闸门靠它判「改了这个模块的代码」，写漏了闸就看不见。
    - `## 1. 概述`：输入、输出、一句话流程。
    - `## 2. 规则`：按执行顺序分节（`### 2.1 第一步：…`），每条规则一个四级标题 `#### <编号> <一句话标题>`。
    - `## 3. 常量表`：表头固定 `| 常量名 | 值 | 代码位置 | 含义 | 用于 |`；常量名写代码里的名字原样，代码位置写定义它的文件（相对项目根），用于写引用它的规则编号。
    - `## 4. 已知例外与坑`：不成规则、但改代码的人必须知道的。
    - `## 5. 取代记录`：被取代的规则整条搬到这里，标题后加「→ 被 <日期> <新编号> 取代」，不删。

[规则条目]
    - **编号**：`<模块缩写>-<步骤缩写>-<两位序号>`，全大写字母数字加连字符（`TR-OLT-03`）。编号一经发出不复用、不改号；规则改了含义就发新号、旧号进取代记录，只改措辞不改判据的原号保留。
    - 六个字段全部必填，模板里逐条标了：
      - **规则**：一句话判据式写法，禁用「一般」「大概」「通常」「尽量」「适当」——写不成一句就拆两条。判据里出现的数字（阈值、上下限、个数、时长、比例）一律写常量名、常量进常量表，不写裸数字；代码里同处也用这个常量，不内联字面量。design-trace 只核常量表，裸数字改了它看不见。
      - **来源**：谁、哪天、原话（用户拍板写原话；实测撞出来的写实测数；引口径写口径编号）。
      - **例子**：输入 → 输出，合成数据，严禁真实数据（真站点名、真 IP、真坐标一律换掉）。
      - **代码**：`文件:函数`，多处逐个列。
      - **常量**：用到的常量名，与常量表对应；判据里没有数字才写「无」。
      - **测试**：对应测试名；还没有写「待补」，design-trace 会把它报成缺口。
    - 测试里用注释标它验的规则编号：Python / Shell `# rule: TR-OLT-03`，JS / TS `// rule: TR-OLT-03`，一个用例验多条用逗号分隔。标签是规则与测试之间唯一的机器链接，测试名字段只给人看。

[核对脚本 design-trace.mjs]
    `node .claude/scripts/design-trace.mjs [--root <目录>] [--json]`，扫 `docs/design/*.md` 与项目里的代码文件，报四类缺口：
    - 文档有编号、没有任何测试标它（只认测试文件里的标签：路径含 test / tests / spec / __tests__ 目录，或文件名 test_*、*_test.*、*.test.*、*.spec.*、*Test.java / *Test.kt / *Tests.*；非测试文件里的标签不算数，末尾只提示）；
    - 测试标了编号、文档现行规则里没有（标的是已被取代的编号单独说明）；
    - 常量表里的值与代码里同名常量的值对不上，或代码位置里找不到这个常量，或同名常量在代码位置文件里有多处赋值（定义不唯一；注释、文档字符串里的不算）；
    - 结构缺口：规则段里 `####` 标题解析不出编号、某份设计详述一条现行规则都没有（只有模板占位也算）、文首没有代码范围行或只有占位、某条通配在项目里匹配 0 个文件。编号后面允许跟任意标点，标题可用 `**` 包裹编号。
    退出码：0 全对或没有设计详述（跳过），1 有缺口，2 用法错，3 脚本内部错误（stderr 一行说明，不与「有缺口」混）。输出是人话清单，`--json` 给机器读。

[接进流程]
    - **派单**：改动触及有设计详述的模块（文件落在其代码范围里）时，派单包 Business Context 抄对应规则编号与一句话规则；implementer 回执的 Business assumptions 之后必须写「改了哪几条规则 / 新增哪几条」，没动规则写「规则未动」。
    - **记决策**：progress.md 要记的 Decision 属于某模块的算法规则时，主 Agent 当场把规则写进设计详述（新号或取代旧号），progress 只留一行指针：`- 日期: <模块> <编号> <一句话> → docs/design/<模块名>-设计.md`。
    - **Stop 闸**：three-file-sync-gate 在原有判定之外，查未提交改动里有没有落在某份设计详述代码范围内的代码、而那份设计详述没改——有就提醒。档位单列一行 `design-detail-sync`：fast / standard 提醒，strict 拦。只改了测试、没改规则含义的，在设计详述里补测试名即可过闸。
    - **审查**：code-reviewer Stage 1 核对改动是否违背设计详述里的现行规则；违背的报「需求存疑」，或要求先改设计详述再改代码，不默认代码对、文档错。
    - **Phase 四步走第 2 步、发版装配**：跑 design-trace.mjs，rc 1 记 CONCERNS，缺口清单进残留；rc 2 当脚本用错修好再跑。没有设计详述的项目 rc 0 跳过。
