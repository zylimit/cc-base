本文件由 CLAUDE.md 下沉；主控命中指针时必须完整读取本文件再行动，不得凭指针行猜测内容。

[定位与边界]
    - **口径 = 这个领域里「事情是怎么算的」**：跟领域走，不跟仓库走、不跟人走。换了代码库、换了实现者之后仍然成立的才是口径，这是它与其余三样的分界。
    - **它是副产品，不是流程环节**：口径长在需求分析、澄清、方案设计的对话里——那些过程本来就要发生，顺手把结论留下而已。不进四步走、不设卡点、不出现在任何验收链路上；没有 domain/ 不报错、不催补。它存在的理由只有一个：让 AI 下一次输出更准的需求规格、更稳的架构、更好用的前端设计。跟本项目的域有关的会最多，扯得很远的也收，持续往上长。
    - 与已有三样划清界限：progress.md 的 Decisions 是**项目决策**（跟项目走）；.claude/feedback/ 是 **AI 工作方法的纠正**（跟 AI 走，与领域无关）；Spec 的功能需求是**产品要做什么**。口径是第四种——产品做什么、代码怎么实现都可以变，事情怎么算不跟着变。
    - **载体：项目根的 `domain/` 目录**，与 Product-Spec.md 同级，不塞进 .claude/（那是框架自己的东西，口径属于项目的领域）。存在即维护、不存在的不强造——框架本体没有领域，没有 domain/ 是正常的。
    - 判一条该不该进库，两问按顺序过：**① 收它是为了让 AI 下次输出更准，不是为了记全**——答不出「下次哪一步会因为它不一样」就别收，哪怕它是真的；记全的代价是让 AI 在一堆正确的废话里挑管用的那条，那是噪音的另一种形状。② 本次开发做完之后，这条还成不成立、还需不需要被下一个人读到？成立且需要 → 口径；只约束本次 → 不进。
    - 条目形态：ID + 一句话标题（`R-CLU-002 Cluster 边界＝整簇凸包`），出处（CHANGELOG 版本 + 日期 / 用户拍板）附在依据栏末。
    - 按域分文件（`domain/<域>.md`），**域取自领域本身，不取自本项目的模块划分**：OLT / Cluster / 光功率 / TOPO 是域，行业规范、组织里怎么办事、某个外部系统的脾气也是域。和本项目八竿子打不着却值得留的那类，给它自己立一个域，别为了归类把它判出库；一时归不到域的先进 `domain/_未归域.md`，攒够一类再拆出去。与检索的「按域」维度同一套，不另立第二种组织方式。

[七栏]
    - **现行值**：判据式写法——「关联键＝OLT IP，禁止用 OLT 名」，不是叙述式的「通常用 IP」。叙述式给 AI 留下补全空间，判据式没有，这一栏的写法本身就是防幻觉。
    - **依据**：分三类，**三类之外（凭记忆、凭推断）说得再确定也不收**，这是防噪音唯一的闸——① 实测撞出来的（实测数、表结构、跑不通的实验：「全库 0 条 cable_segments 接触 OLT」「74,586 行全 NULL」「headless 重登跑不通」）；② AI 查外网得到的（协议规范、厂商文档、标准条文）；③ 人查公司内部得到的（内部规范、历史上定过的事、只有在场的人知道的那条）。分工是定的：**AI 去外网找，人去公司内部找**，两边信息源不重叠，所以一条口径常要其中两类才立得住——实测撞出现象，外网或内部说清它为什么是这样。回填 8 条只有 4 条填得满，填不满的位置就是知识流失的位置。
    - **适用范围**：这条在哪些查询、页面、导出上生效。没有范围的口径会被用到不该用的地方。
    - **取代**：顶掉了哪条旧口径，旧条标记不删。
    - **失效条件**：什么情况发生后这条不再成立（「OLT 命名统一到同一套规范后需重评」）。多数能从依据倒推——依据没了，口径就没了。
    - **被谁依赖**：哪些口径、指标、导出引用了本条，改它要连带复核这些。
    - **已知污染**：口径对、生产数据不满足前提（某 session 的 connectivity 全 NULL）。是暂时不成立、会被修复，不是失效。
    后两栏是回填逼出来的不是设计出来的——边界算法被四处引用、TOPO 口径正确但数据不达标，都是填到一半发现没地方放。
    **一条只写一个判据**：一句里出现两个判据就拆两条。36 条里 8 条要拆，混着写就是这么来的。

[四类分拣（36 条实测：口径 24 / 待拆 8 / 范围限制 2 / 事实记录 2）]
    - **口径**：做完仍为真 → 进库。
    - **范围限制**：约束本次改动边界（不新建持久表、不新增依赖、本批不改），做完即失效 → 不进库。
    - **事实记录**：当前数据处于什么状态，有时效、会被修复，但修复前读口径的人必须知道 → 作为「已知污染」挂在对应口径下，不单独立条。
    - **待拆**：一条里两类混着（「不改①–⑤口径与默认页签；加载/失败/空态独立可见」前半句做完即失效、后半句永久）。整条丢会丢掉真东西，整条留会留下过期噪音，只能一条条拆——这是分拣真正的工作量。
    - **混合不是写的人不严谨，是容器逼出来的**：这些话写在 CHANGELOG 里，而 CHANGELOG 天然是「本次做了什么」的容器，人写本次约束时顺手把永久判据写进同一段。这条就是口径需要独立载体的证据。

[三种变更]
    - **修订**：判据不变、值变了——是同一条的新版本，不是新条目。Cluster 边界「凹包外轮廓 → FAT 外轮廓 → 整簇凸包」是一条的三版，拆成三条就是在库里造三个互相矛盾的真相。
    - **取代**：新口径顶掉旧的，旧条标记不删——AI 会检索到旧措辞，删了只剩幻觉，标了才知道这条不算数。
    - **收窄放宽**：值不变、适用范围变了。最容易漏记，因为看起来什么都没改。
    - **版本机制不自己造**：口径文件只保持现行态，修订历史进 git，`git log` 就是修订链。只有**取代关系**要在条目里显式写——AI 读不到 git log。

[四种老化]
    - **条件失效**：失效条件命中 → 该条作废。
    - **关联失效**：被依赖的口径变了 → 依赖它的全部进待复核。**这条最重要也最容易漏**——改 Cluster 边界时没人会想起覆盖健康、责任区、整改单导出三处都引用它。「被谁依赖」栏准不准，决定这条跑不跑得起来。
    - **批量失效**：模块下线，其口径批量作废。
    - **污染**：口径对、数据不对，是暂时不成立、修复后自动恢复。**不能混进失效**——混了就会有人去改一条本来正确的口径。

[三个触发源（可靠性递减）]
    - **机器发现（最可靠）**：条目引用的字段、表、接口不存在了 → 该条进待复核。照 `adr-check` 查幽灵引用那套做；能机器判的只有引用是否落空，判不了口径本身对不对。
    - **事件驱动**：某条被修订 → 依赖它的自动进待复核。前提是「被谁依赖」栏准，栏不准这条就是空转。
    - **干活时撞见（最不可靠、覆盖最广）**：走反例回流，与 code-review / tester / bug-fixer 报「需求存疑」同一条路，只是终点是口径库不是 Spec。红蓝审查也在这条路上：Red 刻意攻死角，攻出来的一部分是缺陷，另一部分是「原来这个域是这样的」——后者按缺陷判会被关成无效，该当线索送进来。
    - 进待复核 ≠ 自动改：改一条口径要有新的依据，依据栏那三类的门槛在复核时同样成立。
    - **明确不做定期复查**：定期扫 23 条还行、200 条就是仪式，最后没人做；且多数口径是定义型、几年不变。与本仓「闸靠数据留，不靠感觉留」同一逻辑。

[两条硬约束与回流去向]
    - **采集必须寄生在已有动作上**，不许新增「记得去记录」的步骤。实证：.claude/feedback/ 38 条里 20 条没被 CLAUDE.md / rules / skills / agents 任何一处按文件名引用过（2026-09-11 实测），因为写它要专门起一个动作；progress-recorder 活着是因为主控写死了「检测到决策语言就立即触发」。口径的寄生点是 Sub-Agent 回执里的 **Domain findings** 栏——子 Agent 本来就要写回执，顺手多填一栏。
    - 该栏填不出就写 None，不逼着凑。**寄生只解决「顺手」，不解决「催」**：闸只在回执里**真有**领域发现时提醒主 Agent 判一句要不要收，缺这一栏不点名、不催补报。副产品不该催，催出来的是凑数，凑的没有依据，进库即噪音——那正是本规则自己要防的东西。
    - **线索与口径分两级，别把一级当二级用**：子 Agent 撞出来的是**线索**——现象真、解释未必真，它手上只有实测那一类依据。线索进不了库，要 AI 去外网、人去公司内部各自查证，凑齐依据才定论入库。所以那一栏的门槛是「报你手上的证据」，不是「报一条已经成立的口径」；定论归主 Agent 和用户，不归子 Agent。
    - **这条通道会收到三类东西，收到即分去向，别一股脑进库**：
    - **领域口径**（这个域里事情怎么算，依据齐了）→ 派 domain-recorder 收进 `domain/`。
    - **框架实践问题**（我们自己的工具、验证手段、流程的缺陷，与业务无关）→ 走 feedback，或当场改掉那处实践；**不进 `domain/`**——混进去，口径库就成了什么都装的杂物间。
    - 两个出口的判据：**这次就能修好的当场改，需要以后记得的走 feedback**；两者不互斥——当场改掉了、但这个坑以后还会踩的（某个验证手段在某类对象上失效），改完仍要记一条，否则下次换个人再撞一遍。
    - **需求存疑**（代码对得上 Spec、Spec 对不上业务）→ 回流 product-spec-builder。这条路已有，不重复造。
    - 判去向不靠感觉：问「换一个八竿子打不着的项目，这条还成立吗」——成立且与业务无关的是框架问题，成立且描述某个域的是口径，不成立的是这个项目的需求问题。
    - **检索用结构化不用向量**：按域、按被引用的技术对象（`pon_links` / `box_chain_summary`）、按状态（现行 / 被取代 / 污染中）三个维度检索。向量会把「关联键用 IP」和「IP 白名单」这种字面像、语义无关的拉到一起，那恰好是幻觉的来源。

[四个读取时机（任务级不是 session 级）]
    - 四个时刻的共同点：**任务范围已知，能精确匹配**——这是口径能按需注入、不必全量注入的前提。
    - **派单时（最主要）**：主 Agent 写派单包，Business Context 那栏本就要从 Spec 抄规则与例外，与本 Task 相关的口径跟着一起抄进去；fresh 实例不该猜的东西里也包括「这个字段怎么算」。
    - **审查时**：reviewer 对照 Spec 审代码，口径是判据的另一半——Spec 说这个字段要出现，口径说它该按什么算，只拿一半判据审出来的是形不是实。
    - **需求迭代时**：改 Spec 前先看现行口径，不看就会写出与口径矛盾的需求，矛盾要么拖到开发时才炸、要么被实现者按自己的理解抹平。
    - **调试定预期时**：口径是「期望行为」的来源之一，与 Spec 条目、派单包 Business Context、用户原话并列——不知道怎么算，就判不了眼前这个数对不对。
    - **不挂 `recap`、不挂 SessionStart、不挂每次对话开头**：口径是任务级不是 session 级。`recap` 读 progress.md + Product-Spec.md + Product-Spec-CHANGELOG.md，回答「我们做到哪了」；口径回答「这个域里事情怎么算」，两件事。当前任务用不到的口径占绝大多数，全量注入是拿上下文预算换噪音——下游项目那三份已经合计四千余行（993 / 605 / 2526），再挤进开工只会让本来就重的开工更重。

[暂不做]
    - **索引不是检索优化，是上面那条读取时机得以成立的前提**——没有索引，派单时就没法按本 Task 精确匹配，只能把库整个塞进去，而整个塞就只能塞在 session 级，正好掉进那条禁令。结论仍是缓做：库现在是空的，二十条以内全读也就两百行，塞进派单包不成问题，过百条再上索引；机器闸（`domain-lint` 之类）跟着索引走，库里没条目，闸没有可校验的对象。
    - 不做定期复查，理由见上。
    - 不做知识图谱、向量库、从 CHANGELOG 自动抽取——拆 8 条混合条目是纯人工判断，机器抽只会把范围限制和事实记录一起收进来。
