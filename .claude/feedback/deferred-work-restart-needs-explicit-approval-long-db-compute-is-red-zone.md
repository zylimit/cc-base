# 押后事项非点名批准不得重启；长耗时计算先报耗时拿批准；数据呈现≠数据重算

**问题描述**：实战项目中，用户此前已明确押后一项长耗时的全量固化重算（原话「先把数据问题一个个搞完再说」，已记 progress Decisions）。之后用户给了一句业务上相邻但含糊的新指令，主 Agent 把它自作主张解读为解除押后，直接在生产库启动预计数十分钟到小时级的图递归重算。跑到约 70 分钟时被用户质问「你在做什么」「我什么时候下过这个任务」「我完全看不到价值」「谁要你算了」，需求当场删除、明令不准再做。用户真实意图只是看一眼质量面板上还剩多少条待清理数据（数据呈现），该数字在前一批分析里现成，零计算即可回答。且这是前一天同类错误（长耗时计算磨一个多小时无果被取消）的重蹈——用户是拿真金白银时间在现场核查的人，几十分钟的黑盒等待 + 看不到价值的计算直接摧毁信任，生产库长查询还有资源风险。

**触发场景**：主 Agent 收到一句可能触及押后事项的含糊指令，在指令解读与任务启动环节两处失守：① 把新指令凭推理引申为解除押后，没问就开工；② 未报预计耗时、未拿到对该具体动作的批准，就启动长耗时生产库计算，让用户对着黑盒干等 70 分钟。

**教训/建议**：
1. **押后事项非点名批准不得重启**：用户明确押后/否决过的动作，重新启动的唯一途径是用户明确点名批准。一句有歧义的新指令若可能触及押后事项，必须先停下问清——宁可多问一句，不准凭推理开工；收到含糊指令先复述自己的理解，用户确认后再动手。
2. **长耗时计算是红区操作**：任何预计超过几分钟的长耗时计算（生产库递归/全表扫描/批处理重算/空间连接等），启动前必须报预计耗时 + 拿到用户对「这个具体动作」的明确批准，缺一不可。这是 foundation-first 里「重计算规格签字前须成本预估」往日常临时任务的延伸——不止规格签字，临场启动同样要过这道闸。
3. **数据呈现 ≠ 数据重算**：用户要「看数」时，优先用现成数据/轻量查询回答，绝不用重算替代呈现。本例答案在前一批分析里现成，零计算即可给出。
4. **开工前自检三问**：这事用户批过吗？押后过吗？能用现成数据回答吗？——任何一问答不上，先问再动。
