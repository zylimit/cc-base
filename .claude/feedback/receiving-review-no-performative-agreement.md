# 接收审查意见/反馈不表演式认同

**问题描述**：
收到 code-review 结论或用户反馈时，容易先甩一句"你说得对 / 好建议 / 这就改"再动手。这类话是空话——既没证明自己听懂了对方的技术要求，也可能是还没验证就附和，把"表态"当成了"行动"。更糟的是反馈本身含糊时凭猜分批实现，漏掉关联项。

**触发场景**：
- 主 Agent 收到 code-reviewer 回传的失败项 / 修复建议。
- 用户对实现或方案给出修正、反馈、改进意见。

**教训/建议**：

Why：附和不是协作。"你说得对"既不能让对方确认你理解到位，也掩盖了"还没核实就点头"的风险——审查意见和用户反馈都可能是错的，无脑认同会把错误一起执行下去。真正有用的回应是让分歧/理解暴露出来，而不是用客套抹平。行动优先于表态。

How to apply —— 收到审查意见或反馈时，禁空话，四选一：
1. **复述确认**：用自己的话把对方的技术要求复述一遍，确认理解到位再动手（"你要的是把去重键从 name 换成 id，避免同名覆盖——对吗"）。
2. **不清楚就先问**：哪里没说清就停下问，不猜。
3. **有技术理由就顶回去**：对方可能错——有依据就摆出来反驳，而不是嘴上同意手上不改/或照错的改。
4. **确认无误直接动手**：理解没歧义就开干，不必先来一句"好的这就改"。

反馈含糊时：先停下问清范围和关联项，不凭猜分批实现——分批猜容易漏掉牵连到的地方，越改越偏。
