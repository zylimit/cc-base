# 元测试不进发版链，脚手架保持轻量

**问题描述**：v3 改造五期收官、发 v2.0.0 前，主 Agent 把 `golden --mutate`（突变测试：往引擎塞 13 个人造 bug，验证 golden 基线能否发现——测的是"检测器"本身，不是业务代码）排进发版链。该步骤单独要跑 65 分钟，加上前面全量 run-all 15 分钟，用户两次追问"这个全量测试也太久了吧，测试什么东西啊"后直接叫停，明确要求整条删除（"去掉，没意义的东西""删掉"）；随后升级为通用原则："一切与代码无关的，都是垃圾啊，脚手架不要过于复杂"。此前 2026-09-05 用户已提过"不是乱累积代码，要避免过度复杂化，做到轻便而全面"——本次是同一诉求的第二次、更强硬的重申。

**触发场景**：
- 给发版链 / 质量门增加任何一层"验证验证者"的机制（元测试、测尺子的尺子、多层账本、给闸生成闸）时。
- 长耗时步骤（本例 65 分钟）产出的不是直接的代码正确性证据，而是"证明检测机制本身可靠"这类间接产出。

**教训/建议**：
1. **加"验证验证者"的机制前先问它省了谁的什么时间**：答不出具体受益人和具体节省，就不加。突变测试本意是防 golden 基线漏检，但排进每次发版链等于每次发版都为"验证测试基建"埋单，成本转嫁给了不该承担它的环节。
2. **发版链只放直接证明代码正确的检查**：单测 / 回归 / golden 基线比对 / 静态审计这类直接判代码对不对的机制留在链上；元测试（测试基建自身的有效性验证）挪出发版链，改成基建变更时才手动跑或低频定期跑，不跟着每次发版走。
3. **现有机制定期按两条标准清理**：「与代码是否直接相关」+「实际拦过什么」（后者是 gates-need-empirical-validation.md 的口径，本条补前者——即便某机制历史上拦过东西，只要它验的是机制本身而非代码，也不该常驻在高频路径上）。宁可删错了再加回，不为"看着全面"养摆设。
4. **用户对耗时极敏感，长任务开跑前先报预计时长和证明什么**：本例已是第三次同类爆发（另两次分别因 60 轮来回、6 轮返工触发用户不满）。长耗时步骤开跑前应一句话说明"预计多久、证明的是什么"，让用户能提前判断值不值得等，而不是跑到一半才被追问叫停。

进化信号（给 evolution-engine）：与 gates-need-empirical-validation.md 互补——后者管"闸有没有拦住东西"，本条管"闸验的是不是代码本身"；两条标准都不满足的机制优先砍。可考虑在 release-gate / harness 装配清单里给"元测试"类步骤加标记位，装配时默认排除出发版链，需要显式 opt-in 才跟发版跑。
