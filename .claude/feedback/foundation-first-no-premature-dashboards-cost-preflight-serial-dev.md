# 地基未稳不助推看盘类锦上添花；重计算规格签字前须真库成本预估；功能默认串行收口

**问题描述**：实战项目中，主 Agent 在「数据未搞准、基本功能未打磨稳」的阶段，陪同用户把多个看盘/报表类需求（融合视图、过程质量大盘、大数字指标卡、对账指标卡）规格化定稿签字，且已开发完毕，其中数项属主 Agent 主动设计/助推。一个重计算特性在真库量级（几十万面 × 百万点）上单条 SQL 磨 1.5 小时无果被取消，成为直接导火索，用户凌晨战略收拢，连续拍板：「所有统计报告不搞」「基本功能问题还很多、易用性不好」「不搞看盘了，等数据准了按需求直接导出 Excel」「基本功能都没好，坚决不搞看板」「功能不能混在一起开发，要一个个开发」。结果：当天陪同定稿签字的四个功能全部冻结或撤销。

**触发场景**：需求拷问、规格定稿与排期环节，三处行为被修正：① 对锦上添花类需求没有先问「基本功能好用吗、数据准了吗」，反而帮用户把它规格化得很漂亮然后排期；② 重计算特性的性能目标拍脑袋写进规格，签字前未做真库量级成本预估/抽样实测——连接耗时是可以事先估出来的；③ 排期把多个功能混批开发，未默认串行。

**教训/建议**：
1. 需求拷问清单加一问：「这是地基还是锦上添花？」——数据未准、基本功能未稳时，看盘/大盘/统计报告/指标卡类锦上添花默认泼冷水降级挂账，不规格化、不排期。提前做出来的看盘展示的是错误数据，还挤占基本功能的打磨带宽；用户热情提需求时主 Agent 的职责是拷问，不是助推；
2. 含重计算特性（空间连接、全量聚合等）的规格签字前，必须附真库量级成本预估或抽样实测（连接量级估算、EXPLAIN / 采样计时），性能目标不许拍脑袋写进规格再指望开发兜底——这是「性能根因先实测」铁律往规格定稿阶段的前移；
3. DEV-PLAN 排期默认一次一个功能串行收口，只有用户明确要并行才并行；混批开发问题多、收不了口；
4. 产品当前阶段的价值锚 =「数据准 + 基本功能稳」，看盘是数据准之后的衍生品——需求价值判断一律以此锚定。
