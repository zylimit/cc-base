# 用户原话是硬约束时，推荐项不得软化

**问题描述**：「前置未完成时改状态」我出了两个选项：2A 弹窗确认后可强行保存（标推荐）、B 直接拒绝。用户选了 2A，v0.5.0 上线后用户说「前置未完成，不能强行开始，这块能否有个动画箭筒指引」，等于推翻 2A，改为硬拦。回头看，用户最初的原话是「必须前面节点完成，进行本节点」，字面就是硬依赖；我把软拦当默认推荐，偏离了原话字面，用户当时选 2A 多半是顺着推荐走，落地后才发现不对，代价是一次已上线版本的返工（v0.5.0 → Spec v1.7）。

**触发场景**：product-spec-builder 迭代模式，需求里有「前置节点未完成时能否改状态」的分支取舍；选项里 AI 自己加了一个「弹窗确认可强行保存」的折中。

**教训/建议**：
- 用户原话已表明硬约束（必须 / 不能 / 只有……才）时，推荐项贴原话字面（这里是硬拦）。
- 软化方案放第二选项，并写明代价（绕过了用户原话的约束，可能与用户本意相反）。
- 想加折中方案之前先问自己：这个折中是用户说过的，还是我替用户让步的？后者要单列为「我的推断」，不能包装成推荐。
- 与 option-side-effect-and-unclear-restate.md 同源（选项里夹带自己的推断），本条侧重「推荐方向偏离原话字面」。

**适用范围与例外**：见 frontmatter。仅在给用户出选项并标推荐时适用；用户原话含糊时先问清硬软，不要自行取软。

**本次落地**：业务规则已改——Product-Spec.md v1.7，REQ-BRD-009（弹窗确认可强行保存）改为 REQ-BRD-011（硬拦 + 看板动画箭头指向前置格子）。工作方法侧尚未落到 skill / rule；落点建议见返回摘要。

**备注（非纠正）**：用户随后补充「整体风格不能太AI感觉，要比较科技感强，新潮」，属视觉方向需求，应进 Design-Brief / DESIGN.md 或 Spec，不在本条记录范围。
