# 用户说的「SaaS」是生产者角色，看板是消费者应用；拆不拆项目先摆代价

**问题描述**：用户先说「我这个就想当做了一个 SaaS 服务器」，主 Agent 把它理解成要在 Lutetia 仓里做多租户商业产品，用两道选择题把范围收回到「先单租户」；之后用户说「SaaS 可以，我们要开始做看板了，单独启动一个项目，在 Code 目录下」，主 Agent 又理解成要单开一个 SaaS 看板项目，直接去查兄弟仓的脚手架安装方式。用户纠正原话：「那你理解错了，你要的看板是应用，独立的消费者，你现在看法的 SaaS 是个生产者」。随后用户补了一句「或者你觉得没有必要单独启动一个项目，你可以直接完善现在的看板」，主 Agent 这才给出拆与不拆的代价对比，建议暂不拆、直接完善现有看板，用户同意并勾选了四项增强（设备详情页 + 历史曲线、异常总览、GPS 地图、局部刷新 + 手机适配）。

**触发场景**：产品已上线、用户在谈下一步方向时，用了「SaaS」「看板」「应用」这类既可指角色又可指商业形态的词；主 Agent 没问清就按自己的理解推进，连续两次理解偏差。

**教训/建议**：
1. 「SaaS」「平台」「服务器」在这位用户口中是**角色**词：谁出数据、谁提供 API 就是生产者 / 服务端；「应用」「看板」是**消费者**。听到这类词先用一句话复述角色关系（谁生产、谁消费、经哪条接口）让用户确认，再谈范围，不要直接跳到多租户、计费这些商业形态。
2. 「单独启动一个项目」是结构性决定：先摆出拆与不拆各自的代价（仓库、构建、部署、鉴权各一套 vs 复用现有数据与权限）和该拆的触发条件（多客户、前端团队、重交互、第二个消费者），让用户选；不要一听到就去查脚手架怎么装。
3. 连续两次被纠正同一类理解时，停下把自己的理解写成一句「我现在的理解是 X，对吗」再动，比继续推进便宜。

**适用范围与例外**：适用于需求迭代和方向讨论阶段，以及任何提议新建仓库、拆模块、换架构的时刻；用户已经明确说到租户、计费、多客户时按多租户理解，用户直接点名「新建仓库」时照做不反问。
