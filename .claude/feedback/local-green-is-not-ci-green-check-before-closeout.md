# 本地全量回归绿不等于 CI 绿，收官前须独读 CI 真实输出

**问题描述**：
cc-base v2 的 P5/P6 收官阶段十余批改动，每批都亲跑 `bash .claude/tests/cases/run-all.sh` 得到 RC=0，据此在 progress.md 逐批记「全量回归全绿」。收官查 `gh run list` 才发现 GitHub Actions CI 自约一个月前的 commit 起持续 failure，四格三红，整轮工作没有一次去读过 CI 输出。根因不是"忘了看"，而是本地 run-all 与 CI 跑的不是同一件事——CI 额外跑 harness 审计脚本、`golden --check --strict`，还在 windows-latest 真机上跑 selftest；本地 run-all 不含审计步骤，Windows 侧本机无 pwsh 全程 SKIP。"本地全绿"这个事实成立，却被当成了"CI 也会绿"的证据，两个不同范围的验证结论被当一件事使用。

两条红都是真信号：一条是证据层那批写文档引入的 `gate-disable-instruction` 误报；另一条是 Windows 侧 selftest 因路径分隔符断言用了正斜杠而失败——是本仓 Windows 侧一个多月来第一个实质缺陷信号，而 progress.md 一直记着"Windows 侧全程未验、CI 是唯一能真验的地方"。修完两条后，主 Agent 写下可证伪预测（"ubuntu 因 commit X 转绿、windows 因 commit Y 转绿"）并 push，结果 CI 仍全红——原本两条确实修好了，但暴露出两个新问题（`os.devNull` 在 Git for Windows 下用法错误；白名单条目的行号绑定被后续两批改动同一文件推移，豁免失效）。行号漂移那条本可避免：`init` 那批曾专门查过这个时序风险，但之后 `cochange`、`release` 两批又改了同一文件，没有再查第二次。

**触发场景**：
- 收官 / 发版 / 任何要报"全量回归全绿"结论之前，本地测试命令跑绿之后。
- 跨平台或跨环境（CI 专属的 runner、无法本地复现的操作系统）缺陷的修复收尾，本地无法直接复现验证时。
- 机制里存在「文件 + 行号」绑定的豁免/白名单条目，其宿主文件被后续批次改动之后。

**教训/建议**：

Why：本地全量回归和 CI 是覆盖范围不同的两套验证，前者绿只能证明"本地这套命令集合过了"，不能反推"CI 那套更大的命令集合也会过"——本例里 CI 多跑审计脚本 + `golden --check --strict` + windows-latest 真机 selftest，本地这三样都不在内。闸响了、通知也确实送达了——GitHub CI 失败会发邮件，用户一个月来一直收着这些失败通知。缺失的不是通知渠道，是负责验收的一侧（主 Agent）从不去读 `gh run list`，把"本地 run-all RC=0"当成了完整的验收证据；更严重的是，**用户收着红色失败邮件的同一段时间里，主 Agent 在 progress.md 里逐批记「全量回归全绿」**——两个相反的信号并存了一个月，而报"全绿"的恰恰是负责验收的那一侧。这不是"没人知道"的信息缺失问题（加个通知渠道就能解决），是"知道的人和做验收报告的人不是同一个"的验收失效问题——通知本来就到位了，加再多通知也没用，问题出在验收动作本身没有去接这个早就存在的信号。把这类情况误诊成"闸建了没人读=闸在响没人听"会导向错误的解法（去加通知渠道），真正要改的是验收动作本身。跨环境修复同理：改动内容与报错字符串对得上，是推断不是观测，五步闸（completion-claims-need-fresh-verification-five-step-gate.md）早说过"没跑过就下结论不算数"，跨平台场景下"跑过"必须是真实环境跑过，不是本机跑了别的东西。

How to apply：
1. **收官 / 发版前 `gh run list` 是必跑的一步，与本地测试并列，不是可选补充**：本地全量回归绿 + `gh run list` 读到最新一次真实 CI 结果，两者都满足才能报"全绿"；只跑了前者不能替代后者。理由不是"怕没人知道"——本例里用户一直收着 CI 失败邮件——而是"用户已经知道了，而我不知道"：一个连用户都看得见的红，验收方却看不见，这份验收就不成立。发现本地/CI 覆盖范围不一致（跑的脚本、目标平台不同）时，覆盖范围以 CI 为准，本地绿只是必要不充分条件。
2. **人收到通知不等于验收方读到了信号，两者要对齐到同一个动作**：本例中 CI 失败邮件确实送达了用户，但出具"全绿"结论的是主 Agent，主 Agent 没读过 CI 输出——通知到人和验收到位是两件事，不能因为反正有人会收到通知，就默认验收方也已经知情。新增或依赖某道 CI/审计闸时，要明确"谁出具验收结论"就必须是"谁去读这道闸的输出"的那个角色，不能靠别人碰巧收到通知来补位。
3. **跨环境修复只记「已修未验」，不记「已修复」**：本机无法复现的缺陷（如本例 Windows 路径分隔符），改完代码后如实记录为"已提交修复，等待真实环境（CI）判决"，等 CI 转绿再改口"已验证修复"；期间不得用"改动内容与报错字符串相符"当作已验证的替代证据。
4. **行号绑定的豁免机制每次改动宿主文件都要重查，查过一次不代表永久有效**：如 instructions-allowlist 这类靠「文件+行号」定位的豁免条目，后续任何一批改动了同一文件都必须重新核对行号是否漂移，不能因为在更早的批次里查过就默认它仍然成立。
5. **用户对某项结论提出异议或给出反例时，先怀疑自己信息不全，别继续按原有信息作业**：本次用户一句"CI 红色，会给我邮件"，直接推翻了"没人读闸=没人知道"的误诊。这类反例出现时，大概率说明用户手里有主 Agent 没有的实况信号（通知邮件、群里报警、他人反馈等），应当立刻去核实那个信号源，而不是维持原判断继续往下走。

已机械化的部分：本仓新增的 `release` 子命令已把「CI 状态」列为发布就绪装配的七项之一，查不到时报 UNKNOWN 并明说"unknown is not a pass"——但这只覆盖发版场景，日常收官/阶段性小结仍然靠自觉去读 `gh run list`，没有机器闸。

进化信号（给 evolution-engine）：可考虑在 [开发测试规则] 或验收铁律里补一条「本地全量回归绿 ≠ CI 绿，收官/发版前 `gh run list` 是独立核查步骤，且不可用"用户/团队已收到通知"替代主 Agent 自己核查」；也可评估给 Stop 阶段或收官流程加一道轻量提醒（非阻断，因 CI 是异步的，硬阻断不现实），提示"距上次检查 CI 状态已过 N 次 commit，建议读一次"。
