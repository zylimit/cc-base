# Sub-Agent 派单要给最小上下文，不让它自己推导/复核/写长回执

**问题描述**：

主 Agent 派出的 sub-agent 频繁撞 60/100 轮工具调用上限。根因是派单包本身太重：只给模糊目标，让 sub-agent 自己读几百行底本文件去推导改法、自己做突变测试/交叉对拍/指纹复核，还要求写长篇回执。一个只涉及 4 行夹具的机械修正，滚到了 60 轮。

用户当场纠正：「60轮，你是怎么想到这么浪费的」「6轮我都嫌多」——连 6 轮都嫌多，60 轮是彻底失控。

**触发场景**：

派发 implementer / code-reviewer / tester 等 Sub-Agent 去做**范围明确、改动量小**的任务时（修一处已知问题、调一个已知参数、补一条已知断言）。派单包六字段齐全不等于内容精简——字段齐全但每个字段都写成"自己去研究"，照样让 fresh 实例从零推导。

**教训/建议**：

1. **派单只给「文件:行 + 改成什么 + 一条验证命令」**，不让 sub-agent 自己去读大段底本、自己推导改法。主 Agent 已经知道改哪、怎么改时，直接把结论写进派单，sub-agent 的工作是执行 + 验证，不是重新调研一遍。
2. **每单设 ≤ 6 次工具调用的预算**，超预算说明派单本身有问题（范围不够收敛/上下文给少了），该主 Agent 收窄范围重派，不是让 sub-agent 继续摸索。
3. **复核只做一次，且由主 Agent 做**，不让 sub-agent 自己突变测试/自己交叉对拍/自己出指纹复核——那是主 Agent 验收职责的一部分，塞给 sub-agent 只会重复消耗轮数还越权。
4. **≤ 5 行的机械改动，主 Agent 直接自己改，不起 sub-agent 实例**——起一个 fresh 实例的固定开销（读上下文、理解任务、写长回执）本身就比改动大，小到这个量级不值得外包。这条与 [总体规则] 的"主 Agent 职责边界"不冲突：那条铁律管编码/审查/部署/测试四个环节要不要外包，不是所有一行改动都要外包。
5. **reviewer 一次只看一个问题**，不要求它一次性把所有维度、所有可能性都过一遍再汇总——拆小了审查范围可控、轮数也可控。
6. 适用范围：所有 implementer / code-reviewer / tester 派单，尤其是范围明确的小修小补。范围本身不明确、需要探索的任务不受此约束，但探索阶段和执行阶段应拆成两次派发，不要混在一单里。
