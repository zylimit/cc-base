# 机房跳纤没数据就断，不用补全型规则猜；解释推导一次一件事

**问题描述**：主 Agent 向用户解释引擎的一条规则：ODF 上一个口都没跳纤、勘测表也没录的「空框」，夹在两条缆之间时归前一条缆；样板站点有一条缆的 96 芯就是靠这条规则多算一框凑出来的。用户当场否决：「ODF 不存在空框规成一条缆，没有个定义，你的数据太杂了，我不理解你的描述，机房跳纤是最复杂，需要严格验证，没有数据千万不要猜，没有就断」。

同一轮及稍早已有同类否决三次，说明这是一个模式，不是单点：
- 「OSU 按同号口直通」的推定被否决：「OSU 是没有顺序的…我们不要关注 OSU 内部，当成黑盒」。
- 给盒子没接 OLT 的芯补生成成端被否决：「不要帮助他们生成，要反映真实情况，有啥就是啥」。

**触发场景**：逐站核对样板站点「传统段还原」的机房 ODF 成端推导时。引擎为了让芯数、框数对得上，写了「补全型」规则（空框归前缆、同号直通、补生成成端）。

**教训/建议**：
1. 工作方法：机房跳纤是整条链路里最复杂、最需要严格验证的一环。表里没有的数据就让链路在此断开、进问题清单，不用任何补全型规则去凑。给用户提规则时先分清两层：哪一环是表里的事实，哪一环是推出来的；推出来的部分默认不做，除非用户同意。凑得对上数字（如 96 芯）不能当规则成立的证据。
2. 沟通：一次解释塞了太多数字、框号、行号和例外，用户看不懂。讲这类推导要一次一件事，用一个例子讲透，少列表。与用户记忆「对数据一次只过一条」同向，本条补充的是「讲推导」这个场景。

**适用范围与例外**：凡是引擎对机房内链路（ODF、跳纤、OSU、盒子成端）做推断，或给用户讲此类推导，都按这条来。用户明确同意某条推定规则时除外，同意要落进 Decisions。与 presentation-only-actual-data-no-inference.md 同向（只放实际数据不放推断），但那条管展示页，本条管还原引擎的推导规则。
