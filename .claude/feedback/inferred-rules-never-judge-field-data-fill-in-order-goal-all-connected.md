# 自己定的推测规则不拿来判现场错；没有依据按顺序排，有冲突想办法接上，目标全部连上

**问题描述**：传统段还原排芯时，引擎按自己定的「每盒 6 芯、沿缆按盒子先后排」算出每只盒子「应接」哪几芯，再拿现场跳纤去比，比不上就出「插错口了，要改跳纤」。样板站点里，盒子甲的一根跳纤被判成「第 22 口改插到第 20 口」。其实现场这几只盒子的跳纤是一个挨一个顺着插的，只跳过了一个口；是「每盒 6 芯」把第 22 口算给了下一只盒子乙。用户问「依据是什么，22 口是乙，20 口到甲，这是我们自己定的吧」（原话里的口号、盒名已换成合成值），主 Agent 核实后承认那是自己定的规矩。用户随后一路定口径，原话依次是：
- 「我建议不要报跳纤，改规则」
- 「这东西能连上就行，本来也没说正确和错误，那我们只要能圆过去就好」「除非现场看过，不然不可能知道哪里错了」
- 「有问题再说呗，本来就是个推测，顺序排线，也许也是错的」
- 「你现在没有办法知道，那个方案最优，你没有任何参考依据，对不对？你只能凭感觉，按顺序对吧」
- 「我们也可以按顺序，有问题就跳过，就灰度处理嘛」，紧接着改成「优先按照顺序排，有问题解决问题，目标是都能连上」

同一天稍早已有一次同类追问：主 Agent 把推出来的一组芯号当成事实写进问题描述，用户问「这个两个都是有据可查的吗」，主 Agent 这才改口，说那是推出来的。

**触发场景**：传统段还原把勘测跳纤、网管、竣工拼成链，排芯并出问题清单时。为了把每只盒子的芯排满，引擎用了一条推测规则，又把这条推测当成了判对错的标准，结果给现场出了改跳纤的指令。同一天还为「推不出应接」的情形加了「要现场确认」，也是拿推测当标准。两处都是用户追问依据才翻出来的，当时是快速开发模式，改一轮热补一轮。

**教训/建议**：
1. 出「错了、要改」这类结论之前，先问依据是什么：是另一方的事实（网管、竣工、现场记录），还是我们自己推出来的？自己推出来的只能拿来补空，不能拿来判事实错，更不能叫现场改。规则和现场冲突，就改规则去贴现场。
2. 用户问「依据是什么」「有据可查吗」，照实分开说：哪些是几方数据对出来的，哪些是自己定的规矩推出来的。没有依据就直说没有，不拿顺序、惯例去包装成依据。
3. 没有依据时按顺序排。这本身也是推测，也可能错，所以不拿它判别人。碰到冲突不跳过、不挂起，想办法接上，比如往后挪、用剩下的空芯补，目标是全部连上。用户先说过「有问题就跳过，就灰度处理」，紧接着改成「有问题解决问题」：跳过、标灰都不是终态。只有几方事实互相顶、怎么排都接不上的，才列出来。
4. 条目用中性说法，比如「对不上」「接不上」，写清是哪两方对不上。不写「插错了」「搞错了」「要改」，也不说谁错：没人到现场看过，谁也不知道错在哪。

**适用范围与例外**：
- 按这条来：传统段还原的排芯，跳纤清单、问题清单的判定和文案；推而广之，凡是引擎拿自己推出来的结果和事实比、要出判错结论的地方。
- 例外：几方事实彼此真对不上、按顺序也排不通的照列，现象如实报，但不判谁错；用户明确拍板的判定规则按用户的来。
- 和 room-jumper-no-data-then-break-not-guess-and-explain-one-thing-at-a-time.md 的分工：那条管机房内链路的事实，没有数据就断、不补猜。本条放开的只是排芯这一层的按顺序推测：10-20 用户已认可「其余按最优方案补位」，11-04 又定为「优先按照顺序排……目标是都能连上」。用户没说要推广到机房内链路，说明之前，机房内仍按那条办。
- 和 issue-list-goal-is-discovery-not-lower-count-no-self-invented-filter-rules.md 的分工：那条禁止拿自造规则把问题压掉，本条禁止拿自造规则造出问题，同一个根：推出来的东西不当判据。这次去掉「要改跳纤」是用户拍板，属于那条的例外，不是 AI 为了压条数改口径。
