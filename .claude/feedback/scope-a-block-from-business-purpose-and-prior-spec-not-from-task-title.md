# 开工一块业务前，先弄清它干什么用、给谁看、作为什么的依据，不从任务标题倒推范围

**问题描述**：2026-10-10 用户确认过一组口径，主 Agent 把这块记成「光功率坐标证据库 + 导出时修正」，也就是 DEV-PLAN Phase 118 的标题。2026-10-11 用户说「接下来就是光功率了」，主 Agent 沿用这个标题开工：做了离线解析工具（只取盒名、手工坐标、照片上的经纬度与标牌，判坐标可信度四档），启动了全量照片识别（第一遍 22:36 在本机启动，预计约 7 小时），并安排了第二个识别器。表格里的功率值、合格判定没有取；没照片的行只记成「坐标缺失」；没有「漏测」的概念；派单里还写了「照片上光功率计读数不参与判档，不用读」。当晚用户说明：「光功率这个事，其实是个质量保障的过程，施工后的验收，是数据和工程移交给客户前的最后一到关卡，当然光功率测试报告也是客户验收的依据，需要有迹可循，哪些盒子漏测，哪些照片有问题，哪些数据丢失等等，都要非常明确的写出来」，随后补充：「下一步基于这个数据可能要牵引一线去重测，复测等，还有很多事情会做，当前还不涉及」。主 Agent 这才去读三个月前用户确认过的旧规格 `D:\Code\optical-power-toolkit\Product-Spec.md`，那里早就把它定为「光功率测试数据处理与质检工具」。这是主 Agent 把范围理解做窄了，用户没有新增范围；业务口径本身（旧规格的条目、做与不做、待定）记在 progress.md Decisions，本条只记工作方法。

**触发场景**：用户用一句话切换到下一块功能（「接下来就是光功率了」），主 Agent 没有先答「这块在业务里干什么用、给谁看、作为什么的依据」，而是拿上一次留下的任务标题当范围。这个标题是主 Agent 对 10-10 那天口径的概括，用途在概括里丢了。信源其实就在手边：旧规格的路径当天下午主 Agent 就见过（列过 `D:\Code\optical-power-toolkit` 目录），但只拿那里的结果库当识别对照，没有打开规格本身；主仓库自己的 Pinned（2026-07-28）也写着「光功率属于相对独立的 QA 工程」。用户当晚说明的定位，旧规格里早已写明。同一天、同一块功能、同一个开工环节，已有另一类缺口记在 check-existing-boundary-decisions-before-deciding-code-placement.md（相关记录读到了，没拿来约束代码落点）。

代价：按窄口径做出的解析工具要回头补取功率值、合格判定与漏测；派单里「读数不参与判档，不用读」与新定位不符，需要改；在途的识别器实现者要中途通知补字段；第一遍全量识别已在窄口径下启动，没有返工，是因为记录库（schema v2）已存识别原文与文字位置。实际工时主 Agent 未给，不估。

**教训/建议**：

（以下三条为主 Agent 的解读，不是用户原话）
- 开工一块业务前，先答清三问：这件事在业务里是干什么用的、给谁看、作为什么的依据。问不清就查，查不到就问用户；不从上一次会话留下的任务标题（Phase 标题、Decisions 标题）倒推范围。标题是对当时讨论的概括，不是这块的定义。
- 用户以前写过的规格是最直接的信源。路径见到了，就该打开读本体，不能只拿它旁边的结果当对照；「从零开始」指的是代码和结果从零，不是连需求也从零。
- 长耗时、难以重跑的步骤（全量识别）开跑前，把以后可能用到的原始信息尽量一次采全。

（以下为观察员注）
- 写进派单的「不用读 / 不做」是在替用户划排除范围，fresh 实例没有会话历史，只会照办。排除项要有出处（Spec 条款或用户原话）；没有出处的，不写成排除，写进 Escalation 让实现者遇到时回报。
- 第三条这次没有造成返工（识别原文已存），按「没有代价记录的先不成文」处理，记在这里不单独立规；它若再造成返工，自然的落点是 dev-builder SKILL.md [质量门槛] 里「长跑批处理…」那一条。
- 与 check-existing-boundary-decisions-before-deciding-code-placement.md 合看：两条出在同一个环节（开工、写派单之前），缺口不同，那条是边界与归属，这条是业务用途与用户已有规格。所以另记两条、各留各的范围；规则若要改，落在同一处一并评估：rules/subagent-dispatch.md [派单包七字段] 的 Business Context 一栏。该栏已写「为什么做、谁受益」，并要求从 Spec、progress.md 与 domain/ 抄；缺的是来源约束，即用户另处写过的规格算来源，Phase 与 Decisions 的标题不算来源，答不出先问用户。
- 用户没有说明、本条也不替他补：给客户的验收报告版式；「漏测」的全集以什么为准（设计里的 FAT 盒子还是网管里的盒子，Decisions 已列待定）。需要时单独问。

**适用范围与例外**：见 frontmatter。范围是主 Agent 从任务标题或一句话指令接手一块业务功能的那一刻，以及启动长耗时、难以重跑的步骤之前；例外是本仓库 Spec 已写明用途与验收口径、或用户当次已说清的块，以及纯技术小改。不改 skill / rule 本体：用户这次没说「以后都」，按 CLAUDE.md 铁律 8 先不顺手改；等进化引擎扫描时与上面那条一并提给用户确认。

**本次落地**：progress.md Decisions 新增 2026-10-11「光功率服务的定位纠正：它是施工后的验收质检，不只是坐标证据库」（观察员已核对在位），含用户原话、依据（旧规格的口径条目）、做、当前不做（牵引一线重测复测的派工流程；给客户的验收报告版式）、适用范围、取代关系（2026-10-10 以来「坐标证据库 + 导出时修正」的范围表述，即 DEV-PLAN Phase 118 标题；坐标相关各条保留）、待定（漏测的全集以什么为准）。已通知在途 codex 识别器实现者，在全量跑之前给大模型输出加拍摄时间、地址、是否拍到功率计与标牌、照片质量等字段。两遍全量识别照常进行（识别原文与用途无关）；表格一侧的功率值、合格判定、日期靠重读表格补。skill / rule 本体未动。未说明是否已改（按 pending 看）：DEV-PLAN.md Phase 118 标题本体；已做出的离线解析工具的取数范围；派单里「读数不参与判档，不用读」那一句。
