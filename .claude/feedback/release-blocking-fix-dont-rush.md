# 发版阻断修复不要急：问时间不是让你抢跑

**问题描述**：
- 2026-11-03，用户敲 /release-builder，被发版闸以待审清单未清拦下。主 Agent 派三位审查员和一位独立测试员，补审补测 REQ-AUD-002 第 2-4 步，查出 3 条 HIGH：
  - 撤回「去除确认」或重做时，盖掉之后的抽屉手改；
  - 撤回删除时，造出同键重复行；
  - POI 撤回时，改到同组别的 POI。
- 用户问「还有多久」。主 Agent 报了时间，并主动说明两处压缩：「后端修完只跑相关的测试，全量测试只在最后由我跑一次」「这次的修复不单独部署到 8765，跟发版一起上线」。
- 用户再问「还要这么久吗」。主 Agent 回「可以快一些。我不再等测试员补完剩下的失败测试，现在就派后端开修，能提前大约 20 分钟」，接着做了三件事：
  - 亲跑当时已有的 5 条红测，见红后 touch .claude/.red-verified；
  - 派后端 implementer，与测试员补红测并行；
  - 让测试员事后在修复前的冻结代码上证明新补的用例是红的。
- 之后用户又敲了一次 /release-builder，被拦，这次待审清单是 8 个文件。主 Agent 正要在冻结代码上亲跑 12 条红测，用户打断了这次工具调用，说：「修，不要急，修好再说」「快不得」。

**触发场景**：
- 发版前补审补测与修复正在进行，见 progress.md In Progress #24。用户在等发版，连续问时间，中途还问「感觉发版本越来越慢了，难倒要拆服务了？」。
- 主 Agent 把「还要这么久吗」当成了加速信号，动了两处：红锁的节奏（红测没齐就先派修），以及修复的上线方式。

**教训/建议**：
- **问时间先当成问进度**。用户问「还要多久」「还要这么久吗」时：
  - 如实报时间、卡在哪、哪几块不能省；
  - 不主动调换步骤顺序，也不省步骤去换那几分钟。
  - 用户原话是「修，不要急，修好再说」「快不得」。「问时间不等于授权抢跑」是主 Agent 从事情先后顺序得出的理解，用户没有逐字这么说。
- **发版阻断修复按完整闭环走，一步不压**：
  1. 红锁出红，红测要齐，主 Agent 亲见全部失败；
  2. implementer 修；
  3. 原审查员复核；
  4. 在干净导出目录跑全量；
  5. 待审清单清零；
  6. 然后才请用户敲 /release-builder。

  红测没齐不先派修；「修复随发版上线」也不拿来当省时手段。
- **这条已经部分成文，这次是没守住**。.claude/rules/subagent-dispatch.md [隔离原则] 写着：「用户说'加速 / 快点'≠ 授权并行铺开——正解是砍范围、串行提效、减少返工」。这次用户连「加速」都没说，只是问时间，主 Agent 就并行开跑了。
- **用户嫌慢时能给什么（建议）**：
  - 说清哪几块是机器时间：全量测试 12 分钟、ai-ts 演练、打包；
  - 说清哪几块不能省、为什么；
  - 说清事后怎么提速，例如测试并行跑；
  - 要不要砍范围，由用户定。

**适用范围与例外**：
- 按这条来：
  - 发版被闸拦下后的补审补测与修复，尤其阻断发版的数据安全类 HIGH；
  - 此后同类发版阻断修复；
  - 这期间用户问时间、催进度时。
- 不按这条：
  - 日常开发与 fast 档。用户 2026-11-02 说过「不改，快速模式就是尽可能不测试，不检视」，此前也多次要过「快速开发模式」「加速」，见 fast-mode-skips-review-and-tests.md。
  - 用户当轮明确说某一步可以省或可以并行时，按铁律 7。
- 未说明：用户在发版以外的场景明说「加速」时该砍什么，这次没涉及。
