# 测试代码规模按风险分层，卡在有效代码三分之一到二分之一区间

**问题描述**：
当天为两支新脚本（predev-lint.mjs 548 行、ui-audit.mjs 426 行）配套写测试：test-predev-lint.sh 842 行、test-ui-audit.sh 553 行，另在 selftest 新增 316 行 lane。测试代码合计 1711 行，对应有效代码合计 974 行，比例 1.76——测试量反超被测代码近八成。此前同一批改造已因「避免过度设计、过度防御」被纠正一次（review-loop-converge-on-core-behavior-avoid-over-defense.md，管的是审查/红锁循环该在哪收敛），这次用户在测试量本身上再纠正：先说「测试代码要严格降低，只能是有效代码的 1/3，超了改」「本末倒置」；同一轮内用户又把口径精确化——不是「不超过 1/3」的单侧硬顶，而是「不低于 1/3、不高于 1/2，按风险分配，不做全量覆盖」的区间约束。两次表述不矛盾：第一次是对着眼前 1.76 倍超标的当头棒喝，第二次是把这个当头棒喝落成可长期使用的一般规则，补上了"低了怎么办"和"不同模块风险不同、预算不该一刀切"这两块。

**触发场景**：
- 给新脚本/新闸配套写测试或自测 lane 时，测试文件行数逐条累加，没有对照被测代码行数设区间，写多少算多少。
- 不同风险等级的模块（密钥/危险命令闸 vs 提醒类工具脚本）套用同一测试密度，要么高风险模块测得不够，要么工具脚本类测得过度。
- 追求"能想到的输入分支都补一条用例"，用例数随写测者的想象力线性增长，不随模块的实际风险收敛，也不检查是否已经滑出区间。

**教训/建议**：

Why：测试预算不是越多越安全，也不是越少越轻量——它该配得上模块出错的代价。密钥/危险命令类闸出错会泄密毁数据，预算可以给到上限；一个提醒类 hook 或工具脚本出错顶多是体验问题，一两条用例足够，撑到区间下限反而是浪费。本次 1.76 倍超标的问题不在"测试多"本身，而在 predev-lint.mjs / ui-audit.mjs 这类工具脚本被套用了远超其风险等级该有的测试密度。

How to apply：
1. **整体区间：测试占有效代码的 1/3–1/2（按行数）**。hooks / harness / scripts / githooks / 安装器算有效代码，tests/ 与 selftest lane 算测试；低于 1/3 要补关键契约用例，高于 1/2 要删。
2. **预算按风险分层，不是所有模块一个密度**：
   - 高风险（坏了泄密/毁数据/装坏别人项目：密钥与危险命令闸、安装器与 manifest、发布装配）→ 预算可到上限二分之一；
   - 引擎子命令 → 只守退出码契约 + 一条真实场景；
   - 提醒类 hook、档位、工具脚本（本例的 predev-lint.mjs / ui-audit.mjs 属此类）→ 各留一两条即可，不必撑到区间下限。
3. **不做全量覆盖**：参数花样、边角组合、变异体不必逐一进仓测试，尤其工具脚本类——覆盖这些只是把假想输入的组合数误当成测试价值。
4. **写测试前先按模块风险定预算档位，再动笔**，不是先写后核对比例；一次给多个新脚本配测试时逐个定档、逐个核对，不等全部写完合并才发现整体失衡。
