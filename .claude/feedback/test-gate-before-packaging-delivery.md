# 测试卡点：测试通过是打包/交付前的强制前置闸门，部署 ≠ 可跳过测试

**问题描述**：
某次内网部署的多 Sub-Agent 协作流程：主 Agent 派 deployer Sub-Agent 打 arm64 离线包 + 写部署脚本，主 Agent 独立复核脚本，产出跳板机一条龙部署提示词。全程跑了**大量"验证"**（docker ps、curl /health、tar 架构校验、bash -n、下载链可达、network-alias 解析），但**一个项目测试都没跑**。

具体后果：
- v1.0.4 核心改动 #47「圆形框选导出 ST_Contains」**没有任何回归测试，也没做手动功能验证**，就被打包、上架 CF、生成内网部署提示词，一路放行。
- 现有唯一的 pytest（`api/tests/test_np_ring_46.py`，#46 NP范围圈）这次**从未运行**。
- 项目 CLAUDE.md 明确规定四步走验证第2步「测试完整性」是"真卡点"，但在"打包→交付→部署"链路里，测试既没被执行、也不是一个 gating（过不去不许往下走）的步骤。

**触发场景**：
主 Agent 收到"部署/打包/交付"类指令时，默认把流程理解成"构建 + 部署验证"，把"测试完整性"当成开发阶段的事而跳过；部署链路里缺一个强制的"测试通过才允许打包交付"的闸门。尤其带后端逻辑变更（导出/空间查询）的版本，新功能没补测试就被放行。

**用户原话**："测试没有放到关键步骤啊"

**教训/建议**：

Why：构建验证（docker ps / health / 架构校验 / bash -n）只证明"包能起来、脚本语法没错"，**不证明功能行为正确**。带后端逻辑变更的版本（改了导出/空间查询/契约）若不跑回归或手动功能验证就打包上架，等于把未验证的行为直接推到内网交付——一旦逻辑有 bug，部署越顺、回滚越贵。"部署"指令的语境不能成为绕过测试卡点的借口；测试是交付的 Definition of Done 的一部分，不是开发阶段的可选项。

How to apply —— 把"测试通过"做成打包/交付前的**强制前置闸门**：
1. **打包前先过测试卡点**：主 Agent 在派 deployer 打包**之前**，必须先确认"相关功能回归测试已运行且通过"的证据（运行器真实输出），否则不允许进入打包→交付。
2. **带后端逻辑变更的版本必补验证**：若本次版本改了后端逻辑（导出 / 空间查询 / 契约 / 解析，如 #46 #47），新功能**必须补回归测试**，或至少有**手动功能验证证据**，才算满足四步走第2步。无证据不放行。
3. **至少重跑已有测试**：哪怕没新增测试，打包前也要把现有 pytest（如 `api/tests/test_np_ring_46.py`）跑一遍，附通过输出。不能让已有测试在交付链路里"从未运行"。
4. **"部署"不等于跳过测试**：部署/打包/交付类指令进入时，主 Agent 先核对测试卡点状态；卡点未过 → 先派 tester 补测试（务实回归）→ 通过后再派 deployer 打包。

判定规则：测试卡点未过 = 不许进入打包→交付，无论指令是不是"部署"。

进化信号（给 evolution-engine）：release-builder / 部署链路应在「打包/交付」前**显式插入测试 gating 步骤**——固化为「打包前必须有相关功能回归测试已运行且通过的证据（含重跑已有 pytest）；带后端逻辑变更的版本新功能必须补回归测试或手动功能验证证据；测试卡点未过不许打包交付；'部署'指令不豁免测试」。可与四步走第2步「测试完整性」打通，让 release-builder 复用 test-builder 作为前置闸门，而非把测试当开发阶段专属。
