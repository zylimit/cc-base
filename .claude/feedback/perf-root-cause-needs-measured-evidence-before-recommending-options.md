# 性能根因先实测再给方案，代码推测不配作为推荐依据

**问题描述**：生产库一条递归 CTE 查询跑了 1 小时不结束。主 Agent 基于代码结构推测瓶颈是 ANY(path) 数组扫描，未做任何实测就直接向用户推荐「杀掉查询、改造递归 CTE」方案。用户反问"你确定，你考虑清楚方案了"，才承认推荐只是猜测，随后补跑 500-ONU 采样 EXPLAIN ANALYZE + 拓扑统计——结果推翻原猜测：递归 CTE 只占分钟级，真凶是 chains CTE 的 lateral 重复扫描（olt_ip_map 视图无索引匹配 + blank lateral 全扫 edges）和 work_mem=4MB 磁盘溢出。按原方案改造递归 CTE 会白干一场且真瓶颈原样留着。

**触发场景**：生产环境慢查询诊断。压力（查询挂着不结束、用户在等）诱导跳过实测直接给"看起来合理"的方案；被质疑后才补证据，属流程倒置——给用户的选项列表本身就应该建立在证据上，而不是先给选项、被质疑再补证据。

**教训/建议**：
1. 性能类根因判断（慢查询、内存、CPU、IO）给出任何方案选项前，必须先拿到实测证据：EXPLAIN ANALYZE / 采样运行 / profiler 输出 / 资源统计，至少一样在手；
2. "从代码读出来的合理推测"只能作为待验证假设列出，措辞上明确标注"未实测、待验证"，不允许包装成方案推荐；
3. 全量太慢就采样实测（本例 500-ONU 采样几分钟出结果），"实测太贵"不是跳过的理由；
4. 这是 CLAUDE.md「查证后再结论」铁律在性能诊断场景的具体化：证据到手再给选项，用户质疑不该是补证据的触发器。
