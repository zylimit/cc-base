# 新增对接方式默认与旧方式并存，不贴"过渡"标签

**问题描述**：用户提出把本服务做成能被主系统 DigiFiber-conflation 调用的服务，原话「暴露接口……或者直接让他去读数据库也行」。主 Agent 在规格 v0.5 里把现有的「文件方式」（出数据包文件由主系统上传、应测清单用 CSV 放进来）写成「主系统改造完之前的过渡办法」，把接口当成最终形态。这是主 Agent 的推断，用户没说过。用户看复述后纠正，原话：「不对，之前的文件模式也要保留，对接也要留接口」。

**触发场景**：product-spec-builder 迭代模式的需求分析与复述阶段。用户说"加一种新方式"，主 Agent 默认新取代旧，并给旧方式贴了「过渡」标签。复述阶段被用户当场纠正，未进入开发。严重程度：中。

**教训/建议**（以下为主 Agent 的解读，非用户原话）：
1. 用户的话里有「或者……也行」，表达的是多种方式都可以，不是二选一。遇到「新增对接方式 / 新增出口」类需求，默认新旧并存，除非用户明说取代。
2. 凡是给现有做法贴「过渡」「临时」「以后去掉」这类标签，都属于会改变范围的推断：必须标 `[推断]`，并在复述里单独点出来让用户否决，不得直接写进 Spec 当事实。
3. 并存意味着两条路要有一致性约束（本次已加规则「两条路内容一致」），写规格时顺手补上。

**适用范围与例外**：需求迭代模式里凡涉及现有能力去留的措辞都按此办；用户明说取代时不适用。

**本次落地**：当前产物已改——Product-Spec.md 升 v0.6（SCOPE-15、REQ-PUB-002、新增 REQ-PUB-003、FLOW-4 第 2、3 步、规则表新增「两条路内容一致」、决策依据、OUT-9），CHANGELOG 加 v0.6 纠正条目，progress.md Decisions 同步。skill / rule 本体未动，用户未说"以后都"，暂只记录。
