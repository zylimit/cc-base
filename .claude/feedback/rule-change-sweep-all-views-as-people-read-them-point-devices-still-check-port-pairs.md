# 规则一改，抢在团队前面分页签核对「人看到的字」；当成一个点的设备也按口对查占用

**问题描述**：（经过由主 Agent 派单转述，观察员未复核；盒名、芯号、口号已换成合成值）

v2.62.0 把排芯改成逐芯定：现场跳纤落哪芯用哪芯，没跳纤的按顺序往后排、跳过已占的芯，一只盒子的芯从此可以不连续（排芯那一层见 inferred-rules-never-judge-field-data-fill-in-order-goal-all-connected.md）。主 Agent 发版前验的是引擎结果，没有把各页签上人看到的字逐项拿数据核。用户看光路模拟截图（某台 OLT 后一块板的整板口和前一块板最后几个口是黄圈）自己发问，三处与事实相反的字才被查出来：
- 一览「沿线首盒」按头尾把某只盒子写成「第 5–48 芯」，它实际占的是 5、20、45–48。
- 「网管挂了几口」数的是勘测跳纤，不是网管；网管 6 个出口全挂着 OLT 口的盒子显示 0。
- 导入表「预连接ODN-成端」的依据写「网管里没挂 OLT 口」，与网管实际相反。

用户原话依次是：
- 「有个疑问，这个网管说有盒子对应，但是没有勘测，盒子放出来了吗？」（附光路模拟截图）
- 「现在团队已经在逐个排查，请你提前全盘排查好，不要漏了，又被打脸」
- 「刚刚ODF和OLT算是过了，OSU口我说是个点，没有排查，其实内部虽然是1对1,也是有占有关系的，比如占有了5-5这一对」（原话里的口号已换成合成值）

主 Agent 随后分路排查，ODF 和 OLT 过了；OSU 因为用户此前定过「当一个点」，主 Agent 没查口对占用，被用户指出。「又」指哪几次，用户未说明。

代价：三处与事实相反的字摆在一览、导入表这些人要看的地方，是用户自己看图发问才翻出来的，不是主 Agent 先找到的；那时团队已经在逐个排查，用户说的是「又被打脸」；OSU 又漏查一轮，用户得再指一次。

**触发场景**：改了业务规则之后收尾、准备发版或交给团队核对的时候。引擎结果（芯号、问题清单、导入表数据）对了，但同一份结果被好几个页签用文字再讲一遍：用头尾推范围、按某个来源计数、在依据句子里写死某条规则的结论。这些字把老规则当了前提，规则一改就与事实相反。主 Agent 的归因（非用户原话）：老前提是「一只盒子的芯连续」，加上栏名说网管、实际数的是勘测。观察员的读法：这些字不引用任何被改的符号，按「改被引用的东西先 grep 全部引用点」找不到它们，接口返回的数据也看不出来，要靠「谁读这份结果」来列。第二处是排查范围：「当一个点」本是建模上的简化，被拿来当成了不用查的理由。

**教训/建议**：
1. 什么时候做：一条规则或口径改了，或团队要开始核对某一版之前，就做一次全盘核对，不等用户看图、不等团队找出来。标志是展示里有「把老规则当前提」的字：用头尾推范围的、按某个来源计数的、依据句子里写了规则结论的。
2. 怎么做（主 Agent 写进用户记忆的做法，是它从这次纠正归纳的，用户原话里没有这些细节）：先列出读这份结果的所有页签和导出（本项目：一览、地图、机房内、光路模拟、问题与整改、矛盾手册、导入表、对账、各导出文件）；再分路并行做只读核对，看页面上人看到的字，不只看接口返回；每个区块、栏、数字、依据句子拿勘测、网管、竣工、排芯结果核；最后给一张覆盖表，没核到的格子写「没核」。
3. 栏名、依据句子说的口径，要和实际数的来源对号：本次「网管挂了几口」栏名说网管，数的却是勘测。
4. 建模上的简化不是排查豁免：设备在模型里当成一个点，内部的占用关系仍是资源。OSU 内部虽然一对一，每一对同号口是被占的资源（业务规则那一半已进 progress.md Decisions，这里不重述）。覆盖表按资源列行（ODF、OLT、OSU 口对……），不按模型里有几个点列；用户说某几类「过了」，没核的类别也在表上写明，别让「没核」悄悄变成「没问题」（后半句是观察员归纳）。
5. 同族提示（观察员归纳）：visual-sensitive-output-full-rollout-needs-visual-gate.md（08-08，数据验证对 ≠ 地图上看着对）与本条（引擎结果对 ≠ 各页签上的字对）形状相近：交出去之前验的东西，和人实际看到的不是同一件。供 evolution-engine 判断是否成族、是否同落 dev-builder 的验收环节。
