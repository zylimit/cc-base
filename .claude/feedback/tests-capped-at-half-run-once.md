# 测试写太多、跑太多：守 1/2 铁律，一次就够

**问题描述**：
- 2026-11-03 发版前补审补测。审查和测试查出 3 条 HIGH 之后，测试员补了 951 行测试，修复者又加了 2 条。
- 主 Agent 量了比例，向用户报告「超了」：
  - 后端测试 9,600 行，比后端业务代码 7,715 行还多（1.24 倍）；加上这次补的，到 1.37 倍。
  - 前端 7,856 行也算进有效代码，比例是 0.68。
  - 共 743 条用例，几乎全部标 `# risk: high`，「日常只跑 high」形同全跑。
- 用户先后说：
  - 「删了，不能超过1/3，测试只是掩盖无能」
  - 「测试代表超过业务代码，有什么用」
  - 「铁律，测试不能超过1/2」
  - 「现在最大的问题，就是用例写太多，发挥作用很少」
  - 「我现在对发版本，几个小时，烦透了」
  - 「测试执行也是问题，有病吗，执行这多次」
- 同一批改动被跑了十几次：
  - 主 Agent 干净导出跑全量基线，每次 12 分钟；
  - 三位审查员各自跑相关文件；
  - 测试员多轮整跑，外加 7 个变异自检；
  - 修复者两轮各跑 21 个文件，每轮 5–7 分钟；
  - 主 Agent 两次亲跑红锁。

**触发场景**：
- 快速模式下欠的审查和测试，按约定攒到发版前补。补的时候按「HIGH 档 tester 补关键逻辑测试」加用例，却没先看比例。
- 每个角色又都按「自己跑一遍才算有证据」各跑各的，没有一个人管总共跑了几次、花了多少时间。
- test-builder 只写了「测试代码占有效代码 1/3～1/2」这一句建议，没有闸，也没人在写测前算过。比例早就超了，没人拦。

**教训/建议**：
1. **用例数量守比例：测试代码不超过业务代码的 1/2（铁律）**
   - 业务代码按前后端全部业务代码算，不含测试，这是用户选的。
   - 新写测试之前先算比例。已经超了，就先删低价值用例腾出额度，再写新的。不能「先加上，发版后再删」。
   - 删的顺序：同一行为被作者和独立测试员各测一遍的重复覆盖 → 测界面文案、格式细节的 → 从没抓到过问题的。守数据的（升级迁移、导入解析、撤回、密码）最后动。
   - `# risk: high` 只给真会毁数据的用例，其余降到 medium / low。分级要能真正少跑东西。
   - 补测只补那个缺陷的那一条回归，不铺一组变体。变异自检默认不做。
2. **执行次数收敛：每个角色只跑一次该跑的**
   - 修复者：改完对相关文件跑一次，以最后一次为准，不分轮反复整跑。
   - 发版卡点：跑一次全量，主 Agent 读它的原始输出验收，不另跑一遍。
   - 审查员复核：只看 diff，不跑测试。只在要证实某条具体 HIGH 时，跑一条点名的用例。
   - 红锁「亲见 fail」：等红测定稿后跑一次，不分批跑两次。
   - 别人已经跑过、代码也没再变的，不跑第二遍。
3. **用户的耐心有上限**：发版要几个小时，本身就是问题。降时间要靠「少写、少跑、跑快」，不靠省掉审查或红锁这些步骤（见 release-blocking-fix-dont-rush.md）。

**适用范围与例外**：
- 适用于此后所有写测、补测、修复验证、复核与发版，所有角色都照这条来。
- 「不能超过1/3」那句：用户先说 1/3，随后定 1/2 为铁律。主 Agent 按「1/2 是硬上限、1/3 是方向」理解，已写进 progress.md Pinned，待用户纠正。
- 例外：用户当轮明确要多跑或补某类测试时照办。守数据的用例删得最晚，但不因为是守数据的就不算进比例。

**和已有 feedback 的关系**：
- **release-blocking-fix-dont-rush.md**：互补，不冲突。那条说发版阻断修复要走完整闭环：红锁 → 修 → 原审查员复核 → 干净导出全量 → 清单清零，不为提速调换或省掉步骤。这条说闭环里每一步不重复跑测试：复核只看 diff，全量只在发版卡点跑一次。步骤一个不少，执行次数要收敛。
- **fast-mode-skips-review-and-tests.md**：互补。快速模式不测，发版前补测兜底照旧，但补测要守 1/2 上限：先删再补，不能越补越多。
- **review-before-deploy-even-in-fast-mode.md**：修正其中「尽量补测试」一句，补测受 1/2 上限约束，不是越多越好。
- **写测者独立于被测作者**（.claude/rules/subagent-dispatch.md [隔离原则]，指向的 test-independence-author-not-tester.md 不在本项目 feedback 目录里）：有张力，但不冲突。独立测试员仍然要和作者分开，只是不再因此并存两份覆盖同一行为的测试。删重复时，留独立测试员那份或其中更好的一份。
- **test-builder「测试代码占有效代码 1/3～1/2」**：这条修正它的上限说法，从「区间建议」改成「不超过 1/2 的硬上限，写测前先算、超了先删再写」，并写明分母是前后端全部业务代码。下限 1/3 没有依据：用户的方向是「越少越好、起作用的才留」，所以不能再拿 1/3 当「至少要写这么多」的理由。
