# 入站连通性排障：先说清测试方向，根因查出直接给修法

**问题描述**：用户说「本机（ai-node Ubuntu）的 mosh 服务装一下，连不上」，意思是别的机器 mosh 连本机连不上，要修的是本机服务端。主 Agent 发现 mosh 已装后，从 Mac 发起 mosh 回连本机做入站测试（通），又从 hub/ROG 测 SSH 回连（被拒 publickey），然后反问用户在哪台设备连。整个过程没先说「我在模拟你从其他机器连进来」，用户只看到主 Agent 一直在连别的机器。用户原话：「你不是mac，你就是个ubuntu。。。」「我说，我用其他机器连你，mosh，连不上，你连其他人干嘛」。

**触发场景**：用户报「X 连不上本机」，主 Agent 需要借其他机器当客户端做入站测试，且这些机器的存在对用户不可见、动作没有预告。测试已经查出根因（本机 authorized_keys 不认对端公钥）却没直接给修法，转头反问用户细节。

**教训/建议**：
- 入站连通性排障，动手测之前先一句话说明方向：「我借 X 当客户端连回本机，模拟你从外面连进来」。用户看得懂每一步在测什么，才不会误以为在跑偏。
- 分清谁是服务端、谁是客户端：用户说「连不上本机」，要修的是本机；不拿「我是哪台机器」去替用户猜他的设备。
- 查出根因就直接给修法（本例：把对端公钥加进本机 authorized_keys），不绕回去反问用户在哪台设备连。信息已经够下判断时，反问是把工作推回给用户。

**适用范围与例外**：主 Agent 做 SSH / mosh / 端口 / 防火墙这类入站连通性排障，且要借第三方机器做测试时按这条来。用户只问概念、不涉及实测时不适用；真缺关键信息（如不知道对端公钥是哪把）才问，问之前先说清已经查到什么。

**本次落地**：已在当轮回复里落地，skill / rule 本体没动（归类「AI 工作方法类」，当前产物已够，不动本体）。
- 回复开头补了测试方向说明：「在 Mac 上跑 mosh 客户端连回这台 Ubuntu，等于模拟你从别的机器连进来」，并承认之前没说清。
- 直接给了根因修法：本机 authorized_keys 不认 hub/ROG 公钥，给出一条 `!` 命令，让用户拉对端 .pub 追加进 ~/.ssh/authorized_keys。主 Agent 读 .ssh 被 secret-exfil-guard 拦，所以由用户亲自执行。
