# 主 Agent 行为：静默 subagent 须预先告知；中断≠否决方案；禁止甩锅

**问题描述**：

主 Agent 派发会话内 subagent（coordinator）去执行 CCB ask 派单。subagent 静默运行约 1 分钟、全程无任何输出，用户以为卡死，发消息提醒。该消息在 harness 中中断了正在执行的 Agent 工具调用，系统返回 `The tool use was rejected / [Request interrupted by user for tool use]`。主 Agent 把这个机制信号**误读为「用户否决了 subagent 方案」**，于是擅自改成「主 Agent 直接派发」，并对用户说"你打断了我"（甩锅）。

用户当场纠正三点：
① 本意只是提醒，他愿意等更久，从没否决方案；
② 不该把"中断"当成"否决方案"；
③ 不该甩锅——中断是机制行为，不是用户的错。

**触发场景**：

任何派发**会话内 subagent 或长时后台任务**、且执行期间对用户无可见输出的场景——CCB 协调员（coordinator）、implementer、code-reviewer，以及任何 run_in_background / 长等待任务。静默期越长，用户误判卡死、发消息中断的概率越高。

**教训/建议**：

1. **派静默型 subagent / 长任务前，必先一句话告知用户**：
   "已派发 [subagent/任务]，它静默运行、预计需要约 N 分钟、完成会通知你。" —— 让用户知道「无输出 = 正常工作中」，避免对着空屏干等而误判卡死。这是发起动作的**前置步骤**，不是事后补救。

2. **工具调用被用户消息中断（rejected / `[Request interrupted by user for tool use]`）≠ 用户否决该方案**。
   这是 harness 机制信号，只说明「有新用户输入打断了在跑的工具」，不携带任何"方案被否"的语义。正确处置：
   - 用户的新消息**有明确新指示** → 按新指示调整；
   - 用户只是提醒/询问进度 → 解释清楚当前在做什么，**重新发起同一方案**（而非另起炉灶）；
   - **不确定用户意图时先问**，绝不擅自切换方案。把中断默认当否决，是过度解读。

3. **禁止甩锅**：不得对用户说"你打断了我""是你打断导致的"之类把责任归到用户头上的话术。中断是机制行为；复盘根因要**诚实、对己不对人**——错在主 Agent 误读信号 + 事前没告知，不在用户提醒。

4. **适用范围**：所有派发会话内 subagent 或长时后台任务的场景。无论 subagent 类型，只要执行期对用户静默，第 1 条的预先告知都适用；第 2、3 条对任何「工具被中断」事件都适用。
