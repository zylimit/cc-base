# 问题清单要发现问题，不为压低条数自造过滤规则

**问题描述**：T0511 问题清单里「线落不了点」34 条，多数是另一站 LG4592 的馈线（竣工标 LG4592 主用、T0511 备用）。主 Agent 提议按线名里的起点站码把这些线排除出去，只留一行说明，以减少 T0511 名下的问题条数。用户否决：「我不是为了少问题，我要发现问题，不自己加戏」。

**触发场景**：传统段还原的问题清单里，同一类现象条数偏多，AI 想让清单看起来更干净，就拿线名里的站码当推断依据设了一条过滤规则。这条规则是 AI 自己发明的，用户没定过，也没验证过线名站码和归属的对应是否可靠。

**教训/建议**：
- 清单的价值在于暴露问题。条数多是现象本身，不是需要被处理掉的麻烦。
- 不为减少条数提议改判断口径，不自己发明推断规则去过滤。
- 看到什么如实报；觉得有背景需要交代（例如这 34 条多是 LG4592 的馈线、竣工标主用 / 备用），只补一句事实说明，条目照列。
- 想到「能不能把这类排掉」时，这个念头本身就是信号：要不要排是用户的判定，不是 AI 的优化项。
- 与 room-jumper-no-data-then-break-not-guess-and-explain-one-thing-at-a-time.md 同源：推出来的东西默认不做，没有依据就进问题清单。

**适用范围与例外**：传统段还原和其他核查 / 质量类清单都按这条来。用户自己判定某类不是问题（如电杆同名两处不报）时照用户的口径办，那是用户给的规则，不是 AI 推的。

**本次落地**：主 Agent 已在 progress.md Decisions 记下本次决定（2026-10-19）；T0511 清单保持如实列出，不做站码过滤。skill / rule 本体未动。
