# 大批量重构收口、发版前须主动扫重复代码并给出裁定

**问题描述**：v3 harness 连续五期改造（hook 单运行时、档位、分发面、golden 瘦身、CLAUDE.md 瘦身）落地后，主 Agent 直接准备发 v2.0.0，全程没做过一次重复代码/可提炼逻辑检视。用户提醒"检查一下是否存在重复代码、是否可以提炼的逻辑"后，主 Agent 才用 40-token 滑动窗口对 49 个 .mjs 扫克隆，查出 17 处 ≥60 token 重复，裁定提炼三处、两处明确不做（两行的测试 pass/fail 助手 12 份重复，不值得为它拉一个 source 依赖；脚本与引擎各一份 safeId 是有意不互相 import，避免跨层耦合）。提炼过程中 tester 写对照组时又撞出一个真实盲区：git porcelain 检测未跟踪新目录用的命令没带 `-uall`，会漏判。

**触发场景**：多 Phase / 跨目录的重构或新增改造收口、准备发版前。

**教训/建议**：
1. 大批量改造收口、发版前，主 Agent 主动做一次重复代码/可提炼逻辑扫描，不等用户提醒——这该是收口自检清单里的一项，跟三文件同步、四步走验证同一性质。
2. 扫描要量化留痕：用什么工具/窗口（如本例 40-token 滑动窗口）、扫了多少文件、查出几处克隆，不能空口说"看了一遍没问题"。
3. 裁定要「做/不做」都写理由——不做的也要写清楚为什么不值得提炼（如"两行助手 12 份 vs 拉一个 source 依赖的耦合成本"、"两处 safeId 有意不互相 import 避免跨层耦合"），防止为了抽象而抽象，也防止漏判真正该提炼的重复。
4. 提炼动作本身要走正常派发链（implementer 改、tester 补对照组），提炼中冒出的新盲区（如本例 porcelain 未带 `-uall`）按 red-locks 处理，不因为是"顺手重构"就降低验证标准。
