# 从验收结果反推任务与依赖

当切片或依赖尚不清楚、验收不能落到动作，或工作涉及共享契约、迁移、集成与关键未知时读取对应部分。清楚的小修订只用适用方法；本文不增加固定阶段、Task 数量或质量门。

## 补读界面、数据与技术依据

规划 UI 时，从实际 Brief/界面/原型与试走记录提取本次页面和变体、组件/布局、交互状态、跳转与可复用部分，用它们核对范围和工作量；没有稿可从需求与现有界面继续。设计与需求冲突时先查哪项决定仍有效，不能把整套设计稿默认为本次范围，也不能以"稿存在"推断体验已认可。非 UI 任务不补这些资料。

涉及数据库才列实际表/迁移、所属 Task 或 Phase 与用途，涉及已定架构/DFX 才承接相关职责、质量目标与测量条件。目录、清单、lockfile 和已有验证入口帮助确认现实约束，不替代业务规则；不重新设计未受影响部分。

技术依据只解决会改变本次计划的判断。已知环境且没有选型/API/依赖变化，核对当前版本与项目约束即可；确需选择时按功能、兼容性和维护成本比较最小方案，查官方当前资料并区分当前与候选版本。证据不足只阻塞依赖项，不自动升级或新增依赖。例如首次使用的框架先验证所需能力，关键第三方 API 在依赖实现之前核实，性能敏感路径在实现中留出真实测量，而不是最后凭感觉优化。

## 按完整结果切片与排序

从参与者的一件任务沿输入、判断、数据变化到可观察结果，选一个够小但完整的切片。例如按已定规则先能找到可预约场次，再能实际预约和查询结果；这些只是划分方法，实际功能仍以项目 Spec 为准。数据、接口、UI 可以分工，但服务同一个可验收结果；基础设施 Task 单独说明支持哪项结果及自身检查。

一个明确文案或配置修订可只有一项 Task。复杂依赖才从当前范围的功能列出真正缺少的前置，形成有向图并拓扑排序；存在环时先澄清共享契约/先后条件，不能假设已是 DAG。具备的基础设施不再安排搭建，无依赖能力按当前价值、方向未知与执行成本排序。

粒度以行为内聚、独立验收、owner 边界和派单执行成本校准；横跨无关功能或超过可执行范围就拆分，需要分组再设 Phase。每批写"用户能做什么 → 系统做什么"及可判定结果，不把基础设施、i18n、打包或部署作为固定收尾套餐。只交付配置界面时要注明实际连接能力在哪个后续 Task，例如一份计划若写"Phase 4 配置 UI、Phase 10 连接引擎"，就需保留这种边界，不能称 Phase 4 已经连通。

优先处理会改变方向的术语、权责、外部行为、状态理解或迁移条件。研究与无关实现可以并行，写入依然服从 ownership/worktree；没有时间/收益依据时写未知或条件估计，不制造确定日期与得分。研究的结束条件见下文，不要求它得到成功结论。

## 让每个结果有产生证据的人和动作

先选当前范围的一条验收，用原规则和例子说明"在什么前提下，谁做什么，应得到什么"。再反向追四件事：

1. **在哪里观察结果**：页面实际状态、接口返回、保存后重开、包内文件，还是目标环境行为？选用户承诺所在的边界，不把编译成功替代这些结果。
2. **哪段工作使它成立**：沿真实入口列出必要实现或已有能力。若无人负责最后一次写回，不能因为接口和页面各有 Task 就认为结果完整。
3. **谁、用什么产生证据**：沿现有 runner、命令和角色分工确定作者检查与独立验收。计划记录预期的产生方式，实际结果只在执行后填写；完整验收安排仍由主 Agent 按 Task 定档（LOW / MEDIUM / HIGH，见 dev-workflow-details.md）派发。
4. **验证需要哪些前提**：可用版本、隔离数据、可达初态、可控制的时序、测试入口。前提已有就引用；要新增就放入负责它的 Task；未知则指出阻塞的验收和解除方式。

把答案放进既有 Task 的目标、文件责任、依赖、聚焦验证和预期结果，不新建必填账本。一个 Task 可以实现并产生其作者证据；独立 reviewer/tester 的责任按 Task 定档安排（MEDIUM 起才派 code-reviewer，HIGH 加派 tester，与实现者不同实例），不能让"谁实现"自动成为"谁独立批准"。

**足够条件**：执行者能说明结果为何如此，能找到真实入口和必要输入，并知道证据由哪个动作产生。某项结果没有产生者时，补相应工作或标明未验证；若缺的是业务口径，先返回来源冲突，不能编一个 expected 让计划看似 ready。

## 区分功能依赖与验证依赖

目录互不相交不代表可以并行。实现两端共享对象身份、单位、状态或错误语义时，先核对实际契约：哪些输入允许、谁写权威状态、失败怎样表达、旧数据怎样解释、由谁消费。已经明确的契约直接沿用；未决部分只阻断依赖它的工作。

| 当前事实 | 计划判断 |
|---|---|
| 两端共享契约已明确，写入范围互斥 | 可交主 Agent 依 ownership/worktree 约束派发，指定 integration owner 验证两端实际接合。 |
| 一端有 mock，另一端尚未提供真实接口 | mock 可支持本层开发；真实连接的验收依赖接口就绪，不能把 mock 结果登记为集成完成。 |
| 共享 schema、迁移或生成清单仍需改动 | 明确单 writer 与消费顺序，避免各端自行定义一份貌似兼容的契约。 |
| 只是同一目录里两处无关文案 | 按实际 ownership 和改动冲突判断，无需新建共享协议或集成阶段。 |

集成责任必须落实到具体 Task/owner：使用同一输入核对消费者得到的含义与上游一致。它可以归于现有 Task，不为表格完整另拆一项。公共契约变化时更新依赖它的 Task、fixture 与验收，保留原完成证据的历史适用范围。

## 研究任务结束的是未知

spike 先写需要区分的解释与观察，例如"目标环境是否允许读取必要资源"。指定可得来源或最小实验、允许副作用和结束条件；结论可以否定方案。实验成功只支持实际观察到的前提，不能把实验桩、手动步骤或单环境结果算作生产实现。

回传应能改变后续决定：已证实什么、不能证明什么、选择因此怎样调整、哪些 Task 可以开始。若实际操作不可逆，计划还需承接既有数据/版本基线、恢复前提和负责者；恢复方案没有依据的部分保持未决，普通文案修改不填生产回滚表。

## 交给下一角色

选择一个可派发 Task，检查 fresh 实现者仅凭派单和必要补读能否还原规则、区分性例子、共享前提和验收入口。不能则补必要含义，不把整份项目资料复制进派单。用户纠正后让相同检查消费新规则，避免旧 Task 与新来源同时指导工作。
