[任务]
    **生成模式**：读已确认的需求内容（默认 Product-Spec.md；用户指定了别的 PRD / Spec 路径，或本次会话里已经谈拢确认的局部需求，都按实际来源读，`Product-Spec.md` 只是没人指定时的默认名）与可选输入，分析功能依赖，本次确实要新引入或变更技术栈时 WebSearch 验证选型，按 templates/dev-plan-template.md 输出 DEV-PLAN.md。
    **迭代模式**：Spec 变更后分析影响范围，更新 DEV-PLAN.md 的 Phase 划分和文件清单。
    能用一句话描述 diff 的改动不写计划，直接进 dev-builder。
    **计划粒度判据**：完整结果一个 Task 就能交付时，用一个 Phase 装下这一个 Task 就够（本仓 `plan-lint.sh` 要求 DEV-PLAN.md 至少有一个 `## Phase` 小节，不硬拆成多个凑数）；出现多个可独立验收的交付组才真正拆成多个 Phase。Phase 数量由交付组数决定，不是预设几个才算够——Phase 完成时的四步走质量门是 dev-builder 的事，这里只管切多大、切几份。

[依赖检测]
    Skill 启动时第一步自动执行。
    必需的是「已确认的需求内容」，不是固定文件名：没人指定来源时默认读根目录 Product-Spec.md；用户指定了别的 PRD / Spec 路径，或本次会话里已经谈拢、确认过的局部需求，都按实际来源读，不因为文件不叫 Product-Spec.md 就判定缺失。确无任何已确认需求（默认文件不存在、用户也没给出替代来源、会话里也没谈出过任何已确认内容）才提示先调用 /product-spec-builder。
    Spec 里已确认的部分足够支撑局部计划时，可先对已确认部分直接出计划；未确认部分只阻断依赖它的 Phase / Task，不因为 Spec 没写全就拒绝出计划——形成一份「部分可执行 + 明确阻塞点」的计划，好过等全部谈拢才动笔。
    可选（缺了标降级模式继续；同样按项目里的实际路径读，文档实际拆成多份子文档或放在非默认路径时不假设都叫这几个固定文件名——上面的必需输入也遵循这条，Product-Spec.md 只是默认名不是强制文件名）：
    - Architecture-Design.md（含拆出的 ADR 子文档，如有）→ Phase 按模块边界拆，目录结构沿用其骨架，依赖正序按其依赖图排
    - DFX-Spec.md → 各维验证手段折进对应 Phase 的验收标准，critical / high 档验证不许推到最后一个 Phase；缺则把 Spec「非功能」表的 P0 项折进对应 Phase 验收
    - Design-Brief.md → 页面 Task 按 SCREEN 编号拆；缺则视觉细节标 [待 Design Brief 补充]
    - DESIGN.md → token 落地按实际需要折进相关 UI Task 的改动范围，不强行为每个项目单开一个固定的「token Task」
    - 设计工具 MCP 或仓库内已有原型 → 有则 Phase 拆分与关键文件以设计稿 / 原型的实际页面结构为准，不只看 Spec 文字
    - 已有项目代码 → 扫描现有结构、清单与已实现能力作为约束，进迭代模式

    └── templates/

[第一性原则]
    **可验证**：每个 Phase 完成后能编译、能运行、能看到效果，不允许"写一堆代码但什么都跑不起来"的 Phase。
    **价值与未知先行**：Phase 顺序由两件事定——先交付核心价值（去掉它产品不成立的那条流程），先验证关键未知（Spec 里的 `[推断]` `[待定]`、没用过的技术、没试过的集成）。基础设施只做支撑第一条价值流程所需的最小部分，不为「地基」单排一个什么都看不到的 Phase；依赖是校正项，不是排序主轴。排期默认一次一个功能串行收口，不并排几个半成品——并排的那几个最后一起返工。
    **联网优先**：技术栈与关键依赖的版本、兼容性、breaking changes 先 WebSearch 再定；预算有限时框架与数据层先核，小依赖写「安装时取版本」。
    **粒度适中**：一个 Phase 对应一个可独立验收的功能单元，通常 1-3 个核心交付物。
    **文件路径明确**：每个 Phase 列出要创建或修改的具体文件路径。"实现聊天功能"不是计划，"创建 src/components/views/chat-view.tsx 和 src/hooks/use-chat.ts"才是计划。
    **无占位符**：不许 TBD、TODO、"待补充"、"待确定"、"类似 Task N"、"添加适当的错误处理"、"实现相关功能"。每条描述完整到一个没有项目上下文的工程师也能读懂并执行。
    **可执行性标准**：按最坏的执行者设防——对本代码库零了解、品味存疑、甚至厌恶写测试，照着也能做对、不靠悟性。每一步给齐三样：明确的文件路径 + 具体改动（改哪个函数 / 加哪个字段 / 接哪个调用）+ 验证命令（`tsc --noEmit`、`pytest tests/test_parser.py`、`curl localhost:3000/api/x`，不写"自行验证"）。

[分析维度清单]
    **必须分析**（没有这些，DEV-PLAN 就是空中楼阁）：
    - 技术栈：框架 + 版本号、UI 方案、数据库方案、包管理器、部署目标；本次确实要新引入或变更技术栈时逐项 WebSearch 验证，已有项目沿用现有版本不必重新逐项核实
    - Phase 拆分：按依赖关系和复杂度分解为有序 Phase，每个是可独立验收的功能单元
    - 每个 Phase 的交付清单：动词开头，写"用户能做什么 → 系统做什么"
    - 每个 Phase 的关键文件：具体路径；新项目按技术栈约定推导，已有项目扫描现有结构
    - 功能依赖图：识别功能之间的依赖，确保 Phase 排序不违反它
    **尽量分析**（有这些，Plan 更落地）：
    - 数据库设计：表名 + 首次创建的 Phase + 用途说明
    - 每个 Phase 的验收标准：最低能编译 + 能启动 + 新功能可用，推荐加上现有功能未破坏
    - 已知风险与限制：如"Phase 4 只实现 UI 配置界面，实际连接引擎在 Phase 10"
    **不需要分析**（交给 dev-builder 决定）：
    - 具体的代码实现细节（函数签名、类接口）
    - 具体的 CSS 样式方案
    - 测试用例设计
    - Git 分支策略

[分析策略]
    **依赖图构建法**：列出所有功能点 → 逐个问"它能独立运行吗、依赖哪些功能或基础设施" → 构建有向无环图 → 拓扑排序得到的是「不能违反的先后」，不是 Phase 顺序本身；骨架只到能跑通第一条价值流程为止，其余基础设施放进用到它的那个 Phase。
    **价值排序法（排序主轴）**：核心功能（去掉它产品就不成立）→ 重要功能（有它才好用）→ 辅助功能 → 收尾功能（i18n、打包、部署），再用依赖图校正，只在被依赖方必须先做时调整。
    **粒度校准法**：太大＝交付清单超 5 项 / 关键文件超 10 个 / 涉及 3 个以上互不相关的功能；太小＝交付清单只有 1 项且简单、关键文件只有 1-2 个；合适＝交付 2-4 项、关键文件 3-8 个、功能之间有内聚性；首条价值流程的最小骨架 Phase 允许超上限，超了写进已知风险。
    **假设前置法**：每个 Phase 写明「验证的假设」——来自 Spec 的 `[推断]` / `[待定]` / `[默认]`（替用户选的默认也是假设）、没用过的框架、关键第三方 API、性能敏感点，没有就写「无」。含核心假设（假设不成立整条流程要重来）的 Phase 排在纯功能堆叠之前，验收标准里写清「假设成立的证据是什么」；`[推断]` 的核心行为在最早能演示它的 Phase 就拿真数据验，验完回 Spec 改成 `[确认]` 或改需求。
    **大范围迁移法**：同一机械变化（改名、换接口形式、改生成格式）传播到多个消费者且需要兼容期时，按 references/acceptance-and-dependencies.md 的「大范围迁移的兼容与退出」列清消费者、生成入口、批次、兼容窗口与每批可运行基线，写明失败时保留哪个已验证可运行的版本；某批无法独立通过集成检查时只声明实际跑过的局部证据，并指定最终集成与全量检查的 owner Task。一般小功能与单处修订仍按原简单计划，不填这份清单。

[待定问题处理]
    读已确认需求来源（[依赖检测] 判定的实际来源，默认 Product-Spec.md）的「待定问题」表：押后到本计划范围内的问题必须先答，列出涉及的条目提示用户；`[推断]` 条目一并列出，让用户挑错。不能提问时（派单 / 批处理）按表里「不答先按什么做」执行，在计划开头「开工前置」段写明按了哪个默认、押后到哪个 Phase。
    计划阶段发现 Spec 缺口或自相矛盾（待定表的默认与正文条目打架、规则没覆盖的分支）→ 报「需求存疑」+ 反例回流 product-spec-builder，不自行补需求；必须先动时取最简默认，在「开工前置」段列明待回签。
    待定口径还写不出预期行为与验收时（例如完成率的分子分母要等验收负责人拍板），按 references/acceptance-and-dependencies.md「按完整结果切片与排序」里的取证依赖写法，把依赖写成「谁 / 哪份来源回答什么 → 解锁哪项行为、Task 与验收」，先排取证与返回后重判的条件，不把这部分提前列成可派发 Task；已知部分照常成 Task，答案回来再更新依赖与受影响的验收。明确的小修订不画依赖图。

[信息充足度判断]
    **必须满足**（差一条本次范围就不能派发，未达成继续分析，不生成半成品）：
    - 本次范围要落地的技术栈已确定：首次引入框架 / 关键依赖时经 WebSearch 验证；已有项目沿用现有版本不必重新选型，不为出计划强行升级
    - 本次范围的 Task 拆分完成，每个 Task 有明确的交付内容；出现多个可独立验收的交付组才用多个 Phase 分组，一个完整结果只用一个 Phase 装（`plan-lint.sh` 要求至少一个 Phase 小节），不为凑够几个 Phase 硬拆
    - 依赖顺序合理，没有 Task / Phase 依赖未完成的前置
    - 每个 Task 有关键文件列表（具体路径，不是模糊描述）
    - 每个 Phase（有 Phase 时）或整份计划有「验证的假设」（可为「无」），Spec 的 `[推断]` / `[待定]` 核心条目都落在某个 Task / Phase 的假设里、且这些不排在纯功能堆叠之后
    - 本次范围声明要覆盖的核心功能（来自 [依赖检测] 判定的实际需求来源，不要求文件叫 Product-Spec.md）都被安排，没有遗漏；范围外仍待定的部分只阻断依赖它的 Task / Phase，不倒过来阻断已确认部分先出计划
    **尽量满足**：数据库表梳理完成、每个 Phase 有验收标准、已知风险和限制已标注。未达成时在对应 Phase 写最低验收标准（能编译 + 能启动 + 新功能可用），不使用占位符。

[生成前自检]
    - 无占位符：扫描 TBD、TODO、待补充、待确定、"类似 Phase / Task N"，命中即替换为具体内容
    - 命名一致：同一个函数 / 类型 / 字段 / 文件，跨 Phase 跨 Task 的措辞前后一致——不能一处叫 clearLayers 另一处叫 clearFullLayers，不能一处 user_id 另一处 userId
    - 当前范围覆盖：把当前计划范围内的功能逐条拉出来核对，范围内漏的补 Task，凭空多出的核对是否真有 Spec 依据；范围外的功能不在这一步核对，按 [工作流程] 的「## 范围外（本次不计划）」声明
    - 假设覆盖：Spec 的 `[推断]` / `[待定]` 每条落在某个 Phase 的「验证的假设」里，或在计划开头写明押后到哪、押后期间按什么做
    - Task 可派发：每个 Task 除文件路径 + 具体改动 + 验证命令外，还带齐 Business Context（为谁解决什么、关键规则来源、一个能区分对错的输入输出例子）、依赖类型（功能前置 / 验证前置，共享写入标唯一 owner）、证据产生者（这条验证归谁跑——对应 dev-workflow-details.md 的 LOW / MEDIUM / HIGH 判档），能直接抄进 implementer 派单不用主 Agent 现补
    - REQ 覆盖：当前计划范围内、Spec 带 `[REQ-模块-编号]` 的条目，在某个 Task 标题或紧邻行里都能找到对应编号；范围外的 REQ 编号写进「## 范围外（本次不计划）」并给出原因（待确认 / 已押后 / 归别的计划），不强行编 Task，也不能既不安排 Task 又不声明——交给 `plan-lint.sh` 做双向核对（Spec 未用编号则跳过；范围外已声明的 REQ 报「范围外（已声明）」不算失败，只有既没 Task 又没声明的才 FAIL）

[确认策略]
    只在三种情形向用户确认：本次确实要新引入或变更技术栈、且有多个合理选项时（给 2-3 个方案 + 优劣对比让用户选；已有项目沿用现状不涉及选型，不问）、存在多个可独立验收的交付组、Phase 粒度确有偏好空间时（小项目 3-5 个，中型粗粒度 6-8 个或细粒度 10-15 个；完整结果一个 Task 就够、或已有项目一条配置 / 文案 Task 时不问 Phase 数量）、功能优先级有歧义时（先做 A 还是先做 B）。除此之外 Spec 已经写清楚了，不追问。

[命名纪律]
    Phase 编号只指 DEV-PLAN 里的技术开发阶段。对用户描述产品交付顺序时改用功能名或"用户端阶段 / 后台阶段"，别和 DEV-PLAN 的 Phase N 撞出歧义。

[工作流程]
    生成模式：加载已确认的需求内容与可选输入 → 处理待定问题表 → 本次确实要新引入或变更技术栈时 WebSearch 验证选型（已有项目沿用现状、或只是一条配置 / 文案 Task 时跳过这步）→ 依赖图 + 价值排序拆 Phase（完整结果一个 Task 就够时只开一个 Phase，不硬拆多个；不为已有项目一条配置 / 文案 Task 硬问 Phase 数量）→ 粒度校准 → 充足度判断 → 按 templates/dev-plan-template.md 填充（本次计划范围外、Spec 有但没安排 Task 的 REQ 编号连同原因写进「## 范围外（本次不计划）」一节，不强行编 Task 也不能不声明）→ 生成前自检 → 写出 DEV-PLAN.md → 跑 `bash .claude/scripts/plan-lint.sh DEV-PLAN.md <实际需求来源路径>`（路径＝[依赖检测] 判定的那份实际来源，默认来源就是 `Product-Spec.md` 也显式传，不省略第二参数——无参调用只在 DEV-PLAN.md 同目录找 `Product-Spec.md`，来源换了名字或放了别处会漏查覆盖缺口；对计划范围内的 REQ 做需求双向覆盖检查，「## 范围外（本次不计划）」里已声明原因的 REQ 报「范围外（已声明）」不算失败，既没安排 Task 又没声明的 REQ 才 FAIL；需求来源只存在于本次会话、没有文件可传时，lint 跳过覆盖检查，在 DEV-PLAN.md「开工前置」段写明「REQ 覆盖未验证：需求来源无文件，未经 plan-lint 核验」，不把 Phase / Task 结构检查通过说成覆盖检查通过）。
    迭代模式：读现有 DEV-PLAN + 更新后的 Spec + CHANGELOG 定位变更 → 识别影响哪些 Phase 并向用户说明 → 在原文件上改，已完成的 Phase（标 ✅）保留原有交付记录不重写——但已完成只证明"当时那版行为"，不证明 Spec 改完后新行为也成立；发现的修正需求要落成一个新 Task（可以挂在受影响的已完成 Phase 下，也可以新开 Phase），不能因为 Phase 已标 ✅ 就假装不用处理 → 重新校验依赖 → 动到已写代码的 Phase 只提醒回 dev-builder 同步实现，不自动改码。

[初始化]
    执行 [依赖检测]，按有无 DEV-PLAN.md 与 Spec 是否变更判定进生成模式还是迭代模式。
