---
name: domain-rulings
description: 当用户说记一条口径、问某个字段或规则现在按什么算、要列待复核队列或看某条被谁依赖，或沟通里冒出一段说不清该归哪儿的领域知识需要分诊时使用。
---

[任务]
    领域口径库的人机入口：把沟通里冒出来的领域知识**分诊**到它该去的地方，该进库的收进去；另有查现行值、列待复核、看被谁依赖、手工收录四件。
    口径库是需求分析、澄清、方案设计的副产品，本 skill 也在副产品这一侧：不进四步走、不设卡点、不出现在任何验收链路上，人想记或想查的时候才用。
    接住就干——人说一句「记一条」就往下走，不开场白、不先复述本 skill 会做什么。
    不管的三件事：写入归 domain-recorder（本 skill 不碰 domain/ 里的文件）；采集归子 Agent 回执的 Domain findings 栏与那支提醒 hook；派单时按 Task 匹配口径归主 Agent 写 Business Context。

[依赖检测]
    必需：
    - .claude/rules/domain-rulings.md → 七栏、四类分拣、三种变更、四种老化、入库两问、三类依据一律以该文件为准，本 skill 不复述，先读它再动手

    可选：
    - 项目根 domain/ → 不存在就是库还没开张：查询类动作回一句「库里还没有条目」，收录类照走（目录由 domain-recorder 建），都不报错
    - Product-Spec.md / progress.md → 分诊时用来看一条是不是已经躺在「规则与例外」或 Decisions 里了，缺了不阻塞

[第一性原则]
    **分诊在收录之前**：先判这条属于哪一格，再谈收不收。跳过分诊直接收，收进来的多半是 Spec 条目或决策依据——库成杂物间是这套东西最常见的死法。
    **不替人答「谁知道」**：那一问只有人答得出，AI 不知道人知不知道。一问一答问出来，**不自己先给推荐答案**——给了人就顺着点头，要的那个信号当场消失。
    **够格才收，不为记全**：入库两问照 rules 判，不够格直说不收，不打折收录。真的但没用的条目和错条目一样是噪音，只是死得慢一点。
    **查是读，写靠派**：查现行值、列待复核、看依赖都只读。要动库一律派 domain-recorder——本 skill 判值不值得收，它判够不够格收，两道关不合并。

[四象限分诊]
    问一句：**这条当初是谁知道的？**——人知 / 人不知 × AI 知 / AI 不知，四格各有去处，只有一格通口径库。
    - **人知 AI 不知** → Spec 的「规则与例外」。用户脑子里的业务规则，AI 猜不到；走 product-spec-builder 迭代模式写进需求文档。
    - **AI 知人不知** → 技术方向或决策依据。框架、库、协议是怎么回事，用户不必知道；归宿是 Architecture-Design.md / ADR / progress.md 的 Decisions。
    - **双方都知** → 功能需求。两边都清楚的事不必存档成口径，它就是要做的东西，写进 Spec 正文。
    - **双方都不知、要共同查证才得出** → **口径库**。AI 去外网、人去公司内部，凑齐依据才定论；这一格是口径的唯一入口，也是入库门槛只认那三类依据的原因。
    - 一次只问一个，等人答完再问下一个。人答「我也说不清」本身就是信号，往第四格靠；人答「这我一直知道」→ 再看 AI 这边当时知不知道，落第一格还是第三格。
    - 机器做不了这个判断：四格里的条目长得一模一样，区别只在它当初是从谁那儿来的，而那是只有在场的人才记得的事。所以必须对着人问，不许自己诊完就收。

[五个动作]
    - **分诊**（上一节）：其余四件都是机械活，这一件是本 skill 存在的理由。
    - **查现行值**：给域或技术对象（`pon_links` 这种），回现行值 + 适用范围 + 失效条件。这条已被取代的，连「它不算数了」一起说——AI 检索得到旧措辞，不点明就会照旧的干。
    - **列待复核**：标了待复核的全列出来，按老化类型归（条件失效 / 关联失效 / 批量失效 / 污染），每条点明卡在哪儿：缺新依据，还是等数据修好。
    - **看被谁依赖**：读「被谁依赖」栏并顺着往下一层列全，回「改这条要连带复核这些」，不只回直接引用的那一层——关联失效最容易漏的就是第二层。
    - **手工收录**：走分诊 → 入库两问 → 补齐七栏 → 派 domain-recorder。

[工作流程]
    [第一步：认动作]
        说「记一条 / 这个记下来」→ 手工收录；问「X 现在按什么算 / 是哪一版」→ 查现行值；问「有哪些要复核 / 这条还算数吗」→ 列待复核；问「改这条牵动谁」→ 看被谁依赖；只讲了一段刚弄明白的事、没说要记 → 先分诊。
        认不出来就问一句「你是要记一条，还是查一条」，别猜着办。

    [第二步：分诊]
        手工收录与认不出动作的都先过 [四象限分诊]。落到前三格的，说清它该去哪儿并回指那条路，本 skill 不越界代写：第一格回 product-spec-builder 迭代模式，第二格回架构文档或 Decisions，第三格回 Spec 正文。

    [第三步：入库两问]
        照 .claude/rules/domain-rulings.md：① 收它是为了让 AI 下次输出更准——答不出「下次哪一步会因为它不一样」就不收；② 离开这个项目还成立吗。两问都过才往下走。

    [第四步：补齐七栏]
        依据分三类，当场点明这条缺哪类、该谁去查：AI 去外网（协议规范、厂商文档），人去公司内部（内部规范、历史上定过的事）。填不出依据栏就停在这儿，把待查的一两句话交回给人，不替人编；能填的栏先填好，不等。
        一条里出现两个判据就拆两条，拆完再收。

    [第五步：派 domain-recorder 写入]
        传给它：七栏内容、属新增还是修订 / 取代 / 收窄放宽、撞到的已有条目、依据的出处。它会再过一遍够不够格，拒收就按它点的缺口补，不绕过它直接写文件。
        回来后核一眼实际写进了哪个文件哪条 ID，不以「已写入」的自述为准。

[对话示例]
    **示例一：分诊——看着像口径，其实在第一格**
        用户：记一条，OLT 关联必须用 IP，名字不唯一会串数据。
        AI：这条当初是谁知道的——你们一直这么办，还是这次撞出来的？
        用户：一直这么办，我们现场都知道名字会重。
        AI：那它的家不是口径库，是 Spec 的「规则与例外」：人早知道、AI 不知道的业务规则，派单时只抄 Spec 的人得看得见它。我回指 product-spec-builder 迭代模式把它写进去，关联键那条顺带标来源。口径库这边不收。

    **示例二：手工收录——第四格，缺一类依据**
        用户：记一条。刚才查出来 pon_links 里 olt_ip 有 7 万多行是 NULL，所以按 IP 关联会漏一大半。
        AI：这条我不知道、你之前也不知道？
        用户：对，今天跑出来才发现。
        AI：那就是口径库这一格。两问过了：下次派单会因为它换关联写法；换个库也还成立。依据现在只有实测那一类（7 万多行 NULL），还缺一类——这批 NULL 是采集侧没填，还是本来就允许空？规范这种事得你去公司内部问，外网查不到。
        用户：我去问采集组。
        AI：那我先把能填的栏填好（现行值、适用范围、已知污染挂这批 NULL），依据栏留你那半条。问回来我再派 domain-recorder 收。

    **示例三：反例**
        × 用户说「我们这儿一直按 IP 关联」，AI 当口径收进库——第一格的东西，家在 Spec 的「规则与例外」。收错地方的后果是 Spec 缺了这条规则，而派单只抄 Spec 的人永远看不到它。
        × AI 查到「PostgreSQL 的 text 没有长度上限」就收一条——第二格，这是技术方向 / 决策依据。库里塞满通用技术常识，就没人愿意读它了。
        × 双方都清楚的「导出要带表头」收成口径——第三格，它是功能需求。口径回答「怎么算」，不回答「要做什么」。
        × 分诊时先递答案：「这条应该是你早知道、我不知道的吧？」——人会点头，四格当场退化成一格。问法是「这条当初是谁知道的」，问完闭嘴等。
        × 凭一次实测就定论入库——撞出来的是线索，AI 查外网、人查内部补齐依据才定论。
        × 把本次改动的范围限制（不新建表、本批不改 X）收进库——做完即失效，不进库。
        × 同主题已有现行值，又新开一条——那是在库里造两个互相矛盾的真相，该走修订或取代。
        × 把「某 session 的 connectivity 全 NULL」按失效处理——那是污染，口径对、数据不对，混进失效会让人去改一条本来正确的口径。

[收敛条件]
    - 查询类：回了现行值 / 待复核清单 / 依赖链，被取代与污染状态一并点明 → 收敛。
    - 分诊类：四格落定一格，前三格的已回指去处 → 收敛。不强求最后有东西进库——诊清楚了就算办完。
    - 收录类：domain-recorder 回执到手、核过实际写进哪条 ID → 收敛。卡在依据没齐的，把「谁去查哪一类」交回给人也算收敛：悬着的依据不算失败，凑出来的依据才算。
    - 不统计库里有多少条、不追覆盖率——副产品没有覆盖率这回事。

[交接]
    - **给主 Agent 派单**：查出来的现行值进派单包 Business Context（见 .claude/rules/subagent-dispatch.md），与 Spec 的规则与例外并列。
    - **给 product-spec-builder**：第一格的条目交它写进「规则与例外」，本 skill 只回指不代写。
    - **给 domain-recorder**：收录动作的唯一出口，七栏与依据出处一并传。
    - **给 progress.md**：分诊出的取舍（某条判为不收、某条判去 Spec）按 Decisions 三要素记一条；库自身的修订不记 progress.md，git log 就是修订链。
    - **上游三条**：子 Agent 回执的 Domain findings 栏、红蓝审查 Judge 挑出来的领域线索、需求澄清与方案设计当场的对话——都落在本 skill 的分诊入口。
