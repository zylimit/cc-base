---
name: question-bank
description: product-spec-builder 采访选题时读。13 个维度，每维五段（覆盖意图 / 主问题 / 追问深化 / 接受标准 / 不接受的答案）；用户已覆盖的维度直接吸收不重问。它是反含糊的约束工具，不是顺序问卷。
---

[定位]
    想瞎问时看 [主问题]，想接受敷衍时看 [不接受的答案]，想提前停时看 [接受标准]。维度编号和标签只用于自己追踪，用户面前不暴露。
    地基（1-4）必须过；5-11 按产品动态裁剪，用户一次回答溢出覆盖后面维度的直接吸收；12-13 是条件模块，只在产品要用 AI 或本身是 Agent 时展开。

[五段结构]
    覆盖意图 = 为什么问这维度。主问题 = 默认抛的问题。追问深化 = 用户敷衍时的反击，格式「用户说 X → 你回 Y」。接受标准 = 通过条件。不接受的答案 = 必须驳回的样本。

[1 · 现在怎么干（as-is 故事）]
    [覆盖意图]
        锁定一个具体的人和一次真实发生的事。没有真实的一次，需求可能是想象出来的；核心价值藏在手工传递、重复录入、来回确认里。
    [主问题]
        「上次碰到这种情况是什么时候？那次具体是谁先动的手，用的什么，然后呢，最后怎么收的尾？」
    [追问深化]
        用户说「我一般都、我总是」→ 你回：「别说一般。上次这么干是什么时候？那一次具体发生了什么，走一遍。」
        用户说「所有人都会用」→ 你回：「所有人等于没有人。第一版只为一种人做，是谁？现在明确不为谁做？」
        用户给的是观点不是故事 → 你回：「这是你的判断。给我一个真实发生过的例子。」
        用户说「现在没人管这个」→ 你回：「那今天怎么凑合的？拿什么工具、表格、土办法顶着？真是『什么都没有』，这问题可能根本不痛。」
    [接受标准]
        一个可指认的主用户（有名字或化名）+ 一次有时间地点的真实经历 + 现状工具与步骤说清 + 卡在哪一步。
    [不接受的答案]
        「所有人、大家、用户」；纯假设无实例；描述的是他的方案不是他的处境。

[2 · 为什么做、谁受益]
    [覆盖意图]
        谁在为现状买单决定做不做，谁受益决定为谁做，谁变差决定隐性规则在哪。
    [主问题]
        「这事做成了，最先松一口气的是谁？谁会不高兴？现在谁在为它付出时间、钱或风险？」
    [追问深化]
        用户说「挺花时间的」→ 你回：「上次花了多久？一周来几次？折算一个月多少时间、多少钱？」
        用户说「大家都受益」→ 你回：「多一个步骤的人是谁？以前群里喊一句、现在要进系统点的那个人，他怎么想？」
        用户说「会愿意付费」→ 你回：「已经为解决它花过钱吗？买过什么工具、拼过什么方案？没有的话为什么没有？」
    [接受标准]
        受益者、买单者、可能变差者三种人分开写；代价有数字；有已付出的努力或金钱当真实需求的证据。
    [不接受的答案]
        只有未来意愿无过去行为；「会付费」当验证；「很烦、很慢」不带数字。

[3 · 规则与例外]
    [覆盖意图]
        规则是代码的骨头，例外是规则的边界；不问例外，第一个例外那天系统就走错。
    [主问题]
        「这条规则有没有哪次不是这样处理的？那次为什么？谁决定破例的？」
    [追问深化]
        用户说「基本上都这样」→ 你回：「『基本上』之外那次是什么情况？」
        例外超过三个 → 你回：「这已经不是一条规则，是一类流程。是拆成几条，还是砍掉例外？」
        用户说「特殊情况人工处理」→ 你回：「人工是谁？系统要不要知道这单被人工处理了？」
    [接受标准]
        每条规则至少一个例子和一个例外（或明确「无例外」）；例外有触发条件和处理人。
    [不接受的答案]
        「按规矩来」不给规矩；例外说不出具体一次。

[4 · 谁说了算与历史]
    [覆盖意图]
        既定决定不能碰，试过失败的方向不重蹈，拍板人不清楚 Spec 永远批不下来。
    [主问题]
        「这个方向以前试过没有？上次卡在哪？哪些决定已经定了不接受讨论？最后谁拍板？」
    [追问深化]
        用户说「领导定的」→ 你回：「定的是目标还是做法？哪部分能动？」
        用户说「以前那套烂透了」→ 你回：「烂在哪一次？那次损失了什么？这次要避开的是哪一点？」
    [接受标准]
        既定决定清单（标「既定，不接受讨论」）；失败历史与原因；拍板人与「意见得听但不算数」的人。
    [不接受的答案]
        「没什么历史」但产品已经是第二次做；说不出谁能拍板。

[5 · 成功判据]
    [覆盖意图]
        没有能数出来的成功信号，验收就是感觉；虚荣指标（注册量、下载量）会把产品带偏。
    [主问题]
        「上线三个月后，什么数字变了你才认为成了？现在这个数字是多少？」
    [追问深化]
        用户列了一堆指标 → 你回：「挑一个北极星，和用户要完成的那件事直接挂钩的那个。别挑注册数这种好刷又虚的。」
        用户说「用起来顺就行」→ 你回：「顺是多少步、多少秒？上次不顺花了多久？」
        指标只有正向 → 你回：「这个数字涨了但别的坏了怎么办？给一个反向指标看住它。」
    [接受标准]
        1-3 条可度量、技术无关、从用户或业务视角写的判据（「客服 2 分钟内完成录单」是，「接口 200ms」不是）；有当前基线；至少一条反向指标。
    [不接受的答案]
        「体验好、更智能、更专业」；注册量下载量当北极星；无法度量。

[6 · 范围与非目标]
    [覆盖意图]
        显式钉死不做什么，砍掉模糊野心；首版内部再分 P0 / P1，防止什么都 P0。
    [主问题]
        「这一版明确不做什么？至少 3 条故意不碰的。只能上线一个功能，是哪个？」
    [追问深化]
        用户说「先都做了再说」→ 你回：「那就永远发不出来。只能上线一个，留哪个？其余你愿意先不要的是什么？」
        用户冒出新点子 → 你回：「记到『以后』清单别丢，先把核心钉死。」
        用户全标 P0 → 你回：「全 P0 等于没优先级。缺了哪个不能上线？」
    [接受标准]
        至少 3 条显式非目标；每条范围项有 P0 / P1，且每个 P0 单独实现也是可用的一小步（独立可测）；「以后」清单与非目标分开——以后可能做，非目标本轮明确不做。
    [不接受的答案]
        「都要做」；没有不做清单；说不出首版最小集。

[7 · 关键流程（未来那次）与失败路径]
    [覆盖意图]
        把现状故事翻成上线后那次会怎么发生，主角有名字、有高潮一拍；失败行为是产品行为，最可能失败的那一步必须有恢复。
    [主问题]
        「上线后上个月那单会怎么走？从谁打开什么开始，一步一步，到他松一口气那一刻。这条流程最容易在哪一步失败？失败了他看到什么、怎么继续、不丢什么？」
    [追问深化]
        用户跳步「然后他就完成了」→ 你回：「中间那步呢？他怎么从 A 到 B 的，点了什么、填了什么？」
        用户只讲理想路径 → 你回：「这一步他填错了、没数据、网断了，会怎么样？」
        用户说「提示错误就行」→ 你回：「提示之后他能重试、改输入、恢复原状，还是只能退出？刚填的东西还在吗？」
        用户说「不会失败」→ 用真实依赖逐项指出失败可能（外部接口、权限、大文件、并发）。
    [接受标准]
        至少一条完整流程无断点，主角有名字，有高潮一拍；主要分支已标；至少一个关键失败场景有触发、提示、数据保护和下一步。
    [不接受的答案]
        跳步；只有理想路径；「友好提示 / 稍后重试」不说下一步。

[8 · 数据与权限]
    [覆盖意图]
        功能要存取数据，不定实体、关系、谁能看谁能改，开发就在猜；可建必可删。
    [主问题]
        「核心数据对象是什么（工单、客户、维修工…）？它们之间什么关系？这条数据谁改、谁只看、改错了谁兜底？删除或归档怎么走？」
    [追问深化]
        用户只说功能不说数据 → 你回：「这功能背后存什么？一条记录有哪些字段？」
        用户没提删除 → 你回：「任何能创建、导入的东西都得能删或移除。删了以后引用它的地方怎么办？」
        用户说「都能看」→ 你回：「客户的电话谁能看？离职的人还能看吗？」
    [接受标准]
        核心实体 + 关系 + 单一写入者 + 可见性规则 + 删除 / 归档路径；纯前端无持久化可略。
    [不接受的答案]
        说不清数据结构就开发；只进不出的单向功能。

[9 · 产品形状：形态、平台、使用情境]
    [覆盖意图]
        产品类型从使用环境推不从喜好推；使用情境与首要动作是设计阶段的起点，不在这里问颜色和布局。
    [主问题]
        「他在什么情境下用——站着还是坐着、单手还是双手、几秒钟还是几小时、专注还是随时被打断、什么设备？这一屏上最要紧的那一个动作是什么？」
    [追问深化]
        用户说「网页和手机都要」→ 你回：「首版必须在哪个上真实可用？另一个能先降级吗？」
        用户说「界面你看着办」→ 你回：「布局归设计阶段，这里只要两样：他在哪用、最要紧的动作是什么。」
        用户说「像那个终端编程助手」→ 你回：「那是终端 + 对话式 Agent，没有传统页面，有的是会话流、工具调用、授权确认。先确认形态。」
    [接受标准]
        产品类型（Web / Desktop / CLI / Mobile / 对话式 Agent / 嵌入式）从使用环境推得出；首版基准平台明确；使用情境与首要动作各一句。
    [不接受的答案]
        为了「看起来高级」选平台；一上来聊颜色。

[10 · 非功能与隐含合规]
    [覆盖意图]
        性能、安全、隐私、兼容、可靠、可访问六类逐项给数字或明确「不要求」，喂 DFX；行业自带的隐含要求用户没提也是缺口。
    [主问题]
        「多快算够（毫秒或秒）？同时多少人用？出错怎么恢复、数据会不会丢？支持哪些设备和浏览器？这个行业有没有必须遵守的规矩——个人数据、支付、医疗、控制物理设备？」
    [追问深化]
        用户说「要快要安全」→ 你回：「多快，响应秒数、并发多少？安全具体指什么，登录、加密、还是权限？给我能验收的。」
        用户说「安全 / 隐私要完善」→ 你回：「先按产品类型和威胁定边界。自用或内部工具默认保护密钥和本地数据，不主动发明合规仪表盘；对外或涉钱涉个人数据的才上完整要求。」
        用户没提行业规矩但产品涉医疗 / 支付 / 个人数据 / 物理设备 → 你回：「这类产品通常要满足 [PHI / PCI / 个保法 / fail-safe]，你们这边有没有明确要求？没有我先记为待定交 DFX，不替你答。」
    [接受标准]
        六类各有要求或明确「不要求」，关键项有数字并标 P0 / P1；隐含合规逐条点名，标 `[待定]` 给 DFX 或 `[确认]` 用户已答。
    [不接受的答案]
        一句「要快要安全」无数字；六类全空；给自用工具发明用户不关心的安全仪表盘；替用户编合规要求。

[11 · 术语与矛盾]
    [覆盖意图]
        同一个东西两个叫法会让下游各写各的；两条不能同时成立的要求必须当场摆出来选。
    [主问题]
        「你们内部管这个叫什么？还有别的叫法吗？」「你同时要 A 和 B，这两条在 X 场景冲突——更重要的是哪个？」
    [追问深化]
        用户说「都重要」→ 你回：「只能保一个，保哪个？答案就是优先级。」
    [接受标准]
        关键术语一物一名（Spec 里同一叫法）；每条矛盾有用户的选择，写进决策依据。
    [不接受的答案]
        「看情况」不给规则；矛盾留着不选。

[12 · AI 能力（条件模块：产品要用 AI 时）]
    [覆盖意图]
        AI 是概率性的，质量、触发、失败、成本不钉死，开发就在赌；为 AI 而 AI 要先被 litmus 挡掉。
    [主问题]
        先跑 litmus：「把 AI 换成写死规则或一个搜索框，核心价值还在吗？」还在的话可能不需要 AI。
        质量条：「给我 5 个『好答案』和 5 个『丢脸答案』的例子。最重要那个质量维度，命中率到多少你敢上线，80% 还是 95%？低于多少要报警？」
        触发方式：「只是建议或草稿让用户确认，还是自动执行？」默认建议优先，先建信任。
        失败兜底：「这功能能犯的最贵的错是什么？它绝不能做什么哪怕用户要求？AI 不确定时该说不确定、给出处、追问、还是转人工？服务挂了，禁用提示、降级缓存、还是排队？」
        延迟成本：「必须多快，3 到 5 秒可接受还是要瞬时？流式输出行吗？一天大概跑多少次，单次成本有上限吗？」
    [追问深化]
        用户说「用 AI 做」→ 你回：「具体哪类？帮他生成文字、看懂图、还是基于你自己会更新的文档回答？答案该从模型通用知识来，还是从你的文档来？后者要检索增强。」
        用户要 Agent → 你回：「是要 AI 自己动手跨工具做多步，还是只要它建议、你来按确认？多步自动最贵，先确认值不值。」
    [接受标准]
        每个 AI 功能过了 litmus，有质量阈值 + 触发方式 + 绝不能做清单 + 不确定时行为 + 降级策略 + 延迟成本预算；模型与服务选型进场前 WebSearch 当前最佳，不凭记忆报名字。
    [不接受的答案]
        「要准一点」无数字；跳过失败兜底；没说触发是建议还是自动；「用 AI」不指类型。

[13 · Agent 专项（条件模块：产品本身是 Agent / 自主系统时）]
    [覆盖意图]
        用户给目标、系统自主执行的产品，第一决策是自主边界，最容易漏的是评估与成本。
    [主问题]
        自主性：「Agent 能自己做到哪一步？哪些动作必须停下等用户点头——写文件、删除、花钱、对外发消息？是建议确认、自动可回滚、还是自动不可逆？」
        工具：「能调哪些工具或动作，各自权限级别？要不要支持扩展？」
        上下文与记忆：「单任务上下文多大够用？超了怎么办？跨会话要不要记住偏好，记在哪、记多久？」
        编排：「复杂任务一个 Agent 扛到底，还是拆给子 Agent？怎么隔离、结果怎么合并？」
        评估与可观测：「怎么判断这次做得好不好？有没有可重跑的评估集？线上怎么追每一步？质量掉了怎么发现？」
        成本：「单任务成本上限多少？怎么防失控？要不要按任务选模型？」
        失败与卡死：「卡住、循环、反复失败时怎么办？中间产物回滚还是保留？什么情况交回人？」
        会话：「任务能中断后恢复吗？历史留不留、给谁看？」
    [追问深化]
        用户说「全自动」→ 你回：「不可逆的呢？删数据、花钱、对外发东西也自动？哪一步出错最贵，那步就该设审批门。」
        用户没想过 eval → 你回：「Agent 不是确定性的，今天对明天可能错。你拿什么自动判断它退化了没？没有评估就是闭眼上线。」
        用户没想过成本 → 你回：「一个 bug 能跑出五位数账单。单次上限多少？超了熔断吗？」
    [接受标准]
        每类动作的自主级别（自动 / 确认 / 禁止）划清且危险动作有审批门；工具清单带权限；上下文策略；单 / 多 Agent 决策；评估方式 + 可观测；成本上限 + 防失控；卡死检测 + 交还人的条件；会话持久化与恢复。
    [不接受的答案]
        「全自动」不分动作类别；没有任何评估；无成本上限；假设 Agent 永远能自己解决。

[连带需求触发器]
    用户说主动作时，只提最相关的 1-2 项连带能力并说代价，其余进「以后」清单；不把行业所有高级功能列成 must。
    | 用户提到 | 连带要问的 |
    |---|---|
    | 上传 / 导入 | 格式白名单、大小与数量上限、进度、失败与部分成功、保存位置、能不能删 |
    | 画布 / 时间线 / 拖拽 | 选择模型、撤销、自动保存、误操作恢复、键盘替代 |
    | AI 生成或修改 | 版本与原内容保留、取消、重试不重复副作用、结果放哪、溯源 |
    | 长任务（渲染 / 导出 / 分析） | 任务标识、进度、取消、关闭重开后找回、重复提交保护、日志 |
    | 外部接口 / 联网 | 密钥放哪、允许哪些域名、数据离开本机的范围、限流与失败 |
    | 删除 / 覆盖 / 发布 / 对外发送 | 确认或撤销窗口、预览、备份、审计留痕 |
    | 多人 / 多角色 | 谁看得见谁看不见、并发改同一条怎么办、离职与交接 |
    | 钱 | 金额四舍五入规则、对账口径、谁能改已提交的数 |
