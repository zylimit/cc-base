---
name: workflow-iteration
description: product-spec-builder 迭代模式启动时读。用户对已有 Product-Spec.md 提变更时的分类、追问、冲突检测、影响矩阵与阶段回退。
---

[使用时机]
    项目里已有 Product-Spec.md，用户开发中提新功能、改需求、调 UI、纠正误解，或下游送回「需求存疑」的反例。

[顶层规则]
    无缝衔接，不开场白，接住需求直接往下问。
    同样守 interview-principles：一次一问、逼出具体、反失败自检。别一听改需求就照单全收，该顶回去的顶回去。
    先判档（SKILL.md [交互深度分档]）：直推档改完复述一句；确认档一问带推荐；探索档才走完整追问。

[变更分类]
    - 澄清：补细节，不改行为或验收。
    - 加范围：新增用户可感知能力。
    - 减范围：删除或延后能力。
    - 行为变化：同一能力的规则、流程或结果变了。
    - 数据 / 权限变化：实体、可见性、删除、外部接口、密钥。
    - 验收变化：成功判据、规模或性能边界变了。
    - 纠正：旧 Spec 误解了用户原意（下游反例多属此类）。
    分类决定追问深度和回退到哪个阶段。

[追问规则]
    不重走 0-1 采访，只问变化带来的最高风险未知：
    1. 为什么要改，原方案哪里失败（什么事触发的）。
    2. 原来哪条判断错了——Spec 第几条、当时依据是什么、现在看错在哪；纯新增就写「新增，无旧判断」。
    3. 新行为替代旧行为，还是并存。
    4. 影响哪些已确认条目、关键流程哪一步变了。
    5. 输入、输出、数据、权限、平台受不受影响。
    6. 旧数据、旧流程要不要兼容。
    7. 哪些成功判据或验收要新增、修改、作废。
    用户已经明确的直接吸收，不要求重复解释整个产品。用户报新竞品或参考 → 立刻 WebSearch 其做法，追问「它的 X 你要不要、差异在哪」。

[冲突检测]
    加载现有 Spec 与澄清记录，逐项检查新需求是否与以下冲突，命中就把两条并排摆出来让用户选，不静默选边：
    - 明确非目标
    - 既定不可碰的决定
    - 已确认的规则与例外
    - 数据归属与可见性
    - 成功判据与反向指标
    - 已答过的澄清记录（重问只允许在新事实矛盾时，且先摆矛盾）

[影响矩阵]
    每次变更写清：
        变更条目 → Product-Spec 哪些段受影响 → Design-Brief / DESIGN.md 哪些页面与组件受影响 → DEV-PLAN 哪些 Phase / Task 受影响 → 代码哪些模块受影响 → 哪些测试失效 → 回退到哪个阶段
    阶段回退：
    - 只改描述、无行为影响 → 不回退。
    - 改用户流程、界面结构、数据、权限、平台 → 回 design-brief-builder / arch-designer，再回 dev-planner。
    - 设计不变、只改工作量 → 回 dev-planner。
    - 代码缺陷、不改需求 → 交 bug-fixer，不改 Spec。
    只提醒、不自动改下游；主 Agent 据此派对应 skill。

[更新]
    在现有 Spec 上直接改，保持结构，只改需要改的部分；标记与来源同步更新；被推翻的条目标「→ 被 <日期> 取代」，不删历史，不复用编号。
    反例进「规则与例外」标来源（哪个下游、哪个情境）；新答案追加澄清记录。
    涉及新 AI 功能 → 补 question-bank 12 的四问与护栏。
    按 templates/changelog-template.md 追加 Product-Spec-CHANGELOG.md：为什么改、原判断哪里错、影响、变更分类、回退到哪个阶段。
    改完按 SKILL.md [复述理解] 复述改后那次会怎么发生，通过即完成；跑 spec-lint 与 predev-lint。

[禁止]
    - 只改一处描述，留下关键流程、验收、CHANGELOG 脱节。
    - 删除历史而不留 CHANGELOG。
    - 把实现 Bug 伪装成需求变化。
    - 用户只改一个局部，就重新问完整题库。
    - 下游产物已失效仍宣称计划有效。
