# 从案例学习规则

仅在隐性规则、术语歧义或纠正传播确实影响当前需求时使用。以下是虚构教学片段，展示怎样区分解释；例子中的规则不能移植到用户项目。

## 从一件事找到分叉

用户：“我们用表格排活动，想让系统自动开放预约。”

可用的起点是最近一次活动从排入表格到有人预约的经过，先查用户已提供的表格列与说明。若仍不清楚，只问当前最关键的缺口：“最近一次活动排好之后，谁根据什么判断可以对外开放？”这比让用户选择状态机或审批框架更容易取得事实。

假设用户解释：“场地管理员先锁定时段，主办人备齐介绍后自行开放；但内部活动不用开放。”可以形成：

| 已知事项 | 对设计的影响 | 仍不能推断的内容 |
|---|---|---|
| 锁定场地与对外开放由不同人处理 | 至少有两种不同的业务动作和责任 | 不代表必须拆成两个服务 |
| 内部活动不对外开放 | 可见性与场地占用不能共用一个布尔值 | 不代表所有内部人员都可见 |
| 主办人决定资料是否齐备 | 不能静默替用户定义“齐备”的条件 | 是否允许开放后补资料仍未知 |

据此复述当前解释并选择一个反例：“如果介绍尚未写完，已锁定的场地还应占用吗？”只有这个差异影响当前范围时才问；如果来源已经回答，直接承接。

不佳做法是马上生成“草稿→审批→发布”全套流程：它把推测写成规则，还凭空增加审批岗位。

## 同一个词用包含与排除校准

用户：“开放前也能预览。”

这里可能是主办人预览、持链接的人预览，或所有人能搜索。先查现有 PRD 对参与者的说明；仍不清楚时，用具体输入区分：“未登录的人拿到预览链接，会看到活动详情吗？”不要直接写成“所有草稿支持公开链接”。

得到决定后，就地写入相关需求，例如“预览指主办人登录后查看，访客无法通过链接读取”，并附决定来源。术语解释和访问验收使用同一个例子；不建立第二份可能漂移的业务词库。

## 既有 PRD 与当前局部任务

用户给了 `PRD.md` 的“活动列表”章节，并要求把已经明确的“举办地点”列移到日期后。

可以直接定位该章节和当前界面，保留字段含义，更新相关布局说明与交接。一条短需求足够；没有 `Product-Spec.md`、品牌关键词、完整活动生命周期都不是这次移动列的阻塞条件。

如果用户实际说“把地点合并掉”，且可能意味着移除数据、隐藏列或合并地点实体，应先查上下文；仍无法区分时只澄清这个决定。不能因改动字数少就认定行为影响小。

## 纠正不是新增需求

用户：“我前面说的是主办人可预览，参与者还不能看。”

若 Agent 曾把预览写成全员可见，应记录理解纠正，并查找受影响的访问规则、预览路由、按钮文案、实现 Task 和验收例子。派单中写明当前含义与来源，不能只在变更记录写“调整权限”后让旧公开链接验收继续生效。

若本次没有权限修改的 ownership，交回主 Agent：“已定位 PRD 的预览定义；原解释影响访问策略与相关验收，需要同步这些位置。列表列顺序的独立工作可以继续。”不要越界修改，也不要让整个项目停在同一个未知上。

## 没有现成答案时给可讨论的方案

用户无法决定是否允许活动介绍在开放后修改，Agent 可以解释两种后果：允许修改能减少人工关停，但参与者可能按旧信息安排；限制修改便于保持一致，却可能放大纠错成本。推荐必须结合当前活动的实际风险，业务承诺尚未决定时写成候选。

相反，用户已委托列表的可逆排版细节，就按任务频率和现有设计作出选择，说明理由后推进。把每个细节都变成选择题并不会增加业务理解。

## 下一问解锁什么

工单由技师提交、验收员验收，产品负责人要看完成率，却不能代验收负责人决定「完成」。先把提交与验收写成已知动作，完成判据记进待定表（功能条目写「`[默认]` 首版只展示提交与验收记录，暂不计算完成率」）；给验收负责人问「待验收工单算完成吗，退回后怎么算」，说明答案将决定状态转换、完成率分子和对应验收。分母与统计时间若仍未知，分别保留待定，不用一个猜定的公式提前派发计算 Task。已明确的工单展示或无关文案可以继续。

负责人答复「仅验收通过算完成，退回待处理」后，把这一规则写入需求状态与统计口径，在变更记录里写明状态 / 统计相关 Task 的依赖和同一情境的验收要随之修订，交主 Agent 让 dev-planner 同步；原先候选口径标为被替代。分母与时间口径仍待决定，不能因分子已确定就声称完成率公式可验收。
