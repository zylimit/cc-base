# 贯穿五个阶段的预约教学事实

需要完整教学追演时读取。以下是原创、虚构情境，不是 SiteMaster 的产品需求，不是用户研究结果。需求、视觉、架构与 DFX 的例子共用本文件；其他参考只引用需要的规则，不各自建立一份完整真相。文中的设计建议和拟实验都没有运行结果。

## 参与者与当前环境

小型工作室目前通过电话预约、表格登记，再通知相关人。预约者可能是为孩子办理预约的家长；管理员处理预约名单。管理员经常密集查看记录，预约者用手机查看自己的预约。当前教学范围不含付款。

已有单应用和关系数据库由两人维护，没有专职消息基础设施人员。此事实约束维护成本，不证明任何一种数据库结构、消息产品或架构已经合适。

## 已给规则

| 标识 | 教学事实 | 用于区分的输入与结果 |
|---|---|---|
| R1 | 预约事实保存后才算预约成立；按钮反馈和通知送达不能代替这个事实 | 请求响应丢失时，预约可能已成立，也可能未成立，客户端不能自行判失败 |
| R2 | 重试同一提交意图要找回同一预约结果；姓名不代表意图 | 一个家长给两个孩子分别预约，可以是两个意图；同名不等于重复；同一提交再试不应产生第二个预约 |
| R3 | 希望预约成立后自动通知；通知失败不能取消预约，工作人员应能找到未完成的通知事项 | 已保存预约、通知失败时，预约仍成立，通知另行处理；不能显示“预约失败，请重新预约” |
| R4 | 取消释放对应名额，同时保留预约历史 | 取消后另一意图可使用释放的名额；旧预约仍可区分为已取消，不能仅物理删除记录 |

竞争演示使用“某时段只剩一个可预约名额”的数据，以检验两个不同意图竞争同一名额；这不是所有产品或所有场次都只能一人的规则。时段、预约者和名额的具体数据模型由当前需求决定。

## 未知与影响

| 未知 | 影响什么 | 已知条件下仍可继续什么 |
|---|---|---|
| 通知允许等待多久，算提供方接收、设备送达还是人已阅读 | 通知服务目标、时间提示、告警与人工介入时机 | 分开预约/通知状态、保留通知事项、定义候选测量起止点 |
| 实际业务负载、数据量和设备网络条件 | 容量、延迟目标、是否值得新增独立处理设施 | 比较已有应用与数据库内的最小方案，设计测量方法 |
| 外部通知提供方的幂等、查询与送达回执能力 | 外部成功但本地未知时能否安全重发或查证 | 保留发送意图与尝试记录，明确不能承诺恰好一次送达 |
| 取消由谁发起、通知未完成时取消如何影响后续发送、历史保留期限 | 取消权限、通知内容/终止规则、清理策略 | 只确认 R4 的名额释放与历史保留，避免替用户补这些规则 |
| 编辑提交内容后怎样区分原意图与新意图，标识的有效范围与期限 | 冲突处理、幂等契约和界面恢复 | 保留原请求上下文，给出候选规则及其影响，不用姓名去重 |

## 同一事实在各阶段的落点

- 需求：R1–R4 写进相关行为与验收；未知保持为影响明确的缺口。完整结果链包括提交、核对预约结果和通知后续，不因追求“最小”删掉必要结果查证。
- Brief：确定预约事实优先、通知作为另一条状态的视觉层次；名单比较和手机单条查询可用不同密度，但状态含义相同。
- Maker：用演示控制触发响应未知、预约已成立但通知失败等分支；声明模拟边界，让人能理解结果并选择已允许的后续动作。
- 架构：预约事实、同一意图和名额约束需要明确归属；比较直接调用通知与持久保存待通知事项，追演中断与重复发送。
- DFX：分别定义预约结果正确性、通知义务保留和通知交付的观察；HTTP 成功、持久保存、外部接收与人已阅读不能互相替代。
