---
name: spec-self-review
description: product-spec-builder 生成 Spec 前与复述前读。需求的单元测试：逐条测需求写得好不好，不测系统做得对不对；过不了的回去补问或改写。
---

[定位]
    清单项只问「Spec 里写清楚了没有」，不问「系统对不对」。禁止「验证 / 测试 / 确认 + 行为」这种实现测试的写法——那是 test-builder 的事。
    每条对照 Spec 的具体段落过，答不上就是缺口；缺口分两种：会让开发返工的回去补问，便宜能补的进待定问题表。

[完整性]
    - 产品概述里写清了为什么做、谁受益、谁买单、谁可能变差，且有一个真实案例撑着吗？
    - 应用场景至少有一个有名字、有顺序、有工具的真实现状故事，例外单独写了吗？
    - 每个核心功能都有「用户做什么 → 系统做什么 → 得到什么」三段吗？
    - 每条规则至少一个例子和一个例外（或明确无例外）吗？
    - 关键流程至少一条无断点、主角有名字、有高潮一拍，且至少一个失败场景有触发、提示、数据保护和下一步吗？
    - 数据实体、关系、单一写入者、可见性、删除路径写了吗（纯前端无持久化可略）？
    - 范围里至少 3 条显式非目标，且「以后」清单与非目标分开了吗？

[清晰]
    - 功能条目里还有「快、简单、直观、无缝、智能、合理、适当、优化体验」这类无法判定的词吗？每处换成数字、例子或可观察事实。
    - 同一个东西在 Spec 里只有一个叫法吗？
    - 每条功能都能指到一个来源（案例编号或用户原话）吗？没标记的按推断对待，标上。
    - 产品形状（类型、平台、使用情境、首要动作）写清了吗？

[一致]
    - 功能条目与规则例外之间有没有矛盾（例外那次按功能条目会走错）？
    - 关键流程与功能条目一致吗——流程里出现的每一步都有对应功能？
    - 成功判据与范围一致吗——判据依赖的功能是 P0 吗？
    - 决策依据里每条矛盾都有用户的选择，且与正文一致吗？

[可度量]
    - 成功判据能数出来、技术无关、有当前基线、至少一条反向指标吗？
    - 非功能六类各有数字或明确「不要求」吗？
    - AI 功能（如有）有质量阈值、触发方式、绝不能做清单、不确定时行为、降级、延迟成本吗？

[标记纪律]
    - 功能条目里没有 `[待定]` 吗？不清楚的是否已写成 `[默认]` 做法 + 待定问题表一行？
    - 待定问题表每行都有「影响什么 / 谁能答 / 押后到 / 不答先按什么做」吗？
    - `[确认]` 的条目每条都能指到一个真实案例或用户原话吗？转述和推测有没有混进 `[确认]`？
    - `[默认]` 的条目都是低风险、用户可否决、且写明了依据吗？

[隐含合规]
    - 产品涉个人数据 / 支付 / 医疗 / 物理设备 / 未成年人吗？涉了，对应隐含要求（个保法、PCI、PHI、fail-safe）点名了吗——标 `[确认]` 或进待定表交 DFX，没有替用户编？

[交接]
    - 使用情境与首要动作、受益者画像、关键流程——design-brief-builder 能直接起手吗？
    - 数据归属、故障后果、隐含合规——arch-designer / dfx-designer 能直接定档吗？
    - 每条功能的「为什么、谁受益、规则与例外」——主 Agent 派单时抄得出业务上下文吗？

[交接测试与边际测试]
    - 把 Spec 交给一个没参与对话的工程师，他能直接开工不用猜吗？需要猜的地方就是还没够。
    - 再问一个问题，答案会改变要做什么吗？不会，就别问了。
