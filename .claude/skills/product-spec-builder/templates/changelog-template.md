# 变更记录模板

文件名 `Product-Spec-CHANGELOG.md`。一条记录回答四件事：改了什么、为什么改、原来的判断哪里错了、影响哪些已确认条目。只写「改了什么」的记录，下次没人知道当初为什么这么定。

---

## 模板格式

```markdown
# 变更记录

## [v1.2] - YYYY-MM-DD
**为什么改**：<什么事触发的——用户新认识 / 下游反例 / 外部约束>
**原判断哪里错**：<Spec 第几条、当时依据是什么、现在看错在哪；没错只是新增就写「新增，无旧判断」>
**影响**：<哪些已确认条目要跟着变 / 哪些 Phase 受影响>
**分类与回退**：<澄清 / 加范围 / 减范围 / 行为变化 / 数据权限变化 / 验收变化 / 纠正；回到 design-brief-builder / arch-designer / dev-planner / 不回退>

### 新增
- <功能或内容>（来源标记）

### 修改
- <改了什么，改成什么样>

### 删除
- <删了什么、为什么>

---

## [v1.0] - YYYY-MM-DD
- 初始版本
```

---

## 记录规则

- 版本号每次迭代 +0.1，重大改版 +1.0；日期 YYYY-MM-DD。
- 「为什么改」与「原判断哪里错」不能空：这两行是用户以后核对自己判断的证据，也是 progress.md Decisions 的来源。
- 新增、修改、删除分开写，没有的分类不写；一条记录对应一个变更点。
- 新增控件写位置，数值变更写前后对比。
- AI 能力的增减单独一条。
- 下游反例（code-review / tester / bug-fixer 报的「需求存疑」）触发的变更，在「为什么改」里写清反例是什么。
- 「分类与回退」按 references/workflow-iteration.md 的变更分类写，回退到哪个阶段由主 Agent 据此派对应 skill。

## 完整示例

```markdown
# 变更记录

## [v1.2] - 2026-09-15
**为什么改**：tester 写「VIP 单老张休假」用例时发现 Spec 没写走法，报需求存疑；用户确认退回组长派。
**原判断哪里错**：Spec 规则与例外第 2 条只写了「VIP 直达老张」，当时把老张常在当成了事实，实际每年休假两次。
**影响**：功能需求「VIP 直达」条目；Phase 2 派单规则。
**分类与回退**：行为变化；回 dev-planner 更新 Phase 2 Task，设计不变。

### 修改
- VIP 直达：老张不在（系统里标记休假）时退回组长派单 `[确认]`（来源：用户原话 2026-09-15）

### 删除
- 待定问题「VIP 单老张不在时怎么走」（已解决）

---

## [v1.1] - 2026-09-10
**为什么改**：用户看复述时指出客户不需要收通知，客服要。
**原判断哪里错**：Spec 反馈条目是 `[推断]`（从「群里发照片」推的是给客户看），实际照片是给客服结单用的。
**影响**：功能需求「反馈」条目；关键流程客服路径。
**分类与回退**：纠正；回 design-brief-builder 改结单提醒的落点，再回 dev-planner。

### 修改
- 反馈：维修工上传照片 → 客服收到结单提醒（原写客户收到通知）`[确认]`（来源：用户纠正 2026-09-10）

---

## [v1.0] - 2026-09-08
- 初始版本
```
