# Product Spec 输出模板

文件名 Product-Spec.md。每条内容带来源标记：`[确认]` 用户确认的事实（来源写用户原话或案例编号）、`[推断]` AI 的推断（来源写推断依据）、`[默认]` AI 采用的低风险默认（来源写依据，用户可否决）、`[待定]` 没弄清的——只出现在「待定问题」表里，功能条目不许挂它。AI 的建议单独标「建议」。没标记的按推断对待。
必需段（spec-lint 机器检查）：产品概述 / 应用场景 / 功能需求 / 技术方向，段名不改；功能条目必须是「用户做什么 → 系统做什么 → 得到什么」。

## 0. AI 使用说明
- 本文档是产品功能、范围、行为和验收的事实来源；下游 AI（dev-planner / implementer / code-reviewer / tester）按它开工。
- 优先实现 P0；不实现「非目标」里明确排除的内容；按「成功判据」与功能条目的产出判断完成。
- 条目标 `[推断]` `[默认]` 的，实现时若现场证据相反，回报「需求存疑」并附反例，不自行改需求；`[待定]` 表里的按「不答先按什么做」做。

## 产品概述
- 这是什么：一句人话
- 为什么现在做：现状里谁在为什么买单（时间 / 钱 / 风险），用一个真实案例说
- 谁受益、谁买单、谁可能变差：三种人分开写，是同一个人也要说明
- 核心价值：做成之后哪一步不用再做了
- 风险档位：自用 / 内部 / 对外或涉钱涉合规（决定本文档长度与验收深度）

## 写作要点

1. **产品概述**：为什么做要有一个真实案例撑着；三种人（受益 / 买单 / 变差）分开写，写不出「变差」的多半没问够；风险档位定长度——自用两页够，内部五到八页，对外按条目走。
2. **应用场景**：真实发生过的，有人名（可化名）、有顺序、有工具；例外单独写，例外是规则的边界。段名保持「应用场景」开头。
3. **成功判据**：可数、技术无关（「客服 2 分钟录完一单」是，「接口 200ms」不是）、有基线、有反向指标；不用注册量下载量当北极星。
4. **范围与非目标**：每条 P0 单独实现也是可用的一小步；非目标至少 3 条；「以后」与非目标分开。
5. **功能需求**：每条三段带箭头、带标记与来源；`[确认]` 必须能指到一个案例或用户原话；不清楚的写 `[默认]` 做法而不是挂待定。
6. **规则与例外**：一条规则至少一个例子；没有例外就写「无」，别空着。
7. **关键流程**：主角有名字、有高潮、有失败路径；这是 design-brief-builder 与 tester 的直接输入。
8. **决策依据**：写否掉了什么和为什么，「谁定的」四选一；用户坚持而 AI 有异议的，把 AI 的理由也记一句；矛盾的两边和用户的选择写清。
9. **AI 能力**：只写替代人脑判断的地方，四问齐（质量条 / 触发 / 不确定时 / 降级）+ 绝不能做；不是每个产品都有，没有就删段。
10. **非功能与隐含合规**：六类逐项数字或「不要求」；行业隐含要求点名不替答。
11. **待定问题**：每行五列齐；没有「谁能答」是空喊，没有「不答先按什么做」会卡住开发。
12. **澄清记录**：问过的不再问，这张表是证据；纠正过的写原以为什么，方便用户看见改变。
13. **机器闸**：生成后跑 `node .claude/harness/harness.mjs spec-lint` 与 `node .claude/scripts/predev-lint.mjs`，不过先修。
