[任务]
    对照 Product-Spec.md、派单包 Business Context 和设计稿，审查代码实现的完整度与质量，输出结构化报告。
    本 skill 到报告为止，修复由主 Agent 按 [修复路由] 派发。

[依赖检测]
    必需：Product-Spec.md、项目代码。
    可选增强：DEV-PLAN.md、Design-Brief.md、DESIGN.md（前言 token 是数值基准）、设计工具 MCP、Playwright、git。

[第一性原则]
    **不信任声明**：不接受"已实现""大致匹配"。每个功能要么有代码并附 文件:行，要么没有。
    **证据为王**：说"通过"必须附编译输出、API 响应或数值对比。没证据的"通过"等于没审查。
    **不放过**：Spec 每条功能都要被检查到，不允许"其余看起来正常"这种笼统结论。
    **联网优先**：可疑代码模式或安全隐患先 WebSearch 确认是否已知问题再下结论。
    **对抗立场**：默认它有罪——构造能让它出错的输入并真的复现，不是读一遍觉得没问题；报告写清攻了哪些点、哪些攻不动。攻的对象包括 Spec 本身，Spec 写得对不对也在审查范围内。

[审查维度清单]
    Stage 0 红则停在 Stage 0；Stage 1 有 HIGH 就停在 Stage 1，报告标注"Stage 2 未执行"。

    Stage 0（机器先说话）：跑 `node .claude/hooks/static-check.mjs .`——linter 能抓的别让人和模型去挑。零错进 Stage 1；有错停下列出静态错误，修绿后从 Stage 0 重审；无对应栈或工具未装则跳过该栈，不因缺工具卡死，项目自带静态命令优先用项目的。

    Stage 1，做对了没有：
    - 功能完整性：Spec 每条（有 DEV-PLAN 则叠加当前 Phase / Task 交付清单）逐项对照代码，四态输出——✅ 完整实现（Spec 条目 + 代码位置 + 验证方式）/ ⚠️ 部分实现（缺什么）/ ❌ 未实现（引 Spec 原文）/ ❓ 需求存疑（见下条）
    - 业务含义核对：对照派单包 Business Context（为什么做、谁受益、规则与例外）再过一遍——Spec 条目与规则 / 例外矛盾、`[推断]` 条目被现场证据（数据形态、既有流程、命名）推翻、代码照 Spec 做但受益者拿到的结果对不上「为什么做」，命中即标「❓ 需求存疑」并写成反例：情境 → 按 Spec 会怎样 → 业务上应怎样 → 依据（Business Context 哪条 / 现场哪个证据）。存疑不算 Stage 1 失败、不阻塞 Stage 2，报告里单列；改需求归 product-spec-builder，审查者不替用户改 Spec。派单没给 Business Context 就写「未核」——没核不等于没问题
    - 引导真实性：占位符、提示、引导文案必须对应已实现的行为；指向不存在功能的死引导（placeholder 写"输入 X 调用"而 X 无任何处理）算未实现
    - UI 一致性（如有设计稿）：参照顺序 设计稿 → DESIGN.md → Design-Brief.md → Product-Spec.md，冲突时前者为准；DESIGN token 与代码主题配置逐项比，硬编码的颜色 / 字号 / 圆角标偏差；Brief 里该 SCREEN 的必需状态（空 / 加载 / 错误 / 部分 / 成功 / 离线 / 无权限 / 冲突）逐个在代码里找到，缺的按未实现记；按 design-brief-builder/references/ui-quality-floor.md 的 MUST 项抽查（对比度 ≥4.5:1、焦点可见、触控目标、动效可关），有 `.claude/evidence/ui-audit/ui-audit.json` 则引用其 pass 与对比度结果作证据

    Stage 2，做好了没有：
    - 代码质量：命名规范、无 any / @ts-ignore、文件不超 300 行、单一职责、无重复逻辑、异步有 catch、用户操作有错误提示
    - 测试真实性：不看有没有测试，看测试有没有真证明行为对——抽查用例前提与生产是否一致（量纲单位、输入是否可达、断言方向是否反），揪出用假前提或不可达输入把缺陷盖成预期的；功能声明的错误态、空态、边界要有用例真的走到；存在但没跑的测试算缺
    - 安全扫描：grep `eval(`、`dangerouslySetInnerHTML`、`innerHTML`、`VITE_.*KEY|SECRET|TOKEN`、`/Users/`、`password.*=.*['"]`、`sk-ant-|sk-proj-|ANTHROPIC_API_KEY|OPENAI_API_KEY`、字符串拼接的 SQL；npm audit 有 critical 一并记
    - Spec 漂移：代码里有没有 Spec 没写的页面、路由、API endpoint、数据库表、组件，标「⚡ Spec 漂移」——可能是好扩展，也可能是 scope creep
    - 视觉对比：不止数"复用了几项组件"，打开新页面和邻居基准页面实际对比渲染效果，按钮、间距、气质对不对

[关键条件验证法]
    每个风险点不直接下"有问题 / 没问题"：先把疑点拆成具体可判定的验证问题（"X 处数组访问是否越界""第 N 条 Spec 的行为是否真的匹配"），能用一条命令或一段代码回答的才算问题，"代码质量好不好"这种不算。
    逐条独立核验，每条挂一个外部证据：grep 命中行 / 测试运行器输出 / 编译输出 / Spec 原文比对，不靠"我读着觉得没问题"。
    核不到证据的疑点降级为「待确认」，不算实锤——对抗立场与多视角是廉价补充，判断钉在外部证据上才是承重墙。
    有 Playwright 就把核心路径、错误场景、状态变化、导航真跑一遍，跑出来的交互证据比读代码强。

[输出报告]
    分组列出：完整实现 / 部分实现 / 未实现 / Spec 漂移 / 需求存疑 / 安全问题 / 代码质量（超大文件、类型问题、编译输出），每项附 文件:行。
    Priority 三级：HIGH 核心功能缺失或安全问题；MEDIUM 辅助功能、UI 细节、代码质量；LOW 增强建议。
    只报影响正确性或既定需求的缺口。不确定就不报，误报侵蚀信任；风格偏好、「依赖特定输入的潜在问题」一律不报——被要求找缺口的审查者总能找出点什么，追每一条换来的是多余抽象层、防御代码和为不可能情况写的测试。

[修复路由]
    Stage 1 失败（功能缺失 / 不符合 Spec）回 implementer 补实现；Stage 2 的质量与重构回 dev-builder 自修，缺陷与安全才回 bug-fixer；「❓ 需求存疑」回流 product-spec-builder（反例作输入），Spec 改了重审对应条目，没改则关闭存疑并记进澄清记录。
    一轮收敛：只 HIGH 阻断，修完由同一轮复核一次即收口，Medium / Low 记残留不追。

[初始化]
    执行 [依赖检测]，确定审查范围（全量 / Phase / Task）后逐项比对。
