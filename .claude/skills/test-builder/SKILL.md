[任务]
    为高价值逻辑建立并执行可重跑的回归测试，让 dev-builder 四步走第 2 步「测试完整性」从口号变成真卡点（跑套件、贴运行器输出）。
    **写测 ≠ 被测作者**：派 tester fresh 实例（或非该功能作者的另一 implementer 实例）落地，主 Agent 只写提示词 + 独立复核运行输出，自己不写测试代码；铁律见 rules/subagent-dispatch.md [隔离原则]。

[依赖检测]
    必需：项目代码、测试运行器（前端 vitest / 后端 pytest）；缺运行器按 [基建与取舍] 自主 scaffold（pytest 进 requirements 或 venv，vitest 进 devDependencies），要用户权限才提示。
    可选增强：Product-Spec.md（契约与数据规则条目定必测项）、DEV-PLAN.md（定边界）、git diff（锁定本次改动）。

[第一性原则]
    **业务场景先取材**：用例先从 Spec 的「工作现状故事」和「规则与例外」拿——每条规则一个正例、每个例外一个用例、`[待定]` 对应的分支 skip 并注明待定原因；再补工程风险维度。例外用例最容易抓到反例：例外那次按代码会走错，多半是 Spec 没写清，不是代码写错。
    **契约优先**：预算先砸在出错最贵的地方——跨边界契约、解析器、去重主键、状态迁移。这些破了是数据级灾难，比 UI 像素重要得多。
    **真跑真证据**：说"测过了"必须附运行器真实输出（passed / failed 计数 + 用例名）。没有运行输出的"通过"等于没测。
    **不追覆盖率**：不以覆盖率数字为目标，不为凑数写断言空洞的用例。一个能挡住真实回归的用例，胜过十个测 getter 的。
    **可重跑入库**：留下来的必须能重跑、能入库、下次改动自动挡。一次性 `python -c` 验证不算交付。
    **联网优先**：不熟的测试框架用法、fixture 模式、mock 数据库先 WebSearch 确认再动手。

[测试量与分级]
    测试代码占有效代码 1/3～1/2，按风险给预算，不做全量覆盖。
    高风险五种优先吃预算：泄密、毁数据、装坏别人项目、发错版、签字闸误放行。
    每个测试文件头标 `# risk: high|medium|low`，跑测顺序与老化退休按这个分级取舍。

[测试维度清单]
    必须测（破了是契约级 / 数据级灾难）：跨边界契约（导出↔导入往返一致性、序列化↔反序列化、API 请求↔响应）、解析器与数据清洗（多源格式、字段名规范化、表头探测、坏编码容错）、去重与合并主键（去重键计算、冲突判定、覆盖 / 忽略决策）、关键边界与异常（空值 / null、nan / inf、越界、超大与负数，尤其防御性 return 分支）。
    推荐测：纯函数工具（坐标换算、格式化、状态映射）、状态迁移与枚举映射、关键 API endpoint 的入参校验与回落；有 Playwright 时的核心交互流程。
    明确不测：UI 像素与快照（脆、维护重，靠人工眼检 + 设计稿对照）、三方库自身行为、getter / setter 与无分支透传样板。

[基建与取舍]
    无基建则最小化 scaffold（参照 templates/test-scaffold.md）：约定目录 + 一个样例用例，派子 Agent 落地，主 Agent 验"空套件能跑"再继续。
    先列候选（对照 [测试维度清单] + git diff / 当前 Task 范围）按「破了代价」排序，只写必须测 + 高价值推荐测；每个取舍说明理由，不闷头写也不闷头跳。
    数据库依赖优先构造数据喂纯函数 / 构造器，不起真库；必须真库时用最小 fixture + 测试库，绝不碰生产或基线数据。

[失败三分流]
    判断是哪一种之前，先看失败信息、Spec 契约和 Business Context，别条件反射改测试迁就代码：
    - 代码错（测试发现真 bug）→ 派 bug-fixer 修业务代码 → 重跑
    - 测试错（断言 / 夹具写错）→ 派 tester 修测试 → 重跑
    - Spec 错（断言按 Spec 写没错，但与 Business Context 的规则 / 例外矛盾，或它是 `[推断]` 条目而现场证据相反）→ 报「需求存疑」+ 反例（情境 → 按 Spec 会怎样 → 业务上应怎样 → 依据），主 Agent 回流 product-spec-builder；这条用例先 skip 并注明原因，既不改断言迁就代码，也不迁就 Spec

[测试完成度判断]
    四条全中才算完成：测试基建可用（套件能跑、有真实输出）；「必须测」项里与本次改动相关的已覆盖并全绿；失败用例已闭环、无遗留红；新增用例已入库可重跑。
    汇报附：运行器原始输出、本轮新增 / 修改的用例清单 + 各自防的回归类型、未测项 + 不测理由（不假装全覆盖）。
    时效性：贴的运行输出必须是同一条消息里刚跑的；其后又改了代码就重跑，不接受"前面跑过了"。
    red-lock（先写红测试锁定缺陷再修）只给线上行为的 bug 与核心解析器 / 契约的缺陷，边角输入不锁。

[初始化]
    执行 [依赖检测] 与基建探测，无基建先 scaffold 并验空套件能跑。
