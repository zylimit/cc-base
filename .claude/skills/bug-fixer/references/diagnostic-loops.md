# 按症状选择诊断回路

> codex-base `407c3bc` 方法（上游 mattpocock/skills@74ca5fe，MIT，综合改写）；预约例是虚构案例，其中数字、命令、路径不自动成为本项目要求。

故障只在部分环境出现、偶发 / 时序 / 性能异常、有多个解释，或「修过仍失败」时读取。目标是找到能改变判断的证据，沿 SKILL.md 的红测锁与 [修复熔断] 执行；不新增固定假设数量或重试轮次。

先用现有工具找最短且会经过原故障路径的回路，记录为何选它及没有覆盖什么；无需先禁止读代码，也不默认安装调试依赖。

| 症状与可得材料 | 优先回路 | 触达证据与下一步 |
|---|---|---|
| 已有失败测试或稳定命令 | 原测试；必要时缩到 CLI/HTTP fixture 或最短人工操作 | 保留原输入、断言与退出码；缩小后仍回到原测试。 |
| 只在某请求/事件后出现 | 脱敏请求或事件重放，固定身份、状态与顺序 | 核对重放确实经过同一判断；权限、时点不同则不能视为同一复现。 |
| 某版本/配置/环境才出现 | 固定输入，对比版本、配置、依赖与权限；有可靠好坏端点时二分 | 每步只变一个相关条件，记首个分歧；二分命中的变更仍须解释机制。 |
| 偶发、竞争或回应乱序 | 用现有 fake clock、可控 promise/屏障或事件队列指定先后，再跑正常顺序对照 | 记录事件 ID、对象/草稿版本、到达顺序与断言；固定时序下红锁实际变红才算触达。 |
| 性能退化 | 固定测量边界、负载、数据量、机器/配置与可比基线，重复有界测量 | 报每次耗时及波动，区分环境噪声和代码路径；扩大 timeout 或一次快慢不证明根因。 |

每次试验记运行条件、尝试次数/失败次数、实际耗时、原症状断言和正常对照。偶发问题先控制触发条件，不通过无界重试提高「碰到一次」或「跑到绿」的机会。若仍无法复现，保留已查路径、候选解释、缺少的条件、下一项能区分解释的实验；临时日志、fixture 和观测文件标明清理位置，环境或进程操作沿已有授权。

## 一个时序例子

旧回应覆盖新草稿反馈：固定 `Q1(v1) 发出 → 编辑 v2 → Q2(v2) 发出 → Q2 回应 → Q1 回应`，在每个边界记录请求 ID、草稿版本、回应到达次序、当前显示版本。红锁断言 Q1 到达后仍显示 v2 对应反馈；另跑 Q1 先于 Q2 到达的正常顺序。旧回应的服务端预约事实仍按其规则保留，客户端只阻止旧反馈覆盖当前草稿。修复前执行到断言因旧覆盖而失败；修复后以相同序列和断言变绿，再跑原完整预约情境（重复提交、未知结果、保存成功但通知失败）及正常对照。若原情境没有实际执行，明确记为未复验。
