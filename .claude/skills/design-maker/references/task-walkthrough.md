# 带任务试走原型

> codex-base `d1a3287` 教学材料；预约例是虚构案例，其中数字、命令、路径不自动成为本项目要求。

用于跨页面任务、易误解的结果状态或参与者试走。以下是虚构教学例子，应换成当前需求的真实规则与可安全使用的样本。它不规定访谈次数或评分表。

使用预约完整例时先读 [统一教学事实](../../product-spec-builder/references/reservation-case.md)。布局实现、真实/模拟行为与实际渲染的具体方法见 [原型构建参考](prototype-construction.md)；本文件聚焦观察人的理解和恢复。

## 先给目的，再观察路线

目的示例：“找到周日下午的合适场次，办理预约，并判断这次预约是否已经成立。”起始条件包含已知的预约对象与时间限制；页面数据使用明确的演示内容。若涉及离开后查证，先承接项目实际的结果查询与恢复约定。

不要直接告诉参与者“点击第二行，再点右下角蓝色按钮”。那只能证明能跟随指令，无法暴露入口、信息次序或状态文案的问题。Agent 自检可以使用预定操作路线，但必须与参与者自行选择的路线区分。

观察重点按当前未知选择：

| 观察点 | 能获得的证据 | 不能据此声称 |
|---|---|---|
| 是否找到合适场次 | 当时使用的信息、搜索/比较路线、卡点 | 所有用户都能找到 |
| 是否理解预约反馈 | 参与者对结果与下一步的具体解释 | 后端真的受理或发送了通知 |
| 填错人数后能否继续 | 错误提示、输入保留、修正路线 | 所有业务规则都正确 |
| 被打断后能否接上 | 原型内实际保留的状态与恢复方式 | 真实跨设备、网络或持久化可靠性 |

## 结果未知不能伪装成失败或成功

若实际需求允许“已提交但结果待查询”的情境，可以在演示控制中触发它。页面应呈现用户确实能知道的信息和已确认的后续动作；假后端不能让每次点击都变成成功。

如果是否允许重新预约仍是未知业务规则，可先展示讨论中的状态与问题，明确该流程尚未定稿；其他已知页面继续完成。不能把“再试一次”随意绑定为新的真实预约行为。

原型模拟的确认编号、发送、保存等应清楚说明为演示，不做远端副作用。标注不必占据每个产品按钮，可用清晰的原型说明与独立演示控制；用户任务区继续使用业务语言。

预约教学例 R1/R3 中，响应未知与“预约已成立、通知失败”是不同情境。先观察人能否辨认当前已知的事实；核对结果后应保留同一意图与已成立结果。不能把 R3 的通知失败直接做成重新预约按钮，也不能在尚未查证 R1 时直接显示成功。

## 一条发现怎样传下去

观察示例：“参与者看到红色‘发送失败’，认为预约也失败，准备再办一次；教学事实 R3 规定通知失败不取消预约。”此句是拟观察情境，未实际运行。

先查实际规则来源，不能为了让画面只显示一种状态而改变预约成功条件。若规则已明确，可提出分开预约结果/通知后续的层次、文案及已允许的核对入口；若双方对规则有分歧，交主 Agent 补足决定。

修正应同时指向相关需求、Brief 的状态说明、原型区域、实现 Task 与验收例子。只更新截图或按钮颜色会让后续代码继续沿用旧解释。

## 如何记录结果

在 `demo/design-plan.md` 或交接说明中简短记录：

- 情境与所用版本/路径、数据；是否真实参与者或 Agent 自检。
- 实际做了什么、观察到什么；必要的去标识原话。
- 哪项假设受到支持或反驳，尚不能确定什么。
- 修订位置、业务依据和未走过的路线。

没有观察就写未观察；不能用“按钮都能点”“用户没提意见”填成满意。小范围明确调整只核对相关路线，不要求再次完成整个产品的试走。
