## 1. 优先级栈（冲突时前压后）

1. 可靠性——单子不丢（SC-2 十分钟内到手，丢一单就是派错一单）
2. 隐私——客户电话只客服可见（个保法 + Q-2）
3. 可服务性——三人班组没有运维，出事要能自己看出来
4. 成本——一台内网机，不加机器
5. 性能——20 人在线，5 秒内可见即可

理由：用户原话「只能保一个：派单准」；内网单机、无运维，任何要加机器或加人的方案排在后面。

## 3. 延迟与重试预算（韧性维必填）

| 层 | 预算(ms) | 超时(ms) | 重试次数 | 退避 | 失败时的 fallback |
|---|---|---|---|---|---|
| 浏览器（点提交 → 收到回执） | 800 | 4500 | 0 | — | 提示「网络不通，草稿已留」，表单不清空，客服可再点一次（幂等键兜重复） |
| API（鉴权 + 派单规则 + 组装响应） | 2200 | 1200 | 0 | — | 回 500 带工单 id，日志留一行，不自己重试 |
| DB（写工单 + 读组长列表） | 2000 | 600 | 1 | 固定 300ms | 两次都失败抛错交 API；连不上时 `/api/health` 转红 |
| 端到端 | 5000 | — | — | — | 5 秒没到组长列表：组长页顶部提示「同步较慢，请刷新确认」 |

各层之和 800 + 2200 + 2000 = 5000ms，正好压在 §2 第 6 维性能的「录单提交到组长列表可见 ≤ 5 秒」上；重试只放 DB 层（1 次 × 600ms 超时 = 1200ms，塞得进本层 2000ms 预算），浏览器与 API 一律写 0——重试逐层相乘，三层各 3 次就是 27 次。

## 6. 质量属性场景明细（critical/high 维度逐条展开）

### 场景 R-1：断网重试不重复建单
- 来源：客服小李 · 刺激：提交时手机热点断网，点了两次提交 · 环境：正常工作时段 · 制品：orders 模块
- 响应：第二次提交命中幂等键，返回同一工单 id · 响应度量：重复建单 0 单
- 验证：回归测试「同幂等键重放只建一单」

### 场景 S-1：越权读取客户电话
- 来源：维修工小张 · 刺激：把 URL 里的工单 id 改成别人的 · 环境：已登录 · 制品：auth + orders
- 响应：他人工单返回 403；本人工单响应不含电话字段 · 响应度量：越权成功 0 次
- 验证：权限专项测试（THR-1）

### 场景 P-1：日志不带电话
- 来源：任何请求 · 刺激：记录工单日志 · 环境：生产 · 制品：全部模块
- 响应：日志只写工单 id 与客户名称 · 响应度量：日志含电话 0 行
- 验证：fitness no-pii-in-logs

## 9. 取舍记录（被牺牲方 + 理由 + 越档理由）

- 韧性只到 medium：不做多副本，三人班组接受 30 分钟内人工重启，换成本第 4 位
- 性能不做缓存层：20 人在线 5 秒可见靠数据库索引即可，换可修改性（ADR-2 后果）
- 隐私定 high 而不是 critical：电话字段泄露是合规事故不是人身事故，且无 catalog 时 critical 与 high 执法一样
