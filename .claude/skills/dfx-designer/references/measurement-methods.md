# 让质量目标对应真实结果

> codex-base `d1a3287` 教学材料；预约例是虚构案例，其中数字、命令、路径不自动成为本项目要求。

需要制定目标、解释指标、设计测量或比较恢复/跨属性代价时读取相关部分。本文提供原创方法，不复制外部 SLO 数字、表格或固定检查套餐。评价范围和执行角色服从当前 DFX 定档结果与主 Agent 派单范围；无数据时可以给带缺口的讨论稿，不能假定通过。

## 1. 从业务损失到结果定义

先问发生什么失效、伤害谁、在哪段业务时间内、有什么现行补救；区分可重做的工作、不可重建的数据、错误外部动作和不可接受的损害。证据可来自实际需求、事故、任务记录或已有承诺；没有事故记录不是风险为零。

把场景写具体：谁发起什么、运行在什么环境/负载、哪个对象遇到刺激、系统必须保持什么结果。结果先用业务语言表达，再选度量。比如"查询能给出本次预约是否成立的正确结果"，比"API 返回 200"更接近使用者需要的事情。

数值不是唯一精确性。权限、名额和同一意图可写成明确断言；响应时限、恢复时限、可接受数据丢失范围则需要来源与条件。保护边界不能因为统计大多数成功而允许少量越权或损害。

## 2. 区分结果、目标、机制与采集

| 层次 | 要回答的问题 | 不能拿来替代它的东西 |
|---|---|---|
| 结果定义 | 人在规定条件下要得到什么，什么算正确/完成 | 某个按钮变绿、某个技术事件方便统计 |
| 目标与依据 | 希望何时、在什么比例或边界内满足；谁/哪份依据作出承诺 | 示例 SLA、行业习惯、没有来源的提升百分比 |
| 设计机制 | 哪个责任模块用什么办法保护结果，哪些失效仍可能发生 | 单独写"缓存/重试/备份"就称质量达标 |
| 采集实现 | 在哪里采集哪些事件，怎样计算，哪些情况看不到 | 把仅服务端日志的覆盖范围当全部用户任务 |
| 验证结果 | 什么版本/环境/窗口下实际观察到什么 | 目标写完、检查声明存在、拟实验或旧回执 |

已有承诺保留来源；候选目标写建议依据与代价；当前基线写测量时间、环境、输入与证据。没有测量写"未测"，不是 0；目标未知不等于当前不达标，实际 FAIL 也不能被改写成目标未知。

技术指标良好但用户仍办不成时，先检查结果定义和测量覆盖。例如提供方已接收消息，使用者却未收到；可能是采集停在中间步骤，不能直接说用户提高了要求。

## 3. 让分母和时间窗口保留失败

先定义观察总体，再选择计算：

- **观察单位**：是一次用户意图、请求尝试、数据记录还是时间片？这些数量不同。重试可以增加尝试次数，但不应把同一意图重复计成多个独立任务；诊断重试流量时则应单独保留尝试。
- **正确结果集合**：按规则拒绝也可能是服务正确完成，不能把"没有名额"一律算服务故障；但合法请求被错误拒绝也不能按 HTTP 状态方便地排除。业务成交/预约成立率与服务正确处理率是不同指标。
- **起止事件**：用户开始、请求发出、服务端接收、事务提交、用户能查询、外部接收、设备送达、人已阅读分别是什么时间。选择与结果一致的起止点，区分端到端等待和服务处理时长。
- **窗口与归属**：按发起时刻还是完成时刻归入窗口，跨窗口的慢任务、恢复后补齐的迟到事件如何记录。不能把未完成任务移出分母，或只统计已完成项来掩盖长尾。
- **取消、超时与未知**：预先说明是否属于应被服务的任务，以及尚未结算状态的处理。取消可能已经产生部分事实；超时可能已经保存。保留未知数量与后续核对，不为得出漂亮比例临时剔除。
- **采集位置与盲区**：服务端看不到在它之前失败的请求；数据库看不到用户是否读懂反馈；提供方回执未必代表最终交付。记录盲区，必要时用授权范围内的端到端观察补充，不能把没有记录当没有失败。
- **分群、采样与偏差**：设备/网络、低频重要任务、失败路径可能在聚合值中消失。说明样本来源和缺失群体；采样方式不能系统性排除慢请求或错误。个人数据采集同时遵守隐私边界。

当结果定义与目标已确认时，比例可表达为"窗口内符合结果判据的观察单位 / 同窗口内按定义应观察的单位"，但分子/分母要具体落到上述语义。零样本或无有效分母写无样本/不可计算，不是 100%。P95 等分位数还需记录样本数量、单位、环境和未完成任务处理；不以一个分位值掩盖数据丢失或权限错误。

## 4. 让同一结果经历不同条件

按当前场景选择，不要求每个小任务重做全套。重要的是条件变化后仍检查同一结果，而不是只有正常情况下满足的指标。

| 条件 | 怎样选有区分力的情境 | 需要保留的观察 |
|---|---|---|
| 正常 | 代表数据、当前主要任务、常见设备/网络与权限 | 基线及端到端结果；没有代表性依据就标为探索样本 |
| 压力 | 已知峰值、突发、数据积累或依赖变慢；未知负载先测量 | 等待、拒绝、积压、资源消耗，以及是否破坏一致性/访问规则 |
| 失败 | 当前机制最怕的断点或外部未知结果 | 哪些事实已成立、哪些未知、谁可查证，失败是否可见 |
| 恢复 | 依赖恢复、进程重启后的重放/补偿/人工接管 | 待办是否遗漏、结果是否重复、积压是否影响新请求；恢复时限仍需来源 |
| 变更 | 实际计划中的升级、迁移、规则/模式或契约变化 | 新旧调用方与数据是否仍有明确语义，不可逆变化后如何恢复或前向修复 |

性能测试需说明数据规模、并发/到达方式、持续时间、预热、硬件与网络、依赖是否真实或模拟。故障验证需可控条件与观察点；不擅自安装或对当前服务做破坏性操作。执行范围由主 Agent 派单与当前定档决定，不按"压力"标签自建更轻或更重等级。

## 5. 反查机制的跨属性代价

为当前实际机制写"降低哪种损失，也可能增加什么"，再给能推翻它的情境：

- 缓存减少等待，但旧数据可能造成错误判断或越权可见；需要有依据的新鲜度/隔离条件。
- 重试增加恢复机会，也可能放大故障流量、费用和重复外部副作用；不能用较高尝试成功率掩盖用户重复处理。
- 持久任务保留义务，也增加状态维护、积压诊断、数据清理和共享数据库负载；不能由"持久"推断外部恰好一次。
- 更细日志有助定位，但可能引入个人数据、秘密暴露与保留成本；诊断便利不能越过保护要求。
- 共享组件可降低共同规则的修改成本，也可能把不同变化原因绑在一起；应看规则与消费者契约，不以重复实现数越少越好作目标。

服务可用率的组合要检查共享数据库、网络、控制面和人为操作等相关故障。不能默认独立再相乘得出高精度承诺；没有足够数据时用故障场景与依赖分析说明局限。

不可逆迁移应明确可停止的位置、兼容条件、备份恢复或前向修复路径、期间新增数据怎样处理、恢复后的验证。回滚二进制并不自动回滚数据或已发送通知。没有可行补救就显式保留风险和依赖决定，不能用"一键回滚"填模板。

## 6. 分别评价服务、任务体验与无障碍

| 关注 | 结果与方法 | 不能据此推断 |
|---|---|---|
| 服务可用性 | 在约定环境/时间内，合法任务能得到按规则正确的服务结果；用运行事件与端到端观察核对 | 页面容易理解，或所有使用者都能操作 |
| 易用性 | 有代表性的使用者能辨认入口、完成任务、理解结果并从相关错误恢复；记录具体行为和卡点 | 服务持续可用，或没有观察到的群体也没有障碍 |
| 无障碍 | 对实际任务检查语义、键盘、焦点、对比、缩放和适用辅助技术/残障使用者需求 | 全站合规、所有障碍已消除，或一般用户成功就足够 |

这些可以在实际 DFX/设计说明中分别保留评价，不增加 harness attributes 字段。有 catalog 的项目 attributes 仍只用 module-catalog.json 已有字段（reliability、resilience、security、safety、privacy、performance、availability、maintainability）；档位仍按 [定档策略] 的六档（critical/high/medium/low/minimal/none）。文档的 N/A、候选和未知不是档位，也不能借它们删除既有保护声明。

## 7. 预约例的完整测量链

先读 [统一预约事实](../../product-spec-builder/references/reservation-case.md)，架构候选见 [预约协作追演](../../arch-designer/references/collaboration-walkthrough.md)。下列是拟规格/拟验证，不存在运行数据或 PASS。

### 预约结果正确性与同一意图

- 损失：用户重复占名额、工作人员无法判断哪次成立，取消后历史或可用名额错误。
- 场景：同一意图在响应丢失后重试；两个不同意图竞争最后一个名额；按已确认权限取消。
- 结果：按 R1/R2 找回同一结果、名额不被重复占用；按 R4 释放名额且保留历史。不同孩子的独立意图不能因同名被误判重复。
- 目标依据：上述是教学断言，不需要先编成功率；通知时间未知也不阻止这些断言形成。
- 候选机制：明确预约写入权、意图关联、名额约束与取消语义；事务/版本等实现仍需架构选择与验证。
- 采集：核对受控输入、请求意图关联、权威预约/名额/历史与用户可查询的结果；尝试次数和业务意图区分。只看客户端按钮或某次 HTTP 200 会漏掉重复写入与未知结果。
- 反证：相同意图新建第二笔、同名独立意图被丢弃、两笔占同一名额、取消仅删历史等任一观察均需解释并修正，不能被其他成功样本抵消。

### 用户何时得到可判断的结果

- 结果定义：用户针对这次意图能得到与权威事实一致的结论；按规则拒绝可作为正确服务结果，不能和预约实际成立率混用。
- 目标依据：允许等待与数据/负载条件尚未确认，不能承诺固定响应值。可先列候选测量方法，不称满足服务目标。
- 采集实现：分别记录用户尝试、服务收到、事实提交、界面获得可判断结果的时间；保留无法到达服务的缺口、超时/未知任务及迟到结果。
- 窗口/分母：明确以哪次意图及发起窗口计数，重复请求另记诊断指标。没有客户端或端到端证据时，只能报告服务内处理范围，不能声称全部用户等待已测。
- 反证：服务处理很快但用户仍不知道是否预约成功，应回查反馈/查询链；不是自动降低目标或将其排除样本。

### 通知义务、发送与最终交付

- 结果定义：R3 先要求已成立预约的通知后续可找到；"义务未丢失""提供方已接收""收件设备收到""人已阅读"是不同结果。
- 候选机制：与预约在同一事务保存待通知事项，可保护该中断窗口的义务；外部成功、本地未知仍可能重复，能力未核验不能承诺恰好一次。
- 采集实现：预约事实、通知事项、发送尝试、提供方回执分别关联；只看已发送记录会漏掉根本未创建的事项，应核对从预约到通知义务的覆盖。
- 时间/分母：若目标是通知交付，要确认起止点、符合通知条件的预约集合、窗口、取消如何处理、迟到/未知回执；不能临时只把收到回执的记录放进分母。
- 未知：允许等待多久、送达口径、取消后的发送规则、提供方幂等/查询能力仍影响承诺与自动恢复。可以继续记录状态与设计测量，不能给这些未知填模板数字。
- 反证：预约还在而通知义务无法查找，或外部只接收却被报为人已阅读，都推翻相应结果声明；通知失败不允许用取消预约来"恢复一致"。

## 8. 交接时保留的最小证据链

在现有 DFX 规格中留下规则来源、场景、结果定义、目标状态/依据、机制/模块、采集实现与盲区、反证和当前证据。critical/high 对齐实际验证落点（adapters / 测试 / fitness 闸）；人工核查只是待核查说明，不能代替验证落点要求的最新一次 PASS。

将缺口分为目标待定、缺检查、未运行、测量覆盖不足或实际 FAIL，并说明影响哪项承诺、哪个 Task 可继续。更正结果定义时同步实际需求、架构、界面与验证起止点；旧证据是否仍适用由主 Agent 按绑定和事实判断，不把全部未知统一记成失败或成功。
