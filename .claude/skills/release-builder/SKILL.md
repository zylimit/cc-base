description: 当用户说要打包、部署、发布、上线，或项目开发完成准备交付时使用。
disable-model-invocation: true
argument-hint: "[版本号或部署目标（可选）]"

[任务]
    按项目类型执行构建 → 打包 → 测试 → 发布，确保产物能安装、能运行、无隐私泄露、无安全漏洞。
    `disable-model-invocation: true`：发布是有副作用的工作流，主 Agent 不代触发——用户口头说"发布 / 打包 / 上线"时，回指 /release-builder 请他亲自敲。

[依赖检测]
    基础：项目代码、git、构建工具、package.json。
    渠道：按用户选定的渠道检测所需 CLI 与认证状态；只打包不发布则不检测部署工具。
    缺失工具自己判断装法直接装；要登录认证、或缺签名证书这类用户专属资产，说明需要什么并让用户准备。

[第一性原则]
    **dev 测通 ≠ 打包能用**：开发环境和打包后的运行时环境完全不同，路径、依赖打包方式、权限都不同。必须从安装包测，不能只测 dev。
    **隐私是底线**：发布产物绝不含个人数据——数据库文件、session、API Key、开发者路径、用户名。没有例外，没有豁免。
    **安装后测试**：Desktop 从安装包装到系统目录测，CLI 全局安装后测，Web 部署后在线测，不从构建输出目录测。
    **联网优先**：打包报错先 WebSearch，特别是签名、公证、打包器与部署 CLI 的版本兼容。
    **测试是打包前的闸门**：构建验证只证明"包能起来、语法没错"，不证明功能对。打包前必须有相关功能回归测试跑过且通过的真实输出；卡点未过先派 test-builder 跑通再打包，"部署 / 打包"指令不豁免这一条（与四步走第 2 步同一闸门，复用而非另起一套）。
    **卡住先诊断**：进程 CPU 0% 而运行时长仍在涨 = 死锁，不是慢也不是网络，别干等。打包工具对依赖布局敏感（electron-builder 会去遍历 pnpm 的符号链接依赖树），且配置声明 ≠ 实际状态（.npmrc 写了 hoisted ≠ node_modules 真是扁平，增量 install 会让二者脱节），打包前先验实际布局。

[发布检查清单]
    版本：package.json version 已按语义化更新，CHANGELOG 已更新，工作区干净。
    构建：构建命令零错误，产物存在且大小合理，异常偏大就排查是否打了不该打的东西。
    隐私审计（绝对底线，对实际的构建产物目录执行）：
    - `grep -rn "/Users/"` 查开发者路径与个人信息
    - `find` 查 `*.db` / `.db-shm` / `.db-wal`、`.env*`、`credentials*` / `*.pem` / `*.key`、用户数据目录
    - `grep` 查 `sk-ant-` / `sk-proj-` / `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / 明文密码
    发现任何一项立刻停，修复后重新构建。
    依赖：npm audit 无 critical，构建过程无 MODULE_NOT_FOUND。
    Git：author 不暴露个人信息，.gitignore 覆盖所有数据文件（.env*、*.db、本地数据目录）。

[部署验收三件套]
    部署派 deployer Sub-Agent 执行，主 Agent 独立核查三件套，全过才算成功（哪怕它回报 incomplete 或空）；子 Agent 回报"完成"不是部署结果。
    1. 容器创建时间戳 + 镜像 tag：创建时间是否晚于最后一次提交、tag 是否目标版本。**勿看 "Up 时长"**——那可能是重启前旧容器的残留读数，会误导。
    2. 健康检查端点返回 200。
    3. live 冒烟：curl 真实端点验证新功能的产物确实存在，不是只看进程起没起。
    收尾：清掉子 Agent 留下的临时产物，确认版本号文件（release.conf / package.json）已提交。

[发布策略]
    Web：构建 → 隐私审计 → 配生产环境变量（密钥在平台配、不进代码）→ 部署并记录 URL → 访问验证无白屏 → 对照 Spec 冒烟。
    Desktop：构建 → 按平台打包并检查签名配置（无证书则告知用户绕过方式）→ 隐私审计 → 提醒用户从安装包装到系统目录启动 → 冒烟。
    CLI：构建 → 隐私审计 → npm publish 或打二进制 → 全局安装验证命令可运行 → 核心命令逐个冒烟。

[回退策略]
    Web：控制台或 CLI 回退到上一个成功部署。
    Desktop：已分发的安装包无法远程回退，修完 bump 版本重新打包发布。
    CLI：`npm deprecate` 旧版本，严重问题 72 小时内 unpublish，修完 bump 版本重发。

[工作流程]
    问清打包还是发布 / 什么渠道 / 什么平台 → 按需检测依赖 → 确认版本号 → 构建打包 → 用实际产物目录跑隐私审计（任一失败就停）→ 安装测试 → 冒烟测试 → 汇报全部结果、用户确认后发布（tag / Release / publish / 部署）→ 发布后再验一次，有问题走 [回退策略]。

[初始化]
    先问清发布需求（打包还是发布、渠道、平台）再动手。
