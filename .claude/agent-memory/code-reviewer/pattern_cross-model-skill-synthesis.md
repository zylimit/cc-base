审异模型 skill 内容合成（如 cc-base 方法并入 codex-base skill，来源表逐节标 K/C/合并）时的固定攻法，2026-09-22 codex-base predev-synthesis 三 skill 审查中验证有效：
1. 先数章节数：来源表声称合成后 SKILL.md「N 节」，逐个顶格 `[节名]` 直接数一遍核对；数字对不上说明表本身没跟着最终稿更新。
2. 来源表声称「整段搬入」的 reference/template/example 文件，逐份 `diff` 真实上游文件与目标仓副本——允许的差异只应是宿主免责声明前缀（版本号/工具名适配），一旦发现实质改写却仍标"K"，判来源表标注失准。
3. 标"K"但目标仓找不到对应单一小节（K 原文该方法散落在多处：某小节一句 + 某 references 文件的一部分 + 模板一角）时，实际是揉合重写不是整段搬运，建议标"合并"更准确；不算 HIGH，但值得记 LOW/MEDIUM 指出标注精度问题。
4. 同一虚构案例配对文件（如 brief+DESIGN 两份）检查免责声明前缀是否每份都加——常见只给其中一份加了历史快照声明，另一份被 diff -q 判定字节全同，是真实可复现的疏漏（本轮命中 after-sales-dispatch-DESIGN.md 漏加，姊妹文件 after-sales-dispatch-brief.md 有加）。
5. grep 全量搜目标仓没有的脚本/工具路径字样（如源仓的 `.claude/scripts`、`ui-audit`、`ui-slop-scan`、`odc`、`npx @xxx`），确认依赖处理写成「有工具才做，没有就未验证」而不是假装能跑；同时用 `find`+比对 `[文件结构]` 声明列表与磁盘实际文件是否一致，两头都要查（有文件未声明、有声明未落盘都算漏）。
6. grep 第三方编排层专属概念（四线切法、commander、第二模型互查、编队工单）没有被误塞进方法性 skill 正文——这类内容用户裁决过应归编队/团队规则，不归方法 skill。
7. 有自证 npm 脚本（manifest:check / pack:check 等）且无外部依赖时，直接独立跑一遍比只读回执可信，成本很低（本轮独立复现 manifest 148 文件、pack 157/157 全过，与回执一致）。
8. 触发词/清单类小节（隐含合规表、威胁表）合并时最容易被"泛化措辞"悄悄丢项：把 K 原表逐行数量与合成版列出的类别逐项比对，不能只看小节标题是否存在——本轮 K 的 9 类合规触发词被压成 6 类+一个兜底短语，"开源许可证""等保/加密出口"两类具体词彻底消失，只留在被免责声明豁免的虚构例里。
10. 新搬入的判据句拿本仓机器闸对拍（2026-09-24）：「不拿猜定 [默认] 顶」撞上 predev-lint「功能条目改写成 [默认]」；「有引擎时 UI 审计一并跑」撞上 ui-audit 只收目录且只开 index.html（传文件 rc2）。
11. 附带重生成的 FRAMEWORK-MANIFEST 看排序：gen-manifest 的 sort 不带 LC_ALL=C，zh_CN 下生成的清单在 C 下 --check 报漂移。
9. 业务判据本身被顺手改严/改松（如"第三方问卷答复自动标确认"改成"核实际权限才标确认"）时，即使改动方向是合理的自查修复，只要来源表仍写"保留原有材料"或标"K"，就要单独点名——判据变了不算"仅宿主适配"，读表的人会误以为逻辑和源仓一致。
