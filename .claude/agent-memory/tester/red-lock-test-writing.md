红锁测试的断言写**修复后应该成立的行为**，不是「缺陷能复现」。复现式断言（现在 exit 0、修好变 exit 1）语义是拧巴的，修完还得反过来改一遍。

**Why:** 红锁的两个目的是「缺陷固化成永久回归防线」和「修复有客观靶子（红转绿）」。复现式断言两个都拿不到——它修完就得删。

**How to apply:**
- 整体现在必须 FAIL，那是成功状态；交付时把「哪几条红、红因是功能缺失」逐条核到。
- **偶然绿的断言要显式标注**（如「白名单 sha256 不符须失效」——机制还没实现时命中本来就报错，绿得毫无信息量）。标成「防回归位」，别让人误读成已实现。
- **别读实现源码来决定断言**，用行为探测：先在临时仓造一次条件，观察脚本的实际能力（如「行内压制标记还认不认」），把结论存成变量喂给后续断言。这样实现换了路子测试不会假红。
- 一条缺陷若有多种合规修法（降级 rc 3 / 真扫到 rc 1），断言写**否定形式**（「rc 不许是 0」），别钉死某一种。
- 主 Agent 的目标行为裁定里若含技术上讲不通的部分，顶回去说理由再写，别闷头按错方案写一堆将来必删的断言。
- **「可见性断言」不替代「判定断言」**：实测过一次——`check-syntax` 的 SKIPPED 被改回 rc 0 时，原有的「SKIPPED 行必须打印出来」照样绿，只有另加的 rc/ok 断言才红。凡是「X 要在输出里看得见」的断言，旁边必须再配一条「X 导致的判定必须是什么」。
- **新断言交付前必须做一次反向验证**：临时把对应实现改回旧行为，确认新断言真的红且点名，再 `cp` 还原（勿 git checkout，见 [[audit-scripts-fragile-zones]]）。只跑正向全绿等于没有断言——顺带还能看出哪条老断言其实是摆设。
- **改「锁了旧行为」的断言不是删掉了事**：一条换一条起步，覆盖面只许涨不许缩；与红锁重叠的部分在行为测试里写成一条冒烟即可，深水区（哈希失配、条目过期）留给红锁，两边不重复造轮子。
