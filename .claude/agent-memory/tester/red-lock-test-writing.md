红锁测试的断言写**修复后应该成立的行为**，不是「缺陷能复现」。复现式断言（现在 exit 0、修好变 exit 1）语义是拧巴的，修完还得反过来改一遍。

**Why:** 红锁的两个目的是「缺陷固化成永久回归防线」和「修复有客观靶子（红转绿）」。复现式断言两个都拿不到——它修完就得删。

**How to apply:**
- 整体现在必须 FAIL，那是成功状态；交付时把「哪几条红、红因是功能缺失」逐条核到。
- **偶然绿的断言要显式标注**（如「白名单 sha256 不符须失效」——机制还没实现时命中本来就报错，绿得毫无信息量）。标成「防回归位」，别让人误读成已实现。
- **别读实现源码来决定断言**，用行为探测：先在临时仓造一次条件，观察脚本的实际能力（如「行内压制标记还认不认」），把结论存成变量喂给后续断言。这样实现换了路子测试不会假红。
- 一条缺陷若有多种合规修法（降级 rc 3 / 真扫到 rc 1），断言写**否定形式**（「rc 不许是 0」），别钉死某一种。
- **否定形式必须点名主体，别写成「N 个命令里至少一个非 0」**：析取判据会被**用法错 rc 2** 冒充成「检查真抓到了」。踩过一次——E4b/E4c 跑一列命令里混了个引擎从不存在的 `ledger --verify-evidence`，旧 parser 静默吞未知 flag 时它 rc 0 无害，parser 一收严变 rc 2，两条断言从此拿用法错撑绿，真正该由 `ledger=1` 提供的证据被垃圾数据盖住。写成「`ledger` 自己 rc != 0」才验的是它本该验的东西。
- **验红打两版补丁，不是一版**：只废掉主判定者的（如只让 `ledger` 失明、`risk` 仍报）证明新判据比旧的严——旧析取判据在这版下照样绿；全废的（整条校验失明）证明缺陷本体仍被抓。只跑后者说不出「判据有没有被改弱」。
- 主 Agent 的目标行为裁定里若含技术上讲不通的部分，顶回去说理由再写，别闷头按错方案写一堆将来必删的断言。
- **「可见性断言」不替代「判定断言」**：实测过一次——`check-syntax` 的 SKIPPED 被改回 rc 0 时，原有的「SKIPPED 行必须打印出来」照样绿，只有另加的 rc/ok 断言才红。凡是「X 要在输出里看得见」的断言，旁边必须再配一条「X 导致的判定必须是什么」。
- **新断言交付前必须做一次反向验证**：临时把对应实现改回旧行为，确认新断言真的红且点名，再 `cp` 还原（勿 git checkout，见 [[audit-scripts-fragile-zones]]）。只跑正向全绿等于没有断言——顺带还能看出哪条老断言其实是摆设。
- **改「锁了旧行为」的断言不是删掉了事**：一条换一条起步，覆盖面只许涨不许缩；与红锁重叠的部分在行为测试里写成一条冒烟即可，深水区（哈希失配、条目过期）留给红锁，两边不重复造轮子。
- **被测代码在 Out of Scope 时这样验红**：让测试脚本收一个位置参数指向被测实现（`REPO` 目录或单个 `.mjs`，默认本仓），把被测对象 `cp` 到 /tmp、在副本上打补丁，然后 `bash 测试.sh /tmp/副本` 跑同一份断言。正向红锁在副本上打「修复补丁」验转绿；已修好的分支则反过来打「退回旧行为」的变异补丁验必红。零改动、无还原风险，比改本仓再回滚干净得多；顺手 `sha256sum -c` 复核仓里那份逐字节没动过再收工。顺带再打一版「天真修法」副本（如只加拦停、不接熔断），确认防砖类断言真的会红，别让它当橡皮图章。
- **命令的自述状态不能当判据，要取旁路派生的收敛态**：实测过一次——`stop` 的 win32 分支被改坏后，它自己把孤儿子进程收了，照样回 `{"ok":true,"status":"stopped"}` rc=0；只有另跑 `status`（从 state.json + pid 存活派生）才看得见真相是 `dead` + state 停在 `running`。断言写在自述上那一版，变异后全绿。凡「做完了吗」类断言，判据一律换成独立命令读到的落盘状态。
- **测试自身的卫生也要有断言，否则那个修等于没锁**：清理逻辑（杀进程、删临时文件）改错了整套照样绿。把它变成一条真断言——如按记录下来的各 childPid 当 pgid 查残留进程，精确到组所以不误伤并发跑的别的测试。实测把 `kill -9 -pgid` 改回单杀，这条立刻红并打印出泄漏进程；没有它，那个修永远没人守。
- **对照组的期望值必须写死字面量，不许从「同批别的探测」的结果里取**：实测过一次——路径归一化三态里，相对路径那条本该在变异下仍绿（用来证明红的是绝对路径那两态），但它拿了态一探测回填的变量当期望值，态一一红它跟着红，对照组当场失效。写死同一个字面量，两种写法同名照样锁得住。
- **单元测试守住了工具函数，不等于守住了调用点**：`repoRelative` 的三态单测早就在 selftest 里，但坏在 `path.resolve(root, dir)` 这个调用点上时它一动不动——变异改的是「谁喂给它」。凡是「helper + 调用点」成对的归一化逻辑，断言要落在 CLI 行为层（records 有没有真读到 + source/note 报的是不是同一个地方），单测只是补充。
- **防砖/熔断类断言按轨迹判，别按次数判**：stop-gate 三振熔断的实际形态是 `BBB.B`——5 次里拦 4 次。写成「blocks<=3」会把正确实现判红。正解是记轨迹串，断言「前 4 次里至少出现一次放行」。
- **契约里「哪个字段/形态算合规」不确定时，用行为探测选形态而不是赌**：主 Agent 给的修法有两条等效路（如哈希扩到三行窗口 / 要求豁免行仍在围栏内），断言就只写否定形式（「这次攻击后豁免不许还生效」），两条路都能转绿；控制组那半则先拿候选形态各试一次、把实际被接受的那种存进变量（`BOUNDFORM`）喂给后续断言，实现换了写法测试不会假红。
- **契约从「可选」收严成「强制」时，只补正向断言挡不住回退**：实测过一次——把 `context` 改回可选（无 context 也豁免）后，「绑对了→生效」那条照样绿，只有「没绑→不生效且打点名 note」那条才红；反过来把白名单整个废掉，两条一起红，而反向那条靠的是**note 必须出现**才没被 rc=1 蒙混。收严类改动一律正反各一条，反向那条断言里必须点名那条 note。
- **「A 表有的 B 表也得有」类断言必须限定在 B 的表体内比，整文件 `grep -F` = 永久免检**：实测过一次——⑥ 拿整文件比四份排除表，`settings.json` 在 setup.sh 别处有 13 行、`'FRAMEWORK-MANIFEST.txt'` 在 release.mjs 另有个同名常量，这些臂从表里删光照样全绿。正解是先把表体抽出来（case 块 / 数组字面量 / 规则数组各自的起止）再逐条 `grep -qxF` 整行匹配；顺带整行匹配才分得清 `.DS_Store` 和 `*/.DS_Store` 这种子串关系。
- **首中即返回的表还要比「序」和「处置」，不能只比集合**：`case` 和 `manifestIncludes` 都是首个命中即返回，垃圾臂挪到 keep 臂之后就漏出去而集合毫无变化；把每条抽成 `<臂>TAB<drop|keep>` 后整序列 `cmp`，序、缺、多、keep 翻面四类漂移一网打尽。结构不同没法比序的那份（如 ps1 全是无条件 drop）就改为断言「它凭什么与序无关」，一旦出现 keep 分支当场红提醒回来补。
- **抽取式断言的自检写死条数，别写 `-ge`**：`-ge 20` 而实际 34，抽取正则半坏只抽到 25 条时闸不响、后面逐条比对全在空转。写死 `EXPECTED_ARMS=34` 并在报错里附「另一份表相对它多出哪些」，红了一眼看出是表改了还是抽取坏了。
- **正反两向的红因都要留在输出里**：`chk` 的 GOT 字段把原始 rc / 完整 stdout / 轨迹串全打出来，主 Agent 不用重跑就能判「这条红是 hook 没实现」还是「夹具没搭起来」。脚手架自证（沙箱 git 仓、catalog 就位、故障引擎确实给出契约外码）单独列一段并保持全绿，红全部集中在行为段。
- **红锁除了「验它现在红」，还要验「它修得好」**：把一版候选修复打进实现跑一遍，确认整组转绿。只验红证明得了缺陷在，证明不了这组断言彼此相容——防砖条款（如「仓外路径不许被改写」「不存在的路径不许崩」）很容易和主断言冲突，implementer 接手才发现就晚了。实测：软链归一化那组 5 条，候选修复下 5 条全绿且 selftest 268 不动，才敢交。
- **红锁跨了派单 Goal 没点名的同源方向时，照写但在回执里点出来让主 Agent 裁定**——别闷头扩范围，也别因为「派单没说」就放着同一处缺陷的另一半不锁。软链那条：Goal 只点名「入参经软链」，实测「根经软链、入参真实」是同一处 realpath 基准不对称的镜像方向，只 realpath 入参补不上。
- **「每条表成员一条断言」挡不住表长出新成员——必须再加一条成员集合对拍**：⑤ 给 10 条 pathspec 各写了断言，但加第 11 条时全体沉默，新成员天生免检（那九条前缀裸奔很久就是这么来的）。对拍写法：从**被测那份** core.mjs 里抠数组字面量成员，与测试自己的用例表排序后 `cmp`，报错打印「core 独有 / 本文件独有」。实测加一条假 pathspec、加一条假前缀都当场红并点名。
- **对拍断言必须能分辨「表真的变了」和「我的抽取正则坏了」**：这两种红的处置完全相反。做法是抽取返回哨兵值 + 写死期望条数（不写 `-ge`），抽不到就报「抽取坏了，不是表变了」。实测把被测表整个改名（模拟正则失效），红的是抽取自检那条而不是成员比对那条。
- **「特例先行」的老段落会伪装成全覆盖**：`.runtime/` 那条 untracked 断言写在前面，注释一句「③ 走的是 STATE_EXCLUDE_PREFIXES」就让人以为七条前缀都被守着，实则只守了一条、另有三条 PATHS 一条没碰。写覆盖类注释要点明「覆盖的是表里的哪几条」，别用表名替代条目。
